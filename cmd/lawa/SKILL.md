# Lawa: запуск workflow из чата Codex

Используй эту инструкцию только после явной просьбы пользователя запустить Lawa.
Обычное обсуждение или подготовка задачи не запускают workflow.

Эта инструкция рассчитана на окружение, где у тебя есть только бинарник lawa:
исходного кода и локальной документации может не быть. Поэтому обязательный контракт
workflow приведён ниже целиком. Встроенная инструкция и результат lawa validate
соответствуют установленной версии бинарника; материалы ветки main на GitHub могут
описывать более новую версию и служат дополнительным источником, а не заменой проверки.

## Перед запуском

1. Убедись, что в текущем чате есть одно финальное, понятное описание задачи.
   Если его нет, сначала уточни и сформулируй задачу вместе с пользователем.
2. Возьми название workflow и необязательный комментарий из явного вызова.
3. Найди workflow по названию в рабочей папке проекта. Если совпадений нет или
   их несколько, не выбирай молча: попроси пользователя указать точный файл.
4. Выполни lawa validate <workflow.json>. При ошибке покажи её и не создавай run.
5. Выполни lawa help и проверь app-run/app-series-next/app-series-fail/app-next,
   app-claim/app-continue-claim/app-reset-claim/app-bind/app-update. Если их
   нет, установлена старая версия Lawa: сообщи об этом и не запускай legacy run.
6. Выполни lawa version и сохрани точную версию в диагностике запуска. Значение
   dev означает локальную сборку, которая не поддерживает автоматическое обновление.

## Как построить workflow

Workflow — ровно один JSON-объект с двумя обязательными полями:

- id — непустая строка, понятное имя всего workflow;
- steps — непустой массив кубиков.

Необязательный корневой model задаёт общую модель для кубиков без собственного
model. Приоритет выбора: model кубика, затем model workflow, затем конфигурация Codex.

Каждый кубик содержит четыре обязательных поля:

- id — непустая строка, уникальная внутри workflow;
- type — только строка agent;
- prompt — непустая самостоятельная инструкция одному агенту;
- dependsOn — массив ID других кубиков; пустой массив означает немедленный старт.

Дополнительно кубику можно независимо задать:

- model — непустой ID модели Codex без пробелов;
- effort — непустой reasoning effort, поддерживаемый этой моделью;
- speed — только normal или fast.

Отсутствующие effort и speed наследуются из Codex; model сначала наследуется из
workflow и только затем из Codex. Не придумывай model или effort без запроса
пользователя либо явной причины в задаче. `speed: normal` принудительно выбирает
обычный режим для кубика, а `speed: fast` включает Fast mode Codex. Несовместимое
сочетание Codex отклонит с ошибкой; Lawa не подменяет его другим.

Не добавляй неизвестные поля и не меняй регистр имён. Все зависимости должны ссылаться
на существующие уникальные ID. Нельзя повторять зависимость или создавать прямые и
косвенные циклы. Порядок кубиков в steps не управляет запуском: его задаёт только
dependsOn. Кубики без зависимостей могут работать параллельно. Кубик с несколькими
зависимостями стартует только после успеха каждой из них.

Пиши prompt так, чтобы отдельный агент понял ожидаемый результат без истории этого
чата: укажи цель, границы работы, нужный формат результата и важные проверки. Общую
постановку пользователя Lawa передаст отдельно, поэтому не копируй её во все prompt.
Если кубику нужен результат коллеги, вырази это через dependsOn и попроси прочитать
его память или созданный файл; наличие чужой памяти само по себе не заменяет зависимость.

Пример: metrics запускается первым, architecture и security — параллельно после него,
а summary ждёт обе проверки независимо от порядка элементов в steps.

~~~json
{
  "id": "review",
  "model": "gpt-5.6-luna",
  "steps": [
    {
      "id": "summary",
      "type": "agent",
      "prompt": "Собери итоговый Markdown-отчёт из результатов архитектурного ревью и проверки безопасности. Укажи приоритеты, доказательства и ограничения.",
      "dependsOn": ["architecture", "security"]
    },
    {
      "id": "architecture",
      "type": "agent",
      "prompt": "Проведи архитектурное ревью по собранным метрикам. Запиши выводы и ссылки на код в свою память.",
      "dependsOn": ["metrics"],
      "model": "gpt-5.6-sol",
      "effort": "high",
      "speed": "normal"
    },
    {
      "id": "security",
      "type": "agent",
      "prompt": "Проверь границы доверия и обработку секретов по собранным метрикам. Запиши подтверждённые риски в свою память.",
      "dependsOn": ["metrics"],
      "speed": "fast"
    },
    {
      "id": "metrics",
      "type": "agent",
      "prompt": "Собери проверяемые метрики и факты о проекте, нужные следующим ревьюерам. Сохрани источники и ограничения.",
      "dependsOn": []
    }
  ]
}
~~~

Сохрани JSON в файл проекта и обязательно выполни lawa validate <workflow.json>.
Не запускай workflow, пока проверка не завершилась успешно.

## Запуск и наблюдение через Codex App

Любой workflow, запрошенный из Codex App, использует только app-native driver.
Никогда не запускай `lawa run`, `lawa resume` или их фоновые terminal-сеансы из
задачи Codex: процесс принадлежит создавшему его turn и может быть остановлен при
завершении этого turn. Не переходи на legacy молча даже для вложенного workflow,
временной рабочей папки или повторяющейся серии.

Нужны инструменты create_thread, fork_thread, set_thread_title,
send_message_to_thread, move_thread_to_sidebar_section, list_projects,
list_threads, read_thread и wait_threads. Для повторения также нужен
automation_update. Если требуемого инструмента нет, остановись до создания run и
назови отсутствующую возможность.

Через list_projects заранее сопоставь абсолютный cwd workflow с сохранёнными
проектами. Для каждого launch используй ровно один из двух app-native маршрутов:

- если `launch.cwd` точно равен пути сохранённого проекта, создай task через
  create_thread с этим projectId и environment=local;
- если сохранённого проекта нет, но текущая управляющая задача уже открыта ровно
  в `launch.cwd`, создай task через fork_thread с environment=same-directory;
- если ни одно условие не выполнено, остановись. Не подменяй cwd новой projectless-
  папкой и не запускай отдельный app-server: агент работал бы не с тем checkout
  либо исчез бы из живого интерфейса.

Создай run командой app-run с теми же cwd, task-file, comment-file,
initiator-thread-id и необязательным parent-run. Без повторения сохрани выведенный
runId; с `--repeat` сохрани seriesId и выполни возвращённое действие из раздела
ниже. Явный speed app-run отклоняет: task API не принимает service tier.

~~~sh
lawa app-run <workflow.json> --cwd <проект> --task-file <файл> \
  --initiator-thread-id <id-этого-чата>
lawa app-next <run-id>
~~~

app-next возвращает JSON:

- launch: если codexThreadId пуст, сначала найди точный title через list_threads.
  Запроси достаточно большой limit: отсутствие title на короткой странице последних
  задач не доказывает, что внешний вызов не состоялся.
  Используй единственное совпадение; при нескольких остановись. Только без
  совпадений проверь маршрут cwd и поддержку непустых model/effort, затем вызови
  app-claim. Только при mayCreate=true разрешён один внешний вызов.

  Для сохранённого проекта вызови create_thread с title, prompt, projectId,
  environment=local и непустыми model/effort как model/thinking; пустые override
  не передавай. Title и первое сообщение создаются атомарно. Полученный threadId
  немедленно передай в app-bind.

  Для несохранённого cwd вызови fork_thread с environment=same-directory и сразу,
  до отправки работы, сохрани полученный threadId через app-bind. Затем установи
  точный title через set_thread_title и передай точный launch.prompt единственным
  send_message_to_thread с model/thinking, если они непустые. Fork наследует только
  завершённую историю управляющей задачи; launch.prompt является самостоятельной
  постановкой кубика и имеет приоритет над этой историей.

  Сразу после app-bind вызови move_thread_to_sidebar_section для этого threadId,
  hostId и возвращённым `launch.sectionId` (сейчас `chats`): каждый агент Lawa
  должен появиться верхнеуровневой задачей в разделе Tasks, а не только быть
  спрятан внутри проекта. Операция
  идемпотентна. При её ошибке повтори безопасно и не запускай следующие кубики,
  пока задача не стала видимой. Затем сохрани running и немедленно снова вызови
  app-next, чтобы независимые кубики стартовали параллельно.

  Если create_thread вернул только clientThreadId, дождись готовности и найди
  threadId по точному title. После неопределённого ответа или mayCreate=false не
  вызывай create_thread/fork_thread повторно. Ищи точный title не более трёх раз.
  Если его нет, остановись и спроси разрешение на риск дубля. Только после ОК ещё
  раз проверь title, затем используй app-reset-claim и повтори создание один раз.

  Если codexThreadId уже непуст, используй только этот ID. Повтори app-bind не
  нужно; обеспечь точный title и размещение в `launch.sectionId`. Для Starting-задачи через
  read_thread проверь, присутствует ли точный launch.prompt: отправь его лишь если
  его ещё нет, затем сохрани running. Никогда не создавай или не подбирай замену.
- observe: передай сохранённые ID в wait_threads, максимум по восемь за вызов.
  Большие наборы опрашивай вращающимися группами с ограниченным ожиданием. Запрос
  ввода/подтверждения сохрани как waiting_for_approval; ошибку как failed.
  `interrupted` сохрани как cancelled вместе с revision из последнего app-next.
  Если пользователь не просил остановить workflow и текущий контроллер не
  завершался по его команде, возьми ID последнего interrupted turn и вызови
  app-continue-claim. Только при mayContinue=true отправь в тот же threadId один
  turn `continue`; при false сначала перечитай task и не дублируй отправку. После
  появления нового turn сохрани running с новой revision. Если пользователь явно
  остановил задачу, не продолжай её автоматически.

  В app-update всегда передавай revision из последнего app-next. При конфликте
  отбрось старое наблюдение и перечитай task; не повторяй прежний статус с новой
  revision. Пользователь продолжает тот же чат, новый task не создавай.
- Успех: сначала перечитай task через read_thread. Если уже начался новый turn,
  пользовательский ввод или подтверждение, продолжай наблюдение и не фиксируй успех.
  Иначе сохрани полный финальный ответ во временный UTF-8 файл и вызови lawa
  app-update <run-id> --step <id> --state succeeded --revision <N>
  --result-file <файл>. Принятый успех финализирует кубик: более поздние сообщения
  остаются в чате Codex App, но не откатывают workflow. После статуса вызови app-next.
- complete: сообщи итог и закончи наблюдение. blocked: покажи проблемные задачи и
  жди пользователя, не создавая новый run.

Для create_thread привязка следует сразу за атомарным title+prompt. Для fork_thread
привязка, наоборот, предшествует title и prompt, чтобы потеря следующего ответа не
потеряла identity уже созданной задачи. Никогда не заменяй сохранённый ID другим.
После перезапуска начни с app-next и продолжай через read_thread/wait_threads.
Не оставляй пользователя без обновления дольше 60 секунд. App-команды обновляют
meta.json и локальные отчёты; живые сообщения остаются в задачах Codex App.

### Вложенные workflow и срок жизни контроллера

Задача, которая запускает вложенный workflow Lawa, остаётся его управляющим чатом
до terminal результата. Она не заканчивает turn сразу после получения runId и не
оставляет workflow в terminal-сеансе. Все вложенные кубики создаются тем же
app-native протоколом, перемещаются в Tasks и доступны пользователю в реальном
времени. Передавай `--parent-run` только для фактически известного родительского
runId.

Если постановка специально требует освободить запускающую задачу до завершения
вложенного workflow, сначала создай отдельную видимую задачу-контроллер Codex в том
же cwd, передай ей самостоятельную инструкцию app-native наблюдения и убедись через
read_thread, что её turn начался. Лишь после этого исходная задача может завершиться.
Фоновый `exec`, shell job, `nohup` или terminal-сеанс не является контроллером.

### Legacy CLI: только внешний терминал

Используй этот контур только вне интерактивного app-native запуска: задачи отдельного
app-server не получают живые события в уже открытом Codex App.

Сохрани финальную постановку и комментарий в два временных файла через безопасный
файловый инструмент, не интерполируя пользовательский текст в shell. Затем запусти:

~~~sh
lawa run <workflow.json> \
  --cwd <абсолютный-путь-проекта> \
  --task-file <файл-постановки> \
  --comment-file <файл-комментария> \
  --initiator-thread-id <id-этого-чата>
~~~

Если комментария нет, не передавай `--comment-file`. Путь к бинарнику Codex обычно
берётся из PATH; при необходимости используй `--codex` из `lawa help`. Если ID
текущего чата недоступен, остановись и объясни причину: не подменяй его ID кубика.
Не создавай новый run для продолжения прежнего.

Передавай `--parent-run` только когда этот workflow действительно порождён другим
известным run Lawa. Не подставляй ID чата, серии или предполагаемый ID. Связь не
меняет исполнение, но позволяет локальному dashboard показать дочерний workflow
внутри родителя после перезапуска процессов. В таком случае добавь к команде
`--parent-run <run-id-родителя>`.

Сохрани выведенный runId в контексте этого чата. Оставайся интерфейсом управления:
не оставляй команду без наблюдения дольше 60 секунд. Пока процесс работает, жди
его новый stdout не более минуты за один цикл. Lawa обновляет локальные
`workflow-status.md`, `workflow-status.puml` и `workflow-status.png` при изменениях
и не реже раза в минуту. В stdout она печатает только краткую статистику и ссылку
на папку run: первый и финальный блоки сразу, промежуточные — не чаще раза в 5 минут.

Каждый напечатанный блок краткой статистики опубликуй одним сообщением в исходном
чате. Сохрани счётчики и VS Code-ссылку дословно, но не добавляй список кубиков,
не пересказывай `workflow-status.md` и не прикладывай PNG в чат. Пользователь откроет
подробности и встроенную картинку по ссылке. После финального блока с успешным
завершением не жди новых обновлений. Не отправляй ради статуса новые turn в чаты
кубиков и не создавай отдельный run. Полные ответы агентов остаются в их чатах.

Lawa строит Markdown и схему из одного снимка `meta.json`; порядок берётся из
сохранённого run, зависимости — из его `workflow.json`. В `workflow-status.md` ID
с непустым `codexThreadId` ведёт в точный чат кубика, а текущий PNG подключён
относительной ссылкой. Напечатанная ссылка
`vscode://file/<percent-encoded-absolute-run-dir>` всегда относится к текущему run.

Для PNG Lawa локально запускает `plantuml -pipe` с таймаутом 30 секунд; установка
и Java зависят от ОС, см. https://plantuml.com/command-line. Если renderer отсутствует,
вернул ошибку или не создал PNG, Lawa сохраняет актуальные Markdown и source, удаляет
старую картинку и добавляет короткую диагностику в ближайшую чат-сводку. Не останавливай
и не запускай workflow заново только из-за ошибки визуализации.

Если Lawa остановлена, продолжай тот же запуск командой lawa resume <run-id>.
Не вызывай run повторно. Resume сам отправляет один turn `continue` в чат, чей
последний turn имеет статус `interrupted`. Failed-чат пользователь продолжает
вручную; completed-чат Lawa не перезапускает.

Для общей картины пользователь может отдельно запустить `lawa serve`. Dashboard
доступен на `http://127.0.0.1:60800`, а сложный UI без реальных run — на `/preview`.
Сервер только читает snapshot и не требует Codex, Node.js или дополнительных файлов.
Он показывает тикет из структурированных полей постановки и кнопки действий.
«Тред JSONL» открывает найденный локальный rollout Codex в VS Code; это полный
сырой журнал, который dashboard не публикует по HTTP. Отсутствие или изменение
внутреннего layout Codex только скрывает эту необязательную кнопку.
Поиск охватывает всё дерево и сохранённые ID. Фильтр времени использует соседние
окна: переход «Раньше» с периода в один час показывает предыдущий час целиком,
без ограничения числа workflow внутри окна.

### Повторяющийся app-native запуск

Добавляй повторение только по явной просьбе пользователя. В Codex App передавай
режим в app-run; legacy `lawa run --repeat` здесь запрещён:

~~~sh
# Сразу после завершения; ровно 10 обычных run.
lawa app-run <workflow.json> <обычные-параметры> --repeat immediate --max-runs 10

# С задержкой от завершения предыдущего run; без лимита.
lawa app-run <workflow.json> <обычные-параметры> --repeat after --repeat-delay 1h

# По календарю и явной IANA-зоне.
lawa app-run <workflow.json> <обычные-параметры> \
  --repeat cron --cron "*/5 * * * *" --timezone Europe/Moscow
~~~

Cron содержит пять полей `minute hour day-of-month month day-of-week`, без секунд.
Не вычисляй UTC вручную: передай названную пользователем IANA-зону. Сохрани выведенные
`seriesId` и каждый `runId`. app-run/app-series-next возвращают одно действие:

- run — продолжай указанный runId обычным app-next-протоколом;
- wait — текущего run нет; nextRunAt уже устойчиво сохранён;
- complete/stopped/failed — серия терминальна, новые run запрещены.

Сразу после создания серии создай heartbeat текущей задачи через automation_update.
Его пользовательский prompt должен содержать seriesId, root и требование вызвать
`lawa app-series-next`, а затем выполнить возвращённое действие только app-native
способом. Настрой расписание через поля automation-инструмента, не печатай raw
директивы пользователю. Heartbeat служит восстановлением после завершения turn и
перезапуска Codex; `app-series-next` под lock возвращает существующий run либо
создаёт не более одного нового, поэтому повторное пробуждение безопасно.

Пока action=run, управляющий turn наблюдает его через wait_threads. После успеха
сразу снова вызови app-series-next: immediate может начать следующий run, after и
cron вернут wait до новой точки. При wait текущий turn может завершиться — heartbeat
разбудит ту же задачу не раньше расписания. При terminal серии поставь heartbeat
на паузу, чтобы он больше не будил чат.

Для остановки используй `lawa series-stop <series-id>`. Она запрещает будущие run,
но не прерывает уже работающий: дождись его терминального состояния. Пропущенная
cron-точка не догоняется. После `failed` или явно остановленного либо не
восстановившегося `interrupted` действует политика
stop-on-failure: сохрани причину в UTF-8 файл и вызови `lawa app-series-fail
<series-id> --run <run-id> --reason-file <файл>`. Новый run не создаётся, heartbeat
ставится на паузу, а проблемный app-native run остаётся доступен в прежних задачах.

### Если app-native Lawa завершилась с ошибкой

Сохрани `runId` и покажи пользователю полный текст ошибки без секретов. Не заменяй
его общим сообщением «workflow сломан» и не создавай новый run автоматически.

- Если обратимый отказ произошёл до app-claim, устрани указанную причину Codex и
  продолжи тот же run через app-next. Новый app-run запрещён.
- Если Codex мог создать task/fork, но ID не подтверждён, не повторяй внешний
  вызов: он может создать дубликат. Ищи точный title и следуй протоколу claim/reset
  выше; без явного согласия пользователя reset запрещён.
- Для другой ошибки сначала следуй рекомендации из её текста. Если безопасного
  действия не указано, остановись и сообщи `runId`, команду и ошибку пользователю,
  не угадывая способ восстановления.

## Память и безопасность

Lawa создаёт отдельный чат и отдельный файл памяти для каждого кубика. App-native
агент читает доступную память, но не изменяет служебные файлы: после успеха его
финальный ответ атомарно сохраняет управляющий чат. Legacy-агент обновляет только
собственный memory/<threadId>.md. Чужую память, workflow.json, task.md и meta.json
изменять нельзя. Память коллег можно читать, но зависимый кубик всё равно ждёт их
успеха.

Не обходи sandbox, ограничения организации и запросы авторизации Codex. В legacy
CLI Ctrl+C или SIGTERM останавливают новые волны и прерывают активные turn через
Codex; следующий resume продолжает только подтверждённые interrupted-чаты. В
app-native режиме используй сохранённые task ID и app-continue-claim, не дублируя
failed, completed или уже заново запущенный turn.

## Обновление Lawa

Не обновляй Lawa фоном или во время активного workflow. Только после явной просьбы
пользователя выполни `lawa update`: команда покажет переход версии и точные пути,
проверит checksum release-установщика и запросит подтверждение. Для разрешённого
неинтерактивного обновления файлов можно использовать `lawa update --yes`.

Обычный `--yes` не разрешает установку PlantUML, пакетный менеджер или sudo. Если
обновление сообщает об отсутствующем PlantUML, отдельно покажи пользователю точную
системную команду. Добавляй `--install-plantuml` только после явного согласия;
без согласия продолжай обновление Lawa с предупреждением о недоступных PNG.
