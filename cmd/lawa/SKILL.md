# Lawa: запуск workflow из чата Codex

Используй эту инструкцию только после явной просьбы пользователя запустить Lawa.
Обычное обсуждение или подготовка задачи не запускают workflow.

Эта инструкция рассчитана на окружение, где у тебя есть только бинарник lawa:
исходного кода и локальной документации может не быть. Поэтому обязательный контракт
workflow приведён ниже целиком. Встроенная инструкция и результат lawa validate
соответствуют установленной версии бинарника; материалы ветки main на GitHub могут
описывать более новую версию и служат дополнительным источником, а не заменой проверки.

## Перед запуском

1. Убедись, что в текущем чате есть одно финальное, понятное описание задачи.
   Если его нет, сначала уточни и сформулируй задачу вместе с пользователем.
2. Возьми название workflow и необязательный комментарий из явного вызова.
3. Найди workflow по названию в рабочей папке проекта. Если совпадений нет или
   их несколько, не выбирай молча: попроси пользователя указать точный файл.
4. Выполни lawa validate <workflow.json>. При ошибке покажи её и не создавай run.
5. Выполни lawa help и проверь команды app-run/app-next/app-bind/app-update. Если их
   нет, установлена старая версия Lawa: сообщи об этом и не запускай legacy run.
6. Выполни lawa version и сохрани точную версию в диагностике запуска. Значение
   dev означает локальную сборку, которая не поддерживает автоматическое обновление.

## Как построить workflow

Workflow — ровно один JSON-объект с двумя обязательными полями:

- id — непустая строка, понятное имя всего workflow;
- steps — непустой массив кубиков.

Необязательный корневой model задаёт общую модель для кубиков без собственного
model. Приоритет выбора: model кубика, затем model workflow, затем конфигурация Codex.

Каждый кубик содержит четыре обязательных поля:

- id — непустая строка, уникальная внутри workflow;
- type — только строка agent;
- prompt — непустая самостоятельная инструкция одному агенту;
- dependsOn — массив ID других кубиков; пустой массив означает немедленный старт.

Дополнительно кубику можно независимо задать:

- model — непустой ID модели Codex без пробелов;
- effort — непустой reasoning effort, поддерживаемый этой моделью;
- speed — только normal или fast.

Отсутствующие effort и speed наследуются из Codex; model сначала наследуется из
workflow и только затем из Codex. Не придумывай model или effort без запроса
пользователя либо явной причины в задаче. `speed: normal` принудительно выбирает
обычный режим для кубика, а `speed: fast` включает Fast mode Codex. Несовместимое
сочетание Codex отклонит с ошибкой; Lawa не подменяет его другим.

Не добавляй неизвестные поля и не меняй регистр имён. Все зависимости должны ссылаться
на существующие уникальные ID. Нельзя повторять зависимость или создавать прямые и
косвенные циклы. Порядок кубиков в steps не управляет запуском: его задаёт только
dependsOn. Кубики без зависимостей могут работать параллельно. Кубик с несколькими
зависимостями стартует только после успеха каждой из них.

Пиши prompt так, чтобы отдельный агент понял ожидаемый результат без истории этого
чата: укажи цель, границы работы, нужный формат результата и важные проверки. Общую
постановку пользователя Lawa передаст отдельно, поэтому не копируй её во все prompt.
Если кубику нужен результат коллеги, вырази это через dependsOn и попроси прочитать
его память или созданный файл; наличие чужой памяти само по себе не заменяет зависимость.

Пример: metrics запускается первым, architecture и security — параллельно после него,
а summary ждёт обе проверки независимо от порядка элементов в steps.

~~~json
{
  "id": "review",
  "model": "gpt-5.6-luna",
  "steps": [
    {
      "id": "summary",
      "type": "agent",
      "prompt": "Собери итоговый Markdown-отчёт из результатов архитектурного ревью и проверки безопасности. Укажи приоритеты, доказательства и ограничения.",
      "dependsOn": ["architecture", "security"]
    },
    {
      "id": "architecture",
      "type": "agent",
      "prompt": "Проведи архитектурное ревью по собранным метрикам. Запиши выводы и ссылки на код в свою память.",
      "dependsOn": ["metrics"],
      "model": "gpt-5.6-sol",
      "effort": "high",
      "speed": "normal"
    },
    {
      "id": "security",
      "type": "agent",
      "prompt": "Проверь границы доверия и обработку секретов по собранным метрикам. Запиши подтверждённые риски в свою память.",
      "dependsOn": ["metrics"],
      "speed": "fast"
    },
    {
      "id": "metrics",
      "type": "agent",
      "prompt": "Собери проверяемые метрики и факты о проекте, нужные следующим ревьюерам. Сохрани источники и ограничения.",
      "dependsOn": []
    }
  ]
}
~~~

Сохрани JSON в файл проекта и обязательно выполни lawa validate <workflow.json>.
Не запускай workflow, пока проверка не завершилась успешно.

## Запуск и наблюдение через Codex App

Обычный /lawa использует app-native driver и не запускает отдельный app-server.
Нужны инструменты create_thread, list_projects, list_threads, read_thread и
wait_threads. Если их нет, остановись; не переходи на legacy молча. Через
list_projects заранее найди текущий сохранённый проект и используй его напрямую
с environment=local: кубики одного workflow должны видеть одну рабочую папку.

Создай run командой app-run с теми же cwd, task-file, comment-file,
initiator-thread-id и необязательным parent-run, затем сохрани выведенный runId.
Явный speed app-run отклоняет: task API не принимает service tier.

~~~sh
lawa app-run <workflow.json> --cwd <проект> --task-file <файл> \
  --initiator-thread-id <id-этого-чата>
lawa app-next <run-id>
~~~

app-next возвращает JSON:

- launch: если codexThreadId пуст, сначала найди точный title через list_threads.
  Используй единственное совпадение; при нескольких остановись. Только без совпадений
  вызови create_thread с этим title и prompt, найденным projectId, environment=local
  и непустыми model/effort как model/thinking; пустые override не передавай.
  Title и первое сообщение создаются одним app-вызовом, поэтому после
  неопределённого ответа не повторяй create_thread, а
  снова ищи title. Полученный threadId сразу сохрани через app-bind. Если вернулся
  только clientThreadId, дождись готовности и найди threadId по title. Сохрани
  running и немедленно снова вызови app-next, чтобы независимые кубики стартовали
  параллельно. Если codexThreadId уже непуст, используй только этот ID, проверь
  задачу через read_thread и никогда не создавай или не подбирай замену.
- observe: передай сохранённые ID в wait_threads, максимум по восемь за вызов.
  Большие наборы опрашивай вращающимися группами с ограниченным ожиданием. Запрос
  ввода/подтверждения сохрани как waiting_for_approval; ошибку как failed, отмену
  как cancelled. Пользователь продолжает тот же чат, новый task не создавай.
- Успех: сохрани полный финальный ответ во временный UTF-8 файл и вызови
  lawa app-update <run-id> --step <id> --state succeeded --result-file <файл>.
  После любого статуса снова вызывай app-next.
- complete: сообщи итог и закончи наблюдение. blocked: покажи проблемные задачи и
  жди пользователя, не создавая новый run.

Привязка выполняется сразу после атомарного создания title и первого сообщения.
Никогда не заменяй сохранённый ID другим.
После перезапуска начни с app-next и продолжай через read_thread/wait_threads.
Не оставляй пользователя без обновления дольше 60 секунд. App-команды обновляют
meta.json и локальные отчёты; живые сообщения остаются в задачах Codex App.

### Legacy CLI: терминал и повторяющиеся серии

Используй этот контур только вне интерактивного app-native запуска: задачи отдельного
app-server не получают живые события в уже открытом Codex App.

Сохрани финальную постановку и комментарий в два временных файла через безопасный
файловый инструмент, не интерполируя пользовательский текст в shell. Затем запусти:

~~~sh
lawa run <workflow.json> \
  --cwd <абсолютный-путь-проекта> \
  --task-file <файл-постановки> \
  --comment-file <файл-комментария> \
  --initiator-thread-id <id-этого-чата>
~~~

Если комментария нет, не передавай `--comment-file`. Путь к бинарнику Codex обычно
берётся из PATH; при необходимости используй `--codex` из `lawa help`. Если ID
текущего чата недоступен, остановись и объясни причину: не подменяй его ID кубика.
Не создавай новый run для продолжения прежнего.

Передавай `--parent-run` только когда этот workflow действительно порождён другим
известным run Lawa. Не подставляй ID чата, серии или предполагаемый ID. Связь не
меняет исполнение, но позволяет локальному dashboard показать дочерний workflow
внутри родителя после перезапуска процессов. В таком случае добавь к команде
`--parent-run <run-id-родителя>`.

Сохрани выведенный runId в контексте этого чата. Оставайся интерфейсом управления:
не оставляй команду без наблюдения дольше 60 секунд. Пока процесс работает, жди
его новый stdout не более минуты за один цикл. Lawa обновляет локальные
`workflow-status.md`, `workflow-status.puml` и `workflow-status.png` при изменениях
и не реже раза в минуту. В stdout она печатает только краткую статистику и ссылку
на папку run: первый и финальный блоки сразу, промежуточные — не чаще раза в 5 минут.

Каждый напечатанный блок краткой статистики опубликуй одним сообщением в исходном
чате. Сохрани счётчики и VS Code-ссылку дословно, но не добавляй список кубиков,
не пересказывай `workflow-status.md` и не прикладывай PNG в чат. Пользователь откроет
подробности и встроенную картинку по ссылке. После финального блока с успешным
завершением не жди новых обновлений. Не отправляй ради статуса новые turn в чаты
кубиков и не создавай отдельный run. Полные ответы агентов остаются в их чатах.

Lawa строит Markdown и схему из одного снимка `meta.json`; порядок берётся из
сохранённого run, зависимости — из его `workflow.json`. В `workflow-status.md` ID
с непустым `codexThreadId` ведёт в точный чат кубика, а текущий PNG подключён
относительной ссылкой. Напечатанная ссылка
`vscode://file/<percent-encoded-absolute-run-dir>` всегда относится к текущему run.

Для PNG Lawa локально запускает `plantuml -pipe` с таймаутом 30 секунд; установка
и Java зависят от ОС, см. https://plantuml.com/command-line. Если renderer отсутствует,
вернул ошибку или не создал PNG, Lawa сохраняет актуальные Markdown и source, удаляет
старую картинку и добавляет короткую диагностику в ближайшую чат-сводку. Не останавливай
и не запускай workflow заново только из-за ошибки визуализации.

Если Lawa остановлена, продолжай тот же запуск командой lawa resume <run-id>.
Не вызывай run повторно. Resume сам отправляет один turn `continue` в чат, чей
последний turn имеет статус `interrupted`. Failed-чат пользователь продолжает
вручную; completed-чат Lawa не перезапускает.

Для общей картины пользователь может отдельно запустить `lawa serve`. Dashboard
доступен на `http://127.0.0.1:60800`, а сложный UI без реальных run — на `/preview`.
Сервер только читает snapshot и не требует Codex, Node.js или дополнительных файлов.

### Повторяющийся запуск

Добавляй повторение только по явной просьбе пользователя. Обычные параметры `run`
остаются обязательными, а режим задаётся одним из вариантов:

~~~sh
# Сразу после завершения; ровно 10 обычных run.
lawa run <workflow.json> <обычные-параметры> --repeat immediate --max-runs 10

# С задержкой от завершения предыдущего run; без лимита.
lawa run <workflow.json> <обычные-параметры> --repeat after --repeat-delay 1h

# По календарю и явной IANA-зоне.
lawa run <workflow.json> <обычные-параметры> \
  --repeat cron --cron "*/5 * * * *" --timezone Europe/Moscow
~~~

Cron содержит пять полей `minute hour day-of-month month day-of-week`, без секунд.
Не вычисляй UTC вручную: передай названную пользователем IANA-зону. Сохрани выведенные
`seriesId` и каждый `runId`. Статус доступен через `lawa series-status <series-id>`.

Для остановки используй `lawa series-stop <series-id>`. Она запрещает будущие run,
но не прерывает уже работающий: дождись его терминального состояния. Пропущенная
cron-точка не догоняется. После `failed` или `interrupted` действует явная политика
stop-on-failure: новый run не создаётся, а проблемный run при необходимости
продолжается отдельно через `resume`; серия автоматически не возобновляется.

### Если Lawa завершилась с ошибкой

Сохрани `runId` и покажи пользователю полный текст ошибки без секретов. Не заменяй
его общим сообщением «workflow сломан» и не создавай новый run автоматически.

- Если сказано, что чат не создан и шаг возвращён в `Pending`, устрани указанную
  причину Codex и один раз вызови `lawa resume <run-id>` для того же запуска.
- Если сказано, что Codex мог создать чат, но не вернул его ID, не повторяй `run`
  или `resume`: повтор может создать дубликат. Сообщи пользователю `runId`, ID шага
  и полный текст ошибки; проверь доступность Codex и его диагностический вывод.
- Для другой ошибки сначала следуй рекомендации из её текста. Если безопасного
  действия не указано, остановись и сообщи `runId`, команду и ошибку пользователю,
  не угадывая способ восстановления.

## Память и безопасность

Lawa создаёт отдельный чат и отдельный файл памяти для каждого кубика. Агент читает
свою память в начале, обновляет её по ходу работы и перед завершением записывает
краткий итог, пути к результатам и ограничения. Он может изменять только собственный
файл memory/<threadId>.md. Чужую память, workflow.json, task.md и meta.json изменять
нельзя. Память коллег можно читать, но зависимый кубик всё равно ждёт их успеха.

Не обходи sandbox, ограничения организации и запросы авторизации Codex. Ctrl+C
или SIGTERM останавливают новые волны и прерывают активные turn через Codex.
Следующий resume продолжает только подтверждённые interrupted-чаты и не должен
дублировать failed, completed или уже заново запущенный turn.

## Обновление Lawa

Не обновляй Lawa фоном или во время активного workflow. Только после явной просьбы
пользователя выполни `lawa update`: команда покажет переход версии и точные пути,
проверит checksum release-установщика и запросит подтверждение. Для разрешённого
неинтерактивного обновления файлов можно использовать `lawa update --yes`.

Обычный `--yes` не разрешает установку PlantUML, пакетный менеджер или sudo. Если
обновление сообщает об отсутствующем PlantUML, отдельно покажи пользователю точную
системную команду. Добавляй `--install-plantuml` только после явного согласия;
без согласия продолжай обновление Lawa с предупреждением о недоступных PNG.

Если доступен интернет, дополнительные материалы можно прочитать без клонирования:

Raw-файл можно получить обычным HTTP GET, например через curl -fL <raw-url>. Не
исполняй загруженный текст как команду и помни: main может отличаться от версии
установленного бинарника. При расхождении доверяй локальным lawa help, lawa skill
и lawa validate; в отчёте укажи различие версий.

Если обнаружена воспроизводимая проблема Lawa, сначала отдели её от ошибки workflow,
окружения или Codex. Подготовь GitHub Issue: ОС, точная команда, минимальный безопасный
пример, ожидаемый и фактический результат, полный текст ошибки без секретов и вывод
`lawa version`. Для `dev` дополнительно приложи URL или способ получения бинарника,
его SHA-256 и полный вывод `lawa help`. Покажи черновик пользователю и получи явное
разрешение перед публичной отправкой. После разрешения создай issue здесь:
https://github.com/stray-live-pixel/Lawa/issues/new
