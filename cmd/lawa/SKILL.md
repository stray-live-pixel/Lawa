# Lawa

Используй этот скилл для проектирования, запуска, наблюдения и продолжения workflow или команды
личностей Lawa. Lawa предоставляет единый CLI и сама скрывает процессы App Server, thread,
turn, параллельные волны и восстановление состояния.

## Понятность задачи и ожидания

Перед проектированием workflow или запуском команды, workflow либо заказа Боссу
быстро оцени по запросу и доступному контексту: понятны ли результат, существенные
ограничения и признаки качества. Не проводи отдельный аудит и не требуй подробного
ТЗ, если задача уже достаточно ясна. При продолжении оцени только новые существенные
пробелы; прежнее согласование той же неопределённости сохраняется.

- При небольших пробелах выбери логичные обратимые допущения, кратко обозначь их
  и доведи работу до законченного рабочего результата без лишних вопросов.
- Если разные разумные трактовки существенно меняют результат или качество нельзя
  оценить, до зависимого запуска назови конкретную неопределённость этой задачи.
  Объясни, что результат и качество непредсказуемы: работа может оказаться напрасной
  тратой времени, денег, токенов и лимитов и потребовать нескольких итераций ручного
  доведения. Предложи короткое уточнение или ограниченную пробу и получи явное ОК
  пользователя на выбранный вариант. Сам запрос «запусти» до предупреждения не
  означает принятия этого риска; молчание тоже не является согласием.

При проектировании кратко объясни применительно к задаче: агенты — мощный инструмент,
они могут предложить концепцию, но не знают невысказанного образа финального результата
и не гарантируют попадания в ожидания. Не повторяй предупреждение без новых оснований.
Разрешение самостоятельно выбрать концепцию учитывай как часть согласованных границ.
Пока ждёшь ОК, можно подготовить конкретный план или черновик workflow для просмотра,
но не запускать зависимые модельные работы. Независимую разрешённую работу продолжай.

Передай исполнителям исходную цель без пересказа, существенные допущения, ограничения
и полученное ОК отдельным контекстом, не выдавая свои выводы за слова пользователя.
В инструкциях workflow закрепи тот же подход: при существенной неопределённости
сначала небольшой законченный пример, заранее выбранные проверяющий и признаки успеха,
затем решение с основаниями в памяти или общем чате. Технические тесты не доказывают
субъективное качество. Если ответа человека в текущем workflow получить нельзя,
верни оператору конкретный вопрос и завершись без запуска зависимой работы.
Не создавай ради этого новую FSM, обязательную глобальную паузу или согласование
каждой операции. Экономь ресурсы: не тиражируй непроверенный подход и не повторяй
попытки без нового основания; после подтверждения направления доведи работу до конца.

Пример: для «сделай удобный отчёт» без аудитории и сценария объясни, что удобство пока
нечем оценить; предложи уточнить сценарий либо одобрить пробу на одном разделе.
После ОК проверь, помогает ли раздел решать согласованную задачу, зафиксируй решение
и только затем распространяй подход. Если неизвестно лишь имя выходного файла,
выбери его сам: это не причина останавливать работу.

## Команда офиса: запуск и настройки через CLI

Для команды личностей используй `serve`; для фиксированного графа — `run`,
для отдельного диалога с Боссом через CLI — `order/reply`.
Состав команды, личности и внешность задаются при создании заказа:

```sh
lawa serve --team-config /absolute/team.json --cwd /absolute/project \
  --task-file /absolute/goal.md
```

Передай исходную цель без пересказа. Нужны `--cwd` и ровно один из `--task-file`
или `--task`. Сохрани напечатанные runId и URL `/office?run=...`. Команда запускает
Босса автоматически и обслуживает агентов, пока работает процесс; оставляй её
в foreground либо под управлением durable supervisor.

Конфиг содержит только `characters`; ключ — ID личности и её `@тег`:

```json
{
  "characters": {
    "designer": {
      "name": "Дизайнер",
      "history": "Продуктовый дизайнер с опытом сложных интерфейсов.",
      "instructions": "Исследуй сценарий и предложи интерфейс на компонентах проекта. Результат и вопросы передай Боссу.",
      "avatar": "pixel-designer"
    }
  }
}
```

`name`, `history`, `instructions` обязательны; `avatar` — необязательный ID
из галереи персонажей. ID личности соответствует `^[a-z][a-z0-9_-]{0,63}$`;
`human` и `system` зарезервированы. Лимит — 20 личностей вместе с Боссом.
Если `boss` отсутствует, добавляется стандартный Босс. Без `--team-config`
доступны Босс и Разработчик; явный `{"characters":{}}` оставляет только Босса.
Пиши личности кратко: опыт, цель, границы и свобода выбора способа работы.
Конфиг команды проверяет `serve`, а не `lawa validate`: это не граф workflow.

Снимок настроек сохраняется в заказе. Изменение файла не меняет существующую
команду. Повторный запуск с целью создаёт новый заказ. Для продолжения запусти
`lawa serve --root <прежний-root>` без цели и конфига; `resume/reply` для
командных заказов не используются. `serve` может запускать модели существующих
команд, поэтому не считай его только средством просмотра.

UI показывает состояние, историю, чат и справочную галерею ID. Создания заказов,
импорта конфига и редактирования личностей в UI нет; новые сообщения существующей
команде отправляются через чат. Обычные workflow также запускаются через CLI.

## Заказ Боссу из интерактивного чата

Если пользователь просит передать цель Боссу, используй `lawa order`,
а для фиксированного исполнения графа — прежний `lawa run`.
Передай дословный заказ через `--task-file` и рабочую папку через `--cwd`.
Workflow необязателен: `lawa order [workflow.json] --cwd ... --task-file ...`.
В нём могут быть `characters` и ссылки `step.character`; для одного Босса
допустим профиль только с `id` и `characters.boss`, без `steps`.
Такой профиль не проверяется командой `validate`: его проверяет `order`.

Сохрани возвращённый runId в контексте разговора. Передай человеку ответ и
вопросы Босса, не отвечай за человека. Новую реплику по тому же заказу отправляй
через `lawa reply <run-id> --task-file ...`, сохраняя `--root`, если он задан.
Не создавай нового Босса для каждого ответа. Новый заказ — новый `order`.
Один ответ может исследовать вопрос, выполнить работу или запросить сведения:
статус `succeeded` не доказывает достижение всей цели.

`order/reply` используют тот же App Server и авторизацию, что `run`.
`resume` нужен для прерванной работы, а не для новой реплики. Не повторяй
неоднозначно доставленное сообщение: сначала проверь `status/logs` и историю
Codex. После завершения дочернего workflow передай результат тому же Боссу
через `reply`, если требуется его следующее решение. В CLI-режиме самостоятельного фонового
цикла руководителя нет; адресный runtime офиса описан ниже.

## Общая база команды

В кубиках доступны `team_read {}` и `team_post {"text":"Краткий важный факт"}`.
`team_read {}` возвращает ограниченный снимок: цель, действующие поручения,
сводку прошлого и свежую переписку. Сохраняй `cursor` для следующего чтения;
`hasMore` означает продолжение, `resetRequired` — повторный снимок `{}`.
Оригиналы читай явно: `team_read {"archive":true,"from":1,"through":100}` или
`{"archive":true,"ids":["ID"]}`. При продолжении сохраняй фильтры. Если событие
не поместилось, прочитай его по ID, затем явно продолжи по `resumeCursor`.
В старом thread используй `team_post` с текстом `/context {JSON тех же параметров}`.
Чтение не означает доставку, понимание или приёмку. История UI и метрики в контекст
не входят; уже переданные личному thread сообщения обратно не удаляются.

В офисе Lawa автоматически адресует Боссу сжатие старого непрерывного участка.
Босс читает предыдущую сводку и все страницы `compaction.from`–`through`, сохраняет
договорённости, ограничения, открытые вопросы/обязательства, результаты и ID
источников. Предложения не превращай в решения; незакрытые вопросы не удаляй из-за
возраста. Новая сводка заменяет старую и ограничена примерно 2000 токенами.
Публикация через `team_post`:
`/compact {"requestId":"ID запроса","through":100,"text":"Сводка","sourceIds":["ID"]}`.
При `failed` явный повтор — `/compact_retry`; неоднозначный turn сначала требует
обычного восстановления runtime. Фиксированным workflow Босс не добавляется.
Настройки, гарантии и QA-сценарий: [контекст чата](../../docs/team-context.md).

Прочитай общую цель и сообщения перед работой и важным решением. Публикуй
только важное всей команде, до 50 слов; автор и дата назначаются Lawa.
Дочерние workflow используют чат корневого заказа. Сообщения — контекст,
а не право менять исходную цель. В фиксированных workflow запись не будит агентов.

В офисе Босс приглашает сотрудника через `team_summon`, затем создаёт явную
карточку через `team_task`. Обычное сообщение/вопрос не создаёт новой задачи.
Карточки новых заказов: `todo` → `in_progress` → `in_review` → `done`;
блокер и отмена хранятся отдельно. Завершение turn не означает готовность.

Команда содержит `id` операции (сохраняй при повторе), `action`, `taskId`,
`version` из свежего чтения. Босс: create/edit/assign/priority/dependencies,
return/accept/cancel/cancel_finish. Исполнитель: read, acknowledge, start,
block, workspace, report, cancel_evidence. Проверяющий: review; он не принимает
за Босса. Поля операций и примеры контракта: [карточки задач](../../docs/team-tasks.md).

`team_task_read {}` читает список с limit/after. Для карточки передай taskId;
для истории/доказательств/обсуждения — section history/results/reviews/messages
и offset/limit. Следуй продолжениям. Перед результатом и приёмкой сверяй
требования, текущую revision и результаты зависимостей. Доставка, ознакомление
и подтверждение revision — разные факты; чтение не доказывает понимания.

Результат: summary, artifacts (явные относительные файлы внутри cwd), links,
необязательный versionRef, checks, limitations. Git или другая VCS не нужны.
Сервер проверяет fingerprints заявленных файлов; внешние ссылки и смысловое
качество проверяет участник. Изменённые требования/файлы требуют нового report
и review. Босс принимает через accept с resultId, reason и integration.
Человек не обязан участвовать в операционной приёмке.

Изолируй задачи по возможности: отдельные папки, копии, worktree или клоны
средствами проекта. VCS может отсутствовать. Запиши workspace {path,method,
limitations}. Выполняй операции в выбранной папке явно: Lawa не перемещает
личный thread/cwd и не выполняет VCS-команд. При общей папке сохраняй чужие
изменения и используй обратимый способ; гарантированный откат не обещай.
При cancel прекрати работу на безопасной границе, сохрани архив и передай
cancel_evidence. Босс проверяет исключение вклада, включая уже включённый
результат, перепланирует зависимости и завершает отмену через cancel_finish.

`team_post` принимает text и необязательные taskId/replyTo/revision. Адрес @id
нужен для пробуждения; общий пост без адресата допустим. Ответ коллеге связывай
с его сообщением. Вопросы не расширяют полномочия. Перед отчётом перечитай чат.
Старые thread: `/task <JSON>`, `/task_read <JSON>`, `/message <JSON>` через
team_post. Старые поручения остаются доступными через legacy team_accept;
он не принимает новые карточки. Первая явная операция карточки переводит старую
комнату на новый учёт, не перемещая активные thread.

Босс обновляет pin через team_set_goal только по новой цели Чела. Сбой или
ход без отчёта требует проверки; team_retry допустим лишь при доказанном
отсутствии отправки. Неоднозначную доставку не повторяй. После проверки всей
цели и актуальной приёмки задач вызови team_complete с итогом @human до 50 слов,
затем заверши ход. Вопрос человека сотруднику сам по себе не является задачей.

## Единственный runtime

Lawa работает только через `codex app-server --stdio`. Не создавай задачи Codex
Desktop через другого агента и не ищи скрытый app-native режим: его нет.

Причина зафиксирована сознательно. У Codex Desktop нет публичного программного API,
через который внешний Go-процесс мог бы создавать, продолжать и наблюдать нативные
задачи. Агент-посредник добавлял бы отдельные модельные запросы, задержку, стоимость
и узкое место при параллельном запуске многих workflow. Поэтому наблюдаемость
принадлежит Lawa (`status`, `logs`, `serve`), а появление задач в Desktop не
гарантируется. Пересматривать решение можно только после появления публичного API
Desktop для управления задачами.

На личном macOS/Linux и на Linux-сервере используется один контракт. Установленный
Codex Desktop не меняет runtime; нужен доступный и авторизованный Codex CLI.

## Проверка окружения

Перед первым запуском в текущем окружении:

1. Убедись, что ОС — macOS или Linux.
2. Найди `lawa` и `codex` через `command -v`; не угадывай абсолютные пути.
3. Выполни `lawa version`, `lawa help` и `codex --version`.
4. Выполни `codex login status`. Если активной авторизации нет, не запускай Lawa,
   пока пользователь не выберет и не завершит подходящий способ входа.
5. Фиксированный workflow проверь через `lawa validate <workflow.json>`;
   конфиги команды и профили Босса проверяются соответствующей командой запуска.

## Авторизация Codex CLI

Авторизация относится к системному пользователю и окружению, где работает Lawa.
Не считай вход в Codex Desktop достаточной проверкой и не переноси workflow в
задачи Desktop. После любого способа входа снова выполни `codex login status` от
того же пользователя; запускай агентов через `run`, `resume`, `order/reply`
или `serve` только после успешной проверки.

На компьютере с браузером предложи обычный интерактивный вход:

```sh
codex login
```

На удалённом или headless-сервере предпочитай device code, потому что обычный
localhost callback браузера там может быть недоступен:

```sh
codex login --device-auth
```

Device code должен быть разрешён в настройках личного аккаунта или workspace.
Для доверенной неинтерактивной автоматизации можно предложить API key, если
пользователь осознанно выбрал тарификацию OpenAI Platform и уже безопасно задал
переменную окружения:

```sh
printenv OPENAI_API_KEY | codex login --with-api-key
```

Не проси присылать API key, access token или `~/.codex/auth.json` в чат, task,
comment, workflow либо журнал. Не печатай их для диагностики. `auth.json` содержит
токены и должен обрабатываться как пароль. Если вход не проходит, покажи только
безопасный вывод `codex login status` и предложи свериться с официальной
[документацией авторизации Codex](https://learn.chatgpt.com/docs/auth).

В контейнере или по SSH проверь, что `cwd`, файл workflow и root доступны именно
тому пользователю, от которого запускается Lawa. Dashboard по умолчанию слушает
только `127.0.0.1`; для удалённого сервера предложи SSH port forwarding, а не
публикацию хранилища в интернет.

## Запуск

Многострочную постановку и комментарий передавай файлами, чтобы shell не
интерпретировал кавычки, `$()` и переносы:

```sh
lawa run workflow.json --cwd /absolute/project \
  --task-file /absolute/task.md \
  --comment-file /absolute/comment.md
```

Не добавляй `--mode`: runtime один. Сохрани напечатанные `runId` и URL интерфейса.
По умолчанию команда находит уже работающий совместимый UI того же `--root`
(включая локальный `lawa serve`) и открывает `/graph/<runId>` в браузере. Если UI
нет, создаёт сервер на свободном loopback-порту. Процесс-владелец после завершения
workflow или серии сохраняет UI до Ctrl+C; это режим просмотра, а не продолжающаяся
работа агентов. Остальные команды завершаются после выполнения и чужой UI не закрывают.
Не останавливай владельца, пока пользователь смотрит результаты: Ctrl+C закроет
общий сервер для всех вкладок, хотя другие процессы workflow продолжат работу.

Если пользователь явно просит запуск без UI, добавь `--no-ui`: сервер и браузер
не запускаются, существующий UI не останавливается. Этот режим подходит для
автоматизации, ожидающей завершения команды. Ошибка открытия браузера не прерывает
workflow; URL можно открыть вручную. В серии один сервер обслуживает все run,
каждый открывается при создании. После остановки UI результат можно посмотреть
через `lawa serve` с тем же `--root`. Не отправляй команду в фон, если жизненный
цикл shell не контролируется durable supervisor.

## Общий лимит параллельности

Перед запуском широкого графа или нескольких workflow согласуй суммарное число
одновременно работающих turn. Если пользователь не знает подходящего значения,
предложи начать с `4`, а затем изменить его по фактическим лимитам Codex и
ресурсам машины:

```sh
lawa run workflow.json <параметры> --max-parallel 4
```

Флаг относится ко всему `--root`, сохраняется и действует для отдельных процессов
`run` и `resume`. Следующие команды с тем же root могут не повторять флаг; явное
новое значение меняет общий лимит. Для разных независимых лимитов используй разные
root только по просьбе пользователя — вместе с root разделятся observability и
история запусков. Без однажды сохранённого значения Lawa оставляет параллелизм без
собственного ограничения ради совместимости.

Если все слоты заняты, новый кубик остаётся Pending: это штатное ожидание, а не
ошибка и не повод создавать новый run. Уменьшение лимита не прерывает уже активные
turn. Завершение или crash процесса освобождает его слоты автоматически. Изменить
настройку при продолжении можно той же универсальной формой:

```sh
lawa resume <run-id> --max-parallel 2
```

Для ручного запуска связанного дочернего workflow передай `--parent-run <run-id>`.
Внутри кубика не вызывай `lawa run` через shell: используй доступные ему
структурированные `run_child` или `run_children`. Передай путь workflow, текущий
runId как parentRun, нужный существующий абсолютный cwd и ровно одно из
task/taskFile. Дети одной пачки могут работать в разных разрешённых каталогах.
Workflow и taskFile всё равно должны находиться в workspace родителя или read-only
папке его run. Lawa проверит доступ до регистрации, вернёт runId после надёжной
публикации, применит общий max-parallel и дождётся потомков.
Повтор того же tool call не создаёт дубль; новый запрос после завершения запускает
тот же вход заново.

Для повторений используй только встроенные параметры:

```sh
lawa run workflow.json <параметры> --repeat immediate --max-runs 10
lawa run workflow.json <параметры> --repeat after --repeat-delay 1h
lawa run workflow.json <параметры> --repeat cron \
  --cron "0 9 * * 1-5" --timezone Europe/Moscow
```

## Наблюдаемость

Покажи состояние без запуска модели:

```sh
lawa status <run-id>
lawa logs <run-id>
lawa logs <run-id> <step-id> --follow
lawa logs <run-id> --visit <visit-id> --follow
```

`status` показывает состояния, thread/turn, PID и последнюю активность. Для
workflow v2 он также показывает visit/iteration, решение, переход, skipped-ключи
и отдельные visits со статусом `skipped`, лимит и причину остановки. Позиционный
step-id у `logs` выбирает все посещения
кубика, а `--visit` — одно точное посещение; не сочетай эти формы. `logs` читает
краткое, безопасное для терминала представление журнала Lawa. Raw
reasoning, аргументы и
результаты MCP/tool, diff, неизвестные payload и сырые rollout Codex не
сохраняются.

`lawa serve` запускает dashboard, общий чат на `/office` и runtime существующих
команд. Сам просмотр не создаёт новых заказов. Пилюля в header показывает workflow и
время до ближайшего запуска; клик открывает боковой список всех активных серий.
Новые workflow и исполнения находятся сверху; workflow v2 показывает каждое
посещение как отдельный `step #visit`, не склеивая итерации. В деталях видны
trigger, iteration, attempt, решение и объяснение, переход, skipped-ключи,
terminal skipped-ветки и точные ссылки на память и журнал. Клик по исполнению открывает live-панель с сообщениями
агента, reasoning summary, планом, командами и их потоковым выводом. Панель читает
журнал и не запускает дополнительную модель или агента-посредника.

Команда, её вывод и ответ агента могут содержать секреты. Считай `events.jsonl`
и dashboard приватными, оставляй `serve` на loopback и для сервера предлагай SSH
port forwarding. Не обещай raw reasoning: Lawa его намеренно не сохраняет.
Для наблюдения в реальном времени используй `--follow`: он читает только новые
события и завершается после финальных записей действительно запущенных turn.
Для `skipped`-visit события исполнителя нет, потому что Codex не запускался.
Управляющие символы в диагностике CLI показывает как видимый текст и не исполняет
как команды терминала.

Не обещай пользователю, что App Server thread будет виден как нативная задача
Codex Desktop. Источники истины для оператора — run Lawa, его журнал и dashboard.

## Продолжение и ошибки

Для существующего run всегда используй его ID:

```sh
lawa resume <run-id>
```

`resume` сверяет сохранённые thread и автоматически продолжает только явно
interrupted-кубики; в workflow v2 это `cancelled` visit в том же чате. Успешный
или технически `failed` visit не перезапускается: последний может активировать
кубик восстановления через `after`. Не создавай новый run после неоднозначной
ошибки `thread/start`: первоначальный thread мог быть создан, а повтор дал бы дубль.

Исторические app-native run и серии доступны только через read-only status и
dashboard. Не пытайся автоматически переносить их на App Server: Lawa не может
достоверно проверить уже созданные Desktop-задачи.

При `waiting_for_approval` объясни пользователю, какой шаг ждёт решения. Lawa не
одобряет запросы прав молча и не обходит managed restrictions. При `failed`
покажи `lawa logs <run-id> <step-id>` и исходную ошибку; не подменяй её новым run.

## Workflow

При создании workflow предпочитай Markdown-инструкции. Для нескольких кубиков
создай рядом с JSON папку `prompts/` с отдельным `<step-id>.md` для каждого кубика.
В JSON используй `"prompt": {"file": "prompts/check.md"}`; внутри Markdown разделяй
цель, действия и ожидаемый результат заголовками и списками.
Обычный `"prompt": "Текст инструкции"` остаётся допустимым для коротких инструкций
и совместимости. Строка с именем `.md` сама по себе ссылкой не является.

Путь `file` считается от каталога исходного JSON, а не `--cwd`; абсолютный путь
тоже допустим. Нужен доступный обычный `.md` с непустым UTF-8. Не добавляй рядом
с `file` альтернативный текст: объект принимает только это поле. Markdown
сохраняет разметку; раскрываются подстановки `{{...}}`, но не Markdown-ссылки.
Перед запуском выполни
`lawa validate <workflow.json>`: команда проверяет и файлы инструкций.
В дочерних workflow Markdown должен оставаться в workspace родителя или папке
его run, как и JSON. Снимок запуска/серии хранит уже прочитанный текст: `resume`
и повторы не перечитывают исходные `.md`; для новых инструкций нужен новый запуск.

### Шаблоны prompt

В корневом `templates` зарегистрируй имя и текст либо объект с единственным
полем `file`. Файловый шаблон хранится под `templates/` рядом с JSON workflow;
путь задаётся от папки JSON, включая `templates/`. Абсолютные пути и выход из
этой папки через `..` запрещены. Допустимы вложенные папки и расширение `.md`.
Чтение симлинков подчиняется тем же правам, что `prompt.file`.

```json
{
  "id": "report-flow",
  "templates": {
    "post_comment": "После завершения работы напиши отчёт в Tracker.",
    "context": {"file": "templates/context.md"}
  },
  "steps": [
    {"id": "implement", "type": "agent", "dependsOn": [],
     "prompt": "Реализуй задачу. {{post_comment}} {{context}}"},
    {"id": "review", "type": "agent", "dependsOn": ["implement"],
     "prompt": {"file": "review.md"}}
  ]
}
```

`review.md`:

```markdown
Проверь задачу. {{post_comment}} {{context}}
```

`templates/context.md`:

```markdown
Укажи workflow {{lawa.workflow.id}} и кубик {{lawa.step.id}}.
```

Одинаковый текст в JSON и Markdown раскрывается одинаково, включая пробелы и
переносы строк. Например, `{{context}}` получает `implement` в первом кубике и
`review` во втором. Строка `"templates/context.md"` сама по себе остаётся текстом.

| Параметр | Значение |
|---|---|
| `lawa.workflow.id` | `id` из JSON, не ID отдельного запуска |
| `lawa.workflow.version` | `1` или `2`; без `version` — `1` |
| `lawa.workflow.model` | Модель, явно заданная в workflow |
| `lawa.step.id` | ID текущего кубика |
| `lawa.step.type` | Тип кубика (`agent`) |
| `lawa.step.model` | Модель кубика с наследованием из workflow |
| `lawa.step.effort` | Явно заданный effort кубика |
| `lawa.step.speed` | Явно заданная скорость кубика (`normal`/`fast`) |

Отсутствующая настройка превращается в пустую строку: значения конфигурации
Codex ещё неизвестны. ID запуска, номер визита, результаты других кубиков и
переменные окружения не поддерживаются. Подстановка действует только в prompt
и шаблонах, а значения контекста повторно не интерпретируются.

Имена шаблонов состоят из букв (включая русские), цифр, `_` и `-`.
Пространство `lawa.*` зарезервировано. Вокруг имени внутри `{{ ... }}` допустимы
пробелы. Шаблоны могут вставлять другие шаблоны. Цикл, неизвестное имя/параметр,
незакрытая подстановка, пустой шаблон или недоступный/невалидный UTF-8 файл —
ошибка `validate` и `run`, даже для неиспользуемого шаблона. Пустой итоговый
prompt тоже отклоняется. Глубина раскрытия ограничена 64 уровнями, текст с
подстановками — 1 МиБ; обычные prompt без подстановок сохраняют прежнее поведение.

Для буквального `{{...}}` добавь один обратный слеш: в Markdown
`\{{post_comment}}`, в JSON `"\\{{post_comment}}"`. В результате останется
`{{post_comment}}` без слеша и подстановки. Это действует и внутри шаблона.

`validate` и новый `run` перечитывают файлы и раскрывают шаблоны до запуска
Codex. Снимок содержит готовые prompt без реестра `templates`: `resume` и
повторы существующей серии используют прежний текст, даже если файлы изменены
или удалены. Для применения правок запусти workflow/серию заново.

Сначала определи нужный контракт и не смешивай их:

- отсутствие `version` или `version: 1` — строгий DAG. Каждый шаг содержит
  `type: "agent"`, непустой `prompt` и явный массив `dependsOn`; зависимости
  открываются только после технического успеха, циклы запрещены;
- `version: 2` — agent-граф с непустым `start` и явным `after` у каждого шага.
  `after` ждёт любой терминальный технический исход, включая `failed` и `skipped`,
  но не вычисляет бизнес-условие. Все skipped-источники распространяют `skipped`;
  смешанный join запускается после выполненных и пропущенных источников.

В version 2 каждое смысловое ветвление выделяй в отдельный агентный кубик с
`decisions`. Его prompt должен объяснять, как по памяти и диагностике выбрать один
из разрешённых ключей. Перед успешным завершением агент обязан ровно один раз
вызвать встроенный `choose_decision`; текстовый ответ сам по себе маршрут не
выбирает. Маршрут содержит ровно один из `to` с одним или несколькими кубиками
либо `finish: "succeeded"|"failed"`. Неизвестный, отсутствующий, повторный или
конфликтующий выбор является ошибкой; не угадывай default и не проси Lawa
оценивать `when`, `successWhen`, `failureWhen`, `eval` или shell-выражение.
Невыбранные достижимые ветки получают terminal `skipped`: Codex для них не
запускается и `maxVisits` не расходуется. Если target доступен также по выбранному
пути, он выполняется; список невыбранных ключей остаётся аудитом решения.
Если пропущенный кубик сам содержит `decisions`, не выбирай за него ключ: Lawa
технически распространяет одну causal wave на объединение всех его `to` и через
полностью пропущенные `after`. Повтор decision-target в той же волне
схлопывается, поэтому такой цикл конечен. Отдельный `after` может сохранить ещё
одну FIFO-квитанцию `skipped` того же step, но не запускает и не разворачивает
его повторно; замыкание сохраняется атомарно даже вместе с `finish`.
Технически `failed` кубик решения не применяет выбранный маршрут. Обычному
рабочему кубику `choose_decision` и произвольный типизированный JSON не нужны:
следующий агент решения читает его память и технический статус.

Цикл замыкай только через `to` кубика решения. Для каждого кубика решения внутри
цикла задай положительный `maxVisits`; `onLimit` может явно выбрать terminal и по
умолчанию означает `failed`. Каждый повтор является отдельным visit с собственной
памятью и чатом. Для цикла проверки используй топологию `start: test`,
`checker.after: [test]`, `repeat → fix`, `test.after: [fix]` и terminal-решения
`done`/`fail`; лимит ставь на checker. Для ветвления риска используй checker с
terminal `safe`/`cannot_assess`, fan-out `risk → [security-audit, impact-audit]` и
итоговый кубик с `after` от обеих проверок. Полные примеры хранятся в репозитории:
[fix-until-green.json](https://github.com/stray-live-pixel/Lawa/blob/main/examples/fix-until-green.json)
и [risk-routing.json](https://github.com/stray-live-pixel/Lawa/blob/main/examples/risk-routing.json).
Статические рёбра `after` обязаны оставаться DAG; каждый кубик должен быть достижим
из `start` и иметь путь к естественному листу, `finish` либо явному `onLimit`.
Старые snapshots только читай: не переписывай сохранённый `pending` в вычисленный
задним числом `skipped`.

Не записывай секреты в prompt, task или comment. Кубик читает общий снимок run и
доступную память других исполнений, но пишет только собственный файл памяти.
Общие выводы и ограничения агент обязан сохранить туда перед завершением.

После создания или изменения workflow всегда запускай `lawa validate`. Если нужен
только заранее известный ациклический порядок после успеха, используй простой v1
DAG. Если маршрут зависит от смысла результата, используй решение v2. Если состав
самих дочерних workflow определяется только во время работы, используй run_child
или run_children, а не ручные задачи Desktop и не фоновый shell.

## Картинка графа

`lawa graph <run-id> [--theme dark|light] [--output <файл.png>] [--root <путь>]`
создаёт PNG через локальный PlantUML без запуска агентов. По умолчанию тема тёмная;
существующий файл не перезаписывается. В dashboard также есть показ и скачивание PNG.

## Метрики команды: чтение без запуска агентов

`lawa metrics <run-id> [--root <путь>] [--at <RFC3339>]` печатает JSON из
`team.json` командного заказа офиса. Не запускает Codex и ничего не записывает.
Без `--at` срез заканчивается последним сохранённым событием, поэтому одинаковый
файл даёт одинаковый отчёт. Для ожиданий на текущий момент передай явную дату.

- `calendarSeconds` — время заказа; `knownActiveAgentSeconds` — сумма измеренных
  интервалов сотрудников, `knownActiveCalendarSeconds` — их объединение без
  удвоения параллельной работы. `activeAgentSeconds: null` означает неполное покрытие.
- `waits` сохраняет тип и источник ожидания. Зависимость и отсутствие новых сообщений
  не оцениваются как потери; граница достоверной истории — `waitRecordedFrom`.
- `tasks` для legacy-поручений показывает время до заявленного проверяемого результата, отдельной
  приёмки и число явных возвратов. Сотрудник пишет через `team_post`
  `/result @boss <что готово и где проверить>` для полученных открытых поручений.
  Босс возвращает `/rework <ID результата> @сотрудник <что исправить>`.
  Возврат продолжает прежние поручения. Приёмка остаётся через `team_accept`;
  обычные уточнения не считаются доработками. Старые сообщения продолжают работать.
- `executions` связывает доставку, turn и доступные счётчики. `usage.threadTotal`
  накоплен по чату, `usage.lastRequest` — последний запрос модели, а не весь turn.
  `observedTurnTokens` — разность при известной базе; эти данные могут быть неполными.
  Отсутствующие usage/границы/цена — `null`, не ноль. После рестарта без сохранённого
  окончания `observedFinishedAt` не подменяет время окончания работы.

Метрики и история исключены из `team_read`; рабочие поручения, сообщения и текущие
причины ожидания сохранены. Подробные определения и ограничения: `docs/team-metrics.md`.
