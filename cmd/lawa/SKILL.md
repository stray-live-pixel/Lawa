# Lawa

Используй этот скилл, когда пользователь просит запустить или продолжить workflow
Lawa. Lawa предоставляет единый CLI и сама скрывает процессы App Server, thread,
turn, параллельные волны и восстановление состояния.

## Единственный runtime

Lawa работает только через `codex app-server --stdio`. Не создавай задачи Codex
Desktop через другого агента и не ищи скрытый app-native режим: его нет.

Причина зафиксирована сознательно. У Codex Desktop нет публичного программного API,
через который внешний Go-процесс мог бы создавать, продолжать и наблюдать нативные
задачи. Агент-посредник добавлял бы отдельные модельные запросы, задержку, стоимость
и узкое место при параллельном запуске многих workflow. Поэтому наблюдаемость
принадлежит Lawa (`status`, `logs`, `serve`), а появление задач в Desktop не
гарантируется. Пересматривать решение можно только после появления публичного API
Desktop для управления задачами.

На личном macOS/Linux и на Linux-сервере используется один контракт. Установленный
Codex Desktop не меняет runtime; нужен доступный и авторизованный Codex CLI.

## Проверка окружения

Перед первым запуском в текущем окружении:

1. Убедись, что ОС — macOS или Linux.
2. Найди `lawa` и `codex` через `command -v`; не угадывай абсолютные пути.
3. Выполни `lawa version`, `lawa help` и `codex --version`.
4. Проверь workflow через `lawa validate <workflow.json>`.
5. Если Lawa сообщает об ошибке авторизации App Server, попроси пользователя
   авторизовать Codex CLI и повтори тот же run. Не заменяй его задачами Desktop.

В контейнере или по SSH проверь, что `cwd`, файл workflow и root доступны именно
тому пользователю, от которого запускается Lawa. Dashboard по умолчанию слушает
только `127.0.0.1`; для удалённого сервера предложи SSH port forwarding, а не
публикацию хранилища в интернет.

## Запуск

Многострочную постановку и комментарий передавай файлами, чтобы shell не
интерпретировал кавычки, `$()` и переносы:

```sh
lawa run workflow.json --cwd /absolute/project \
  --task-file /absolute/task.md \
  --comment-file /absolute/comment.md
```

Не добавляй `--mode`: runtime один. Сохрани напечатанный `runId`. Команда остаётся
в foreground и наблюдает workflow до результата; не отправляй её в фон, если
жизненный цикл shell не контролируется durable supervisor.

Для связанного дочернего workflow передай `--parent-run <run-id>`. Для повторений
используй только встроенные параметры:

```sh
lawa run workflow.json <параметры> --repeat immediate --max-runs 10
lawa run workflow.json <параметры> --repeat after --repeat-delay 1h
lawa run workflow.json <параметры> --repeat cron \
  --cron "0 9 * * 1-5" --timezone Europe/Moscow
```

## Наблюдаемость

Покажи состояние без запуска модели:

```sh
lawa status <run-id>
lawa logs <run-id>
lawa logs <run-id> <step-id> --follow
lawa serve
```

`status` показывает состояния, thread/turn, PID и последнюю активность. `logs`
читает нормализованный журнал Lawa: reasoning, аргументы команд и инструментов,
diff и сырые rollout Codex туда не копируются. `serve` запускает read-only
dashboard с теми же безопасными событиями.

Не обещай пользователю, что App Server thread будет виден как нативная задача
Codex Desktop. Источники истины для оператора — run Lawa, его журнал и dashboard.

## Продолжение и ошибки

Для существующего run всегда используй его ID:

```sh
lawa resume <run-id>
```

`resume` сверяет сохранённые thread и автоматически продолжает только явно
interrupted-кубики. Не создавай новый run после неоднозначной ошибки
`thread/start`: первоначальный thread мог быть создан, а повтор дал бы дубль.

Исторические app-native run и серии доступны только через read-only status и
dashboard. Не пытайся автоматически переносить их на App Server: Lawa не может
достоверно проверить уже созданные Desktop-задачи.

При `waiting_for_approval` объясни пользователю, какой шаг ждёт решения. Lawa не
одобряет запросы прав молча и не обходит managed restrictions. При `failed`
покажи `lawa logs <run-id> <step-id>` и исходную ошибку; не подменяй её новым run.

## Workflow

Workflow — JSON с `id` и непустым `steps`. Каждый шаг содержит уникальный `id`,
`type`, непустой `prompt` и необязательный `depends_on`. Ссылки должны вести на
существующие шаги, граф обязан быть ацикличным. Независимые готовые шаги Lawa
сама запускает параллельно.

Не записывай секреты в prompt, task или comment. Кубик читает общий снимок run и
память зависимостей, но пишет только собственный файл памяти. Общие выводы и
ограничения агент обязан сохранить туда перед завершением.

После создания или изменения workflow всегда запускай `lawa validate`. Если
нужные ветвления нельзя выразить статическим DAG, сначала объясни ограничение и
согласуй отдельные workflow, а не имитируй планирование ручными задачами Desktop.
