## Публикация изображений через gh

Владелец явно разрешил обоим QA публиковать изображения проверяемого продукта
и их оригиналы **только в GitHub**, в репозитории задачи, и вставлять их в отчёт
issue. Дополнительное согласование этой публикации не требуется. Catbox и другие
сторонние хостинги не разрешены. Не публикуй секреты и персональные данные
тестового окружения; используй безопасные тестовые данные.

Используй авторизацию `gh`, браузерная сессия GitHub не нужна. Основной способ —
Git Data API через `gh api`: изображения хранятся в отдельной ветке материалов,
а комментарий содержит Markdown со ссылками на них. Это не вложения, загруженные
через форму сайта. Отсутствие браузерной авторизации или API таких вложений
само по себе не является причиной `blocked`.

1. Возьми `OWNER/REPO` из URL issue; проверь `gh auth status` и доступ к репозиторию.
   Подготовь оригиналы и копии с разметкой во временной папке. Создай список файлов,
   состояний и кейсов; включай только материалы текущей проверки.
2. Выбери уникальную ветку `qa-artifacts/issue-<номер>-<runId>-<stepId>-<visitId>`.
   Сначала проверь, не опубликована ли она уже этим посещением. Не обновляй
   существующую ветку вслепую: сравни файлы и используй подтверждённый результат.
3. Для каждого PNG подготовь JSON-файл с полями `encoding: "base64"` и `content`
   (байты изображения в Base64, без переносов). Отправь
   `gh api --method POST repos/OWNER/REPO/git/blobs --input blob.json`.
   Сохрани возвращённый `sha` и путь `originals/01.png` либо `annotated/01.png`.
4. Собери `tree.json` с массивом `tree`: для каждого файла объект с `path`,
   `mode: "100644"`, `type: "blob"`, `sha`. Отправь
   `gh api --method POST repos/OWNER/REPO/git/trees --input tree.json`.
   Поле `base_tree` не задавай: ветка содержит только материалы QA.
5. Подготовь `commit.json`: `message` с номером issue и runId/visitId,
   `tree` из ответа и `parents: []`. Создай один коммит на весь набор:
   `gh api --method POST repos/OWNER/REPO/git/commits --input commit.json`.
   Создай `ref.json` с `ref: "refs/heads/qa-artifacts/issue-<номер>-<runId>-<stepId>-<visitId>"`
   и `sha` коммита; отправь
   `gh api --method POST repos/OWNER/REPO/git/refs --input ref.json`.
   Не меняй main, ветку PR и историю других посещений; не создавай PR для картинок.
6. В отчёт вставь `![Состояние и кейс](https://raw.githubusercontent.com/OWNER/REPO/COMMIT_SHA/annotated/01.png)`
   и ссылку на оригинал с тем же `COMMIT_SHA`. Используй SHA коммита материалов,
   а проверенный SHA кода укажи отдельно. Для большого набора допустимы блоки
   `<details>` с изображением и пояснением каждого состояния.
7. Опубликуй через `gh issue comment <номер> --repo OWNER/REPO --body-file report.md`.
   Перечитай комментарий через `gh api`, проверь наличие всех изображений,
   соответствие загруженных файлов оригиналам и доступность картинок читателям issue.
   Для приватного репозитория проверь доступ с правами читателя: не делай репозиторий
   публичным ради картинок и не помещай токены авторизации в ссылки.

Все JSON-файлы формируй сериализатором; не вставляй Base64 или многострочный текст
в shell-команду. При неоднозначном ответе API сначала проверь сохранённые SHA,
ветку и комментарий; не создавай дубли. Сохрани эти ссылки и SHA в памяти.
Если `gh` действительно не авторизован, нет права записи или изображения недоступны
читателям, сохрани черновик и точную причину `blocked`. Само разрешение публикации
уже дано; не запрашивай его повторно и не обходи реальные ограничения доступа.

Для публичного репозитория проверь URL изображения без авторизации. Если raw URL
не работает для читателей приватного репозитория, не объявляй публикацию успешной:
сохрани материалы и сообщи конкретное ограничение. Не выдавай ссылку на локальный
файл или JSON-ответ API за встроенный скриншот.
