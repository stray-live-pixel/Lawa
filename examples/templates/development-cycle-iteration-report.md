Для QA frontend без изменений frontend действует ранний пропуск из его prompt:
только запись в памяти и передача финальному QA, без отчёта в issue.

GitHub issue — хронология работы всех участников. Возьми точный URL issue из
постановки; не выбирай тикет наугад. Программист проверяет доступ к нему до правок.
PR возьми из постановки или памяти программиста, создавшего его для этой задачи.

После каждого посещения, включая возвраты и блокировки, оставь отдельный комментарий
в issue. Укажи роль, runId/visitId, ссылку на PR, SHA рассматриваемого коммита,
сделанное, проверки и результат, ограничения и следующий шаг. Программист объясняет,
почему считает итерацию законченной и готовой к ревью; ревьювер — причины своего
вердикта; QA frontend — наблюдаемые помехи интерфейса или основания приёмки;
финальный QA — результат пользовательских кейсов. Частичный результат называй
частичным. Завершение итерации не означает завершения всей задачи.

Перечитай опубликованный комментарий и сохрани его URL вместе с PR и SHA в памяти.
При неоднозначной отправке сначала найди комментарий по runId/visitId и роли;
повторная попытка того же посещения не должна создавать дубль. Новое посещение —
новый отчёт; не перезаписывай историю предыдущих итераций или чужие комментарии.
Публикуй многострочный текст через структурированный API или `--body-file`.

Если issue/PR недоступен или PR ещё не удалось создать, явно зафиксируй блокировку
и отсутствие ссылки, не выдумывай её. Если нельзя опубликовать отчёт, сохрани его
черновик и причину в памяти; не считай передачу завершённой. Ревьювер и оба QA выбирают
`blocked`, программист оставляет явную блокировку для ревьювера. Ошибка GitHub
не должна превращаться в успешную итерацию.

Не публикуй секреты и персональные данные тестового окружения. Эти отчёты —
комментарии в issue, а не в PR; каждый доступный PR обязательно связан ссылкой.
