# Code Review

Code Review — самостоятельный файловый run Lawa: сбор контекста, независимая
проверка и подготовка доказательного результата. MVP использует один агентский
метод с возможностью субагентов. Merilo и сравнение методик в MVP не входят.

## Запуск

```sh
lawa review --cwd /path/to/project --prompt 'Проведи ревью изменений по задаче …'
lawa review --cwd /path/to/project --prompt-file request.md --no-ui
lawa review --prompt-file request.md --config review-config.json
```

Без `--no-ui` команда открывает `/code-review?reviewId=<id>` в общем локальном UI
того же root. Владелец сервера оставляет просмотр доступным до Ctrl+C после
завершения работы. Явный `--no-ui` не запускает HTTP и браузер. Закрытие вкладки
не отменяет ревью; кнопка остановки передаёт устойчивый запрос координатору.
Ревью, созданное через UI, исполняется отдельным worker текущего бинарника Lawa.

Главная страница `/code-review` принимает свободную постановку, рабочую папку и
модели этапов. Минимальная ширина интерфейса — 1280 px, включая мобильные окна:
на них доступна горизонтальная прокрутка, отдельной мобильной компоновки нет.

## Конфигурация и границы этапов

| Этап | Модель по умолчанию | Effort | Результат |
| --- | --- | --- | --- |
| Контекст | `gpt-6-sol` | `high` | Задачи с комментариями, дизайн, diff, снимки файлов и команд |
| Проверка | `gpt-6-astra` | `high` | Замечания и фактические доказательства, без обязательного storytelling |
| Результат | `gpt-6-sol` | `high` | Обзор изменений, экскурсии по замечаниям, Markdown и публикация |

Точные модели должны быть доступны в аккаунте Codex пользователя. Lawa не
подменяет недоступную модель другой молча. Каждый этап запускает отдельный
Codex turn в рабочей папке проекта с его настройками и доступными инструментами.
Проверка автономна: не предусматривает вопросов пользователю. Неудовлетворённые
права или отсутствующие данные отображаются как явное препятствие, а не успех.

Настройки можно переопределить до запуска через UI, `--config <file>` либо
`--config-json <JSON>`. Последние два аргумента взаимоисключающие. JSON использует
те же PascalCase-поля, что и HTTP API. Частичное описание накладывается на defaults:

```json
{
  "Context": {"Model": "gpt-6-sol", "Effort": "high"},
  "Review": {"Model": "gpt-6-astra", "Effort": "high"},
  "Presentation": {"Model": "gpt-6-sol", "Effort": "high"},
  "RublesPerDollar": 100
}
```

Конфигурация сохраняется при создании и не меняется даже при повторной попытке.
Для другой конфигурации создаётся новое review. Отдельной страницы настроек,
наследования конфигураций проекта и выбора альтернативных методик в MVP нет.

## Единый источник результата

Авторитетные структуры находятся в `internal/reviewstore/types.go`. Сохранённый
результат используется UI, Markdown-комментарием и промптом исправления. Агент
не может завершить этап просто фразой «готово»: исполнитель проверяет наличие
структурированных результатов, ссылок на материалы и требуемых доказательств.

Начальный контекст замораживается после сбора. Дополнительные снимки проверки
хранятся как evidence отдельно, не подменяя базу. Требования и дизайн не завязаны
на GitHub: агент использует интеграции проекта и формирует подписи источников.
Первая задача в списке является основной; её ID показывается в истории.

P0/P1 блокируют принятие изменений и дают `request_changes`. P2/P3 — рекомендации:
при успешном выполнении без блокирующих возможен `approve` с ненулевым числом
замечаний. Сбой исполнения не является содержательным вердиктом.

Обзор изменений объясняет смысл и объём работы в смысловом порядке. Экскурсия
замечания доказывает конкретную проблему: причина, сценарий, последствия и
привязки к коду, требованиям или дизайну. Шаг содержит одну короткую мысль, а не
пересказ синтаксиса. Допустимы неизменённые файлы, диапазоны и функции. Если
привязки нет, причина указывается явно. Viewer использует сохранённые снимки,
а не текущие файлы, которые могли измениться после проверки.

Изображения дизайна — реальные экспортированные assets. HTML формы и сгенерированные
картинки не заменяют источник. Тексты скиллов и поручения субагентам показываются
по наблюдённым событиям; доступность скилла не означает его использование.

## Файлы и жизненный цикл

Все материалы одного review находятся в `<root>/<reviewId>/`. По умолчанию root —
`~/.light-ai-workflows`. ID имеет тот же формат, что run Lawa: 128 случайных бит,
32 строчных hex-символа. `meta.json` помечает тип `review`; старый dashboard
workflow пропускает такие каталоги. Основной snapshot — `review.json`.

Снимки обновляются атомарно под блокировкой, координатор удерживает отдельную
межпроцессную блокировку. Конфигурация и уже записанные артефакты неизменяемы;
новая версия имеет новый путь. Попытки, запросы и результаты сохраняются отдельно.
Относительные пути проверяются внутри каталога review; симлинки не дают доступ
за его пределы. Активные HTML/SVG не исполняются браузером через endpoint assets.

История сортируется по `UpdatedAt`. Состояние просмотра хранится отдельно:
прочтение не переставляет запись в истории. Просмотренная версия не должна
сбрасываться устаревшим ответом polling. Повтор после сбоя явный; живой координатор
не объявляется потерянным по одному времени последнего события.

## Метрики и публикация

Input, cached input и output сохраняются отдельно, если источник их сообщает.
Общий input включает кэш; некэшированный input получается вычитанием. Стоимость
считается по тарифу соответствующей модели за миллион токенов до округления.
Тарифы задаются в `Config.Prices` с полями `Input`, `CachedInput`, `Output`,
`Source`, `AsOf`. Неизвестные тарифы или usage отображаются как недоступные:
нулевая цена не подставляется. Это API-эквивалент, не списание подписки Codex.
Курс по умолчанию — 100 рублей за доллар. Время этапа не суммирует параллельные
субагенты; затраты не должны дублировать агрегированные и дочерние usage.

Если передан PR/MR, агент публикует окончательные Markdown-замечания в его
инфраструктуре с корректными привязками к проверенной ревизии. Локальное ревью
ничего внешне не публикует. Публикация фиксирует receipts и внешние ID; повтор
после неопределённого ответа сначала сверяет уже опубликованное, не создаёт
дубликаты. Недоступные локальные ссылки не выдаются за публичные доказательства.
Ревью не исправляет код, не сливает PR и не закрывает чужие замечания.

## Дизайн и проверка

Основные макеты: [ввод](https://www.figma.com/design/Ohltjk2saaQi4jyueGqUzq/Main?node-id=173-13),
[проверка](https://www.figma.com/design/Ohltjk2saaQi4jyueGqUzq/Main?node-id=177-74),
[результат](https://www.figma.com/design/Ohltjk2saaQi4jyueGqUzq/Main?node-id=212-47),
[viewer](https://www.figma.com/design/Ohltjk2saaQi4jyueGqUzq/Main?node-id=236-304).
Полный журнал уточнений сохранён в [требованиях дизайна](code-review-design-requirements.md).
При расхождении приоритет имеют поздние согласованные решения MVP.

Обязательные проверки: файловая безопасность и восстановление, неизменность
конфига, переходы и отмена, контракт трёх агентов, недублирующая публикация,
default UI / no-ui, UI от ввода до результата, Markdown и viewer, обе темы,
ширина 1280 px и больше, сохранение пользовательского выбора при polling.
