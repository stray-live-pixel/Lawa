# Метрики команды

```sh
lawa metrics <run-id> --root /path/to/runs
lawa metrics <run-id> --root /path/to/runs --at 2026-09-21T12:00:00Z
```

Команда печатает JSON командного заказа офиса. Она читает `team.json`, не запускает
Codex, не восстанавливает историю по сети и не меняет файл. Фиксированные workflow
имеют другой жизненный цикл и этим отчётом не измеряются. Без `--at` граница отчёта —
последний сохранённый факт: повторное чтение одного файла даёт одинаковые числа.
Явный `--at` задаёт срез, в том числе конец текущих ожиданий. Длительности — секунды.

## Что измеряется

| Поле | Определение |
| --- | --- |
| `calendarSeconds` | От первого сообщения заказа до `room.achievedAt` либо границы среза. Для вновь открытого заказа без текущего достижения — до среза, включая прежние периоды. |
| `executions[].deliveries[].delaySeconds` | От времени входящего сообщения до подтверждения `turn/start`. Включает очередь и подготовку подключения. |
| `executions[].claimedAt` | Резервирование порции сообщений планировщиком до сети. Это ещё не доставка модели. |
| `executions[].startedAt/finishedAt` | Наблюдаемые границы подтверждённого turn, а не CPU-время и не время отдельного инструмента. |
| `executions[].activeSeconds` | Закрытый интервал turn минус наблюдаемые runtime-паузы разрешения. Другие периоды не вычитаются по предположению. |
| `knownActiveAgentSeconds` | Сумма известных активных интервалов всех сотрудников. Параллельные сотрудники учитываются каждый отдельно. |
| `knownActiveCalendarSeconds` | Объединение тех же интервалов на календарной шкале: пересечение считается один раз. |
| `activeAgentSeconds` | Полный измеренный итог только при покрытии с начала заказа и известных границах всех попыток. Иначе `null`; известная часть остаётся в `known*`. |
| `waits` | Интервалы причин из нативной истории: queue, capacity, permission, error, result, acceptance, no_messages. Указаны сотрудник, тип и источник; свободного текста нет. |
| `tasks[].firstResultSeconds/acceptedSeconds` | От постановки поручения до первого явного результата / отдельной приёмки Боссом. |
| `firstResultSeconds/firstAcceptedSeconds` | От первого сообщения заказа до первого такого результата / приёмки среди поручений. |
| `tasks[].reworks` | Число явных возвратов данного поручения после начала наблюдений. Старое неполное покрытие — `null`. |

Ожидание зависимости, проверки или новых сообщений само по себе не объявляется
потерей времени. `waitRecordedFrom` показывает начало нативной истории ожиданий.
Восстановленные кадры до этой даты не доказывают причины и не учитываются.
Один сотрудник не исполняет два turn одновременно; actor-lock сохраняет этот
инвариант. Сумма времени разных сотрудников может превышать календарную длительность.

## Результат и доработка — явные сообщения

Обычная переписка не позволяет надёжно отличить отчёт, уточнение и возврат.
Сотрудник отправляет через существующий `team_post`:

```text
/result @boss Готово в src/main.go; проверено командой go test ./...
```

Это заявление проверяемости по всем полученным открытым поручениям сотрудника,
а не автоматическая приёмка. Сообщение хранит их `taskIds`. Если готова только часть,
сначала опиши её обычным сообщением; не объявляй весь набор готовым. Босс возвращает
непринятые поручения указанного результата:

```text
/rework <ID сообщения результата> @developer Исправь обработку пустого ответа
```

Возврат адресно будит сотрудника и продолжает прежние обязательства, не создавая
новых копий задач. После возврата старый отчёт нельзя принять: нужен новый результат
после получения доработки. Приёмка остаётся через `team_accept` с ID задач, отчётом и
описанием проверки. Обычные сообщения и прежняя приёмка совместимы: если явного
`/result` нет, принятый отчёт даёт известную точку результата, но более ранние
реплики не интерпретируются. Повтор того же tool call не удваивает события.

## Токены, пропуски и рестарт

`executions[].usage` содержит последний полученный снимок
`thread/tokenUsage/updated` своего thread и turn. Сохраняются только перечисленные
счётчики: total/input/cachedInput/cacheWriteInput/output/reasoningOutputTokens.
Неизвестные поля, содержимое инструментов, ошибки и секреты не копируются.

- `threadTotal` накоплен по чату; `lastRequest` относится к последнему запросу
  модели, а не ко всему turn. Их нельзя складывать между исполнениями.
- `observedTurnTokens` — накопленный расход нового thread либо разность с последним
  снимком непосредственно предыдущего завершённого turn той же личности/thread.
  Без базы, после неизвестного окончания или при убывании счётчика соответствующие
  значения неизвестны. Это наблюдаемые счётчики: пропущенные уведомления не
  восстанавливаются по предположению, полнота биллинга не гарантируется.
- Отсутствующий usage, граница времени или цена сериализуется как `null`.
  Цена всегда неизвестна: тарифы не задавались и денежной оценки нет.
- Исполнение имеет стабильный ключ `actor/attempt`. Повторные callbacks и
  восстановление после рестарта обновляют ту же запись; интервалы не удваиваются.
- Если терминальное событие успело сохраниться, его время не меняется при рестарте.
  Иначе `observedFinishedAt` указывает только момент обнаружения завершения;
  `finishedAt` и активная длительность остаются неизвестными. Простой сервера не
  превращается в якобы активную работу. Открытые/неоднозначные попытки также не
  считаются нулевыми; `unknownExecutions` показывает их количество.

## Хранение и границы контекста

Постановка, результат, возврат и приёмка используют существующие `messages` и
`room.tasks`; ожидания и блокировки — `history.frames`. Только недостающие границы
исполнений и снимки usage добавлены в `metrics`. Всё сохраняется атомарно под
`team.lock` в том же `team.json`; отдельной БД или журнала нет. Старые файлы читаются
без миграции при GET. `recordedFrom` — реальное начало наблюдений, не выдуманная
история старого запуска.

`ReadTeamForAgent` удаляет `history` и `metrics` перед сериализацией во всех
вариантах `team_read`. Prompt runtime строится из рабочих сообщений и настроек,
не из полного `TeamChat`. Рабочие сообщения `/result` и `/rework`, поручения и
актуальные причины ожидания остаются доступны сотрудникам. Это граница формируемого
контекста, а не запрет локального чтения файлов при наличии файловых прав.

Код: `internal/runstore/team_metrics.go`, `internal/teamruntime/metrics.go`,
`internal/teamreport`. Регрессионные тесты покрывают параллельные интервалы,
рестарт с потерянным/сохранённым окончанием, legacy-файлы, токены, отсутствие
телеметрии в ответе агента и полный цикл результат → возврат → приёмка.
