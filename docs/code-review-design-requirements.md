MVP — актуальные границы первой версии

Первая версия: один агентский прогон по собранному контексту. Управляющий агент может привлекать субагентов, но это один процесс и один итоговый результат review.

В MVP входят создание review, сбор и сохранение контекста, файловое хранение и история, автономная агентская проверка, наблюдение за состоянием, статистика времени и токенов с API-эквивалентом, результат в виде доказательных мини-экскурсий по коду, требованиям и дизайну.

Не входят в MVP: Merilo + workflow, выбор методики, параллельное сравнение методов и вкладка «Сравнение». Эти идеи и концептуальный экран сохранены для следующей итерации. Не реализовывать их сейчас.

Главная цель MVP — удобный базовый инструмент, позволяющий человеку изучить и проверить обоснование каждого замечания. Не ограничиваться текстовым списком замечаний. Статистика включает управляющего агента и субагентов без двойного учёта; стоимость — оценка по тарифам API, а не списание с подписки.

Вкладки MVP: «Контекст → Проверка → Результат». Закладывать понятное расширение на будущие методы, но не строить заранее механизм их запуска и сравнения.

Цель

Дать пользователю свободно поставить задачу по ревью кода и запустить процесс одной кнопкой. Дальше показать ход работы, результат и сравнение способов ревью.

Обязательный принцип — любая инфраструктура

□ А. Ориентировать исполнение на Codex, как в остальной Lawa. Не привязывать управление кодом и задачами к GitHub, GitLab, Bitbucket, Git или другому конкретному продукту. Поддерживать сценарий работы через агента с любой настроенной у пользователя системой контроля версий, хостингом кода и трекером задач.

□ Б. Считать, что окружение пользователя уже настроено для работы с кодом, задачами и ревью изменений. Передавать управляющему агенту контекст проекта, его правила, настройки и доступные скиллы. Способ подключения этого контекста определить при реализации интеграции с Codex.

□ В. Поручить агенту определять нужные команды и инструменты: читать задачу, получать изменения и дизайн, работать с PR / MR или аналогом в инфраструктуре пользователя. UI не должен выбирать провайдера по URL, требовать определённые домены или реализовывать отдельную интеграцию с каждым сервисом.

□ Г. Получать необходимые приложению данные от агентов по единому контракту, независимому от инфраструктуры. Контракт опишем позже: в том числе формат текста задачи и правила его дальнейшего использования. Не придумывать схему данных до проработки соответствующих экранов.

□ Д. Во всех последующих макетах и примерах использовать нейтральные сущности и заменяемые значения. Ссылки на конкретные сервисы не считать обязательным форматом входных данных.

01 — Боковая панель

□ 1. Разделить экран на левую боковую панель и основную область. Начальная ширина панели — 280 px. Разрешить менять её перетаскиванием правой границы; основная область занимает оставшееся место. Базовый размер обоих макетов — 1280 × 1024 px. Сейчас поддерживаем desktop от этой ширины; меньшие экраны не проектируем.

□ 2. Для текущего макета использовать границы ширины 240–480 px. На границе показать курсор изменения ширины и обеспечить управление с клавиатуры. Сохранение ширины между открытиями пока не определено.

□ 3. Разместить общий хедер Lawa сверху внутри боковой панели: исходная иконка, название и переключатель темы. Фон хедера прозрачный. Кнопку с часами в разделе ревью не показывать. Переключатель темы прижать к правому краю панели с отступом 12 px; контейнер кнопки должен занимать только её ширину.

□ 4. Разместить «История ревью» на 12 px ниже хедера. Заголовок истории выровнять слева с отступом 12 px. Текст «Вы ещё не запускали ревью» выровнять по центру панели, показать обычным начертанием и цветом secondary из дизайн-системы. Дополнительную подпись под ним не показывать. Наполнение истории проработать отдельно.

02 — Свободно поставить задачу

□ 5. В основной области показать заголовок «Code Review» размером 48 px и выровнять по центру. Верхний отступ блока с заголовком и полем — 60 px от верхнего края приложения. Подзаголовок убрать. Использовать общие шрифты, компоненты и токены Lawa.

□ 6. Под заголовком разместить многострочное поле для произвольной постановки задачи агенту. Центрировать заголовок и поле относительно основной области. Ширина поля — не более 760 px, боковые отступы основной области — минимум 40 px. При расширении окна растут свободные поля; при расширении боковой панели поле ввода сужается вместе с основной областью. Placeholder: «Укажите ссылку на задачу и ссылку на pull request». Поддержать вставку текста, редактирование и переносы строк.

□ 7. Не показывать вкладки источника, отдельное поле PR и дополнительные пояснения. Пользователь может описать ревью PR, локальных изменений или коммита обычным текстом. Placeholder — пример, а не требование обязательно дать две ссылки.

Шаблон — добавление в постановку

□ 7.1. По нажатию «Провести code review pull request» добавить в конец поля следующий текст шаблона:

Проведи code review изменений по требованиям задачи.

Задача: {{ссылка на задачу}}
Изменения (PR / MR или аналог): {{ссылка на изменения}}
Дизайн (для frontend): {{ссылка на дизайн}}

Существующий текст не заменять. Если поле непустое и не заканчивается переносом строки, перед шаблоном добавить перенос строки.

□ 7.2. Значения в {{…}} — обычный редактируемый текст. Пользователь вручную удаляет переменные и вставляет ссылки из своей инфраструктуры. Ссылку на дизайн добавляет для frontend-задачи; ненужную строку может удалить. Не привязывать переменные к доменам, поставщикам или конкретному формату URL.

□ 7.3. После вставки вернуть фокус в поле и поставить курсор в конец текста. Применить общее правило активности кнопки: есть непробельный текст. Шаблон сам не запускает ревью. Повторное нажатие повторно добавляет текст в конец.

03 — Запустить процесс

□ 8. Показать основную кнопку «Запустить ревью» внутри поля справа внизу. Слева в этой строке показать второстепенную кнопку шаблона «Провести code review pull request». Пока поле пустое или содержит только пробелы, кнопка недоступна. После ввода непробельного текста сразу включить кнопку и показать стандартное оформление action. При очистке поля снова выключить. Сам ввод текста не запускает ревью; две ссылки не являются обязательным условием включения кнопки.

□ 9. По нажатию передать полный текст постановки управляющему Codex-агенту и начать процесс ревью. Агент организует проверку в настроенном окружении пользователя, используя его скиллы, настройки и правила проекта. Обработку неполной постановки и незаменённых переменных шаблона проработать отдельно.

□ 10. Перенос строки в поле не должен случайно запускать ревью. Сочетание клавиш запуска, состояние отправки, ошибки и экран после запуска согласовать отдельно.

Дальнейшая логика

□ 11. Проработать процесс, результат и сравнение ревью агентом, с Merilo и через workflow. Состав записи истории и способ хранения определить вместе с этими экранами.

Уточнить до реализации зависимых пунктов

• Точка входа в раздел из остального UI; маршруты /code-review и query reviewId зафиксированы.
• Как агент определяет проект и источник изменений из текста.
• Доступ к репозиториям и задачам; реакция на недоступные ссылки и неполные данные.
• Контракт данных между управляющим Codex-агентом и UI; параметры сравнения, отмена и ошибки.
• Реакция агента на незаменённые переменные и отсутствие нужных данных или доступа.
• Хранение задачи, истории и ширины панели.
• Диапазон панели 240–480 px — предложение макета; проверить обе границы при ширине окна 1280 px и на более широком desktop.

04 — После запуска · предложение для обсуждения

□ 12. После успешного создания запуска открыть его экран и добавить запись в историю. Сохранить полную постановку. Исходную постановку открывать по иконке документа рядом с названием review.

□ 13. Под ссылками показывать компактные этапы-кнопки «Сбор контекста → Проверка → Результат». Полученный контекст показывать в разделах задач, изменений и дизайна; состояния загрузки отличать от уже сохранённых материалов.

□ 14. Обновлять статусы по данным агента или оркестратора; не имитировать прогресс. Контракт данных опишем отдельно. Не дублировать статус этапа длинными пояснениями и списками.

□ 15. Разместить «Остановить» с иконкой Stop справа в полосе этапов. Вопрос агента показывать только когда он действительно возник. Семантику остановки, уточнения, ошибки и восстановление соединения проработать следующими состояниями.

Этот экран — предложение состояния подготовки. Методы сравнения и результаты ещё не определены.

05 — URL и история ревью

□ 16. Главный экран ввода доступен по /code-review. Пустой и заполненный ввод имеют одинаковый URL. После создания review открыть /code-review?reviewId=<идентификатор>. reviewId равен runId корневого review; это не ID тикета и не ID дочернего исполнения агента.

□ 17. При открытии URL с reviewId загрузить соответствующее ревью и выделить его запись в истории рамкой 2 px и мягкой тенью цвета статуса. Обновление страницы и переход по прямой ссылке должны сохранять выбранное ревью. Обработку неизвестного reviewId проработать отдельно.

□ 18. Запись истории — одна кнопка перехода к ревью. Внутри показать короткий заголовок. Под ним в одной строке разместить лейбл идентификатора тикета слева и дату последнего обновления у правого внутреннего края карточки. Выровнять их по вертикальному центру. Все записи имеют видимую рамку по периметру. Невыбранные — 1 px; выбранная — 2 px и мягкое свечение цвета статуса, без жёлтого выделения и заливки. Выбор не меняет порядок: сохранять хронологическую позицию по дате последнего обновления. Примеры прошлых ревью в макете — демонстрационные данные, не добавлять их в пустую историю пользователя. Нажатие на любой участок, включая лейбл, выбирает ревью; у лейбла нет отдельного действия и внешнего перехода.

□ 19. Получать заголовок ревью и идентификатор тикета от агента по будущему контракту, без разбора URL под конкретного провайдера. До получения заголовка показывать «Ревью изменений». Если тикет не определён, не показывать выдуманный идентификатор. TASK-42 в макете — нейтральный пример.

□ 20. Показывать дату последнего обновления в формате ДД.ММ.ГГГГ ЧЧ:ММ, с ведущими нулями и 24-часовым временем, например 07.09.2026 18:30. Дату показывать обычным начертанием, время ЧЧ:ММ — жирным. Конкретный часовой пояс отображения согласовать отдельно.

□ 21. Подписывать URL над каждым новым экраном CGM. Изменения состояния одного ревью не меняют его reviewId.

06 — Статусы ревью и замечания

□ 22. В работе: синий цвет info и аккуратный круг 8 px. Во время выполнения круг плавно пульсирует. При reduced motion показывать статичный индикатор. В статическом макете показана одна фаза пульсации.

□ 23. Успешно: зелёный цвет positive только когда весь процесс завершился успешно и ревьюер выдал approve — обязательных исправлений перед принятием изменений нет. Необязательные рекомендации допускаются.

□ 24. Красный цвет danger: техническая ошибка выполнения либо замечания, обязательные к исправлению перед принятием изменений. Различать причины текстом: «Ошибка выполнения» или «Исправить». Наличие любых замечаний само по себе не означает красный статус.

□ 25. Для завершённых ревью показывать количество найденных замечаний раздельно: блокирующие и неблокирующие. Approve с 2 рекомендациями остаётся зелёным. Если замечаний нет, показывать 0. При техническом сбое показывать известное количество; если результат ещё не получен — «замечания: нет данных», а не 0.

□ 26. Получать итог процесса, вердикт и замечания отдельно по контракту агента. Не определять approve по одному лишь успешному завершению flow. Техническая ошибка имеет красный статус даже при полученном ранее approve.

□ 27. Цвет статуса использовать для рамки и индикатора в заголовке. Открытое ревью выделять толщиной рамки и мягкой тенью того же цвета. Сортировать историю по последнему обновлению: новые сверху; сам выбор карточки порядок не меняет. На макете: выбранное в работе, невыбранное с обязательными исправлениями и невыбранное approve с рекомендациями.

□ 28. Делать карточку компактной: в первой строке разместить индикатор статуса, заголовок и круглые счётчики замечаний; во второй — нейтральный лейбл тикета и дату. Заголовок занимает не более двух строк, затем обрезается троеточием на второй строке. Полное название доступно при наведении.

□ 29. Блокирующие замечания показывать числом в красном круглом лейбле, неблокирующие — в приглушённом сером. У завершённых показывать оба счётчика, включая 0; у незавершённого без полученных результатов счётчики не показывать. Подсказки раскрывают смысл каждого счётчика и статус процесса. Отдельную третью строку статуса убрать.

□ 30. Тень выбранного ревью применять только к периметру карточки, не к её содержимому. Лейбл тикета во всех состояниях остаётся нейтральным, без свечения.

□ 31. Счётчики замечаний: круг 18 × 18 px, интервал 3 px, без обрезания границ. Значения 0–9 показывать целиком, от 10 — «9+». Плюс уменьшить относительно цифры, всю пару центрировать в круге. Точное количество и критичность доступны в подсказке.

□ 32. Дата карточки — updatedAt: время последнего содержательного изменения ревью, а не создания или запуска. Обновлять автоматически при любом сохранённом изменении содержимого review или его материалов; heartbeat, чтение и служебное состояние просмотра дату не меняют. Сортировать по updatedAt убывающе.

□ 33. Для непросмотренных изменений показывать третий круг 18 × 18 px после счётчиков: иконка Bell из @gravity-ui/icons размером 12 px, жёлтый фон warning-light и жёлтая иконка warning. Интервал между всеми тремя кругами — 3 px. Текст «Новое» в карточке не показывать; подсказка колокольчика — «Есть непросмотренные изменения». Колокольчик информационный, без отдельного действия. Индикатор независим от статуса и счётчиков. Показывать при наличии изменений, которые пользователь ещё не видел.

□ 34. Хранить последнюю просмотренную версию отдельно от версии обновления. Убирать колокольчик после отображения актуальных изменений в открытом ревью при активном окне; фоновую загрузку не считать просмотром. Не менять updatedAt при отметке прочитанным. Границу содержательных событий и хранение состояния просмотра уточнить в контракте.

□ 35. Верхний внутренний отступ всех карточек истории — 10 px. Боковые и нижний отступы сохранить. Колокольчик не связан с наличием замечаний: при отсутствии непросмотренных изменений его не показывать.

07 — Review как файловый run

□ 36. Review — корневая сущность выполнения, объединяющая управляющего агента и все проверки. Генерировать один устойчивый ID: reviewId = runId корневого review. Использовать существующий формат runstore: 128 случайных бит, 32 строчных hex-символа. Не создавать отдельный несвязанный ID ревью. Дочерние исполнения имеют свои ID и принадлежат этому review.

□ 37. Хранить всё ревью в одном каталоге <root>/<reviewId>/, без базы данных. Использовать настроенный root Lawa; по умолчанию ~/.light-ai-workflows. Просмотр, продолжение и перезапуск приложения не создают новый reviewId.

Предлагаемая структура для реализации:
<root>/<reviewId>/
  meta.json — метаданные, состояние, вердикт
  task.md — исходная постановка пользователя
  events.jsonl — общий журнал событий review
  coordinator.lock — единственный координатор
  context/ — полученные задачи, дизайн, контекст
  memory/ — память управляющего агента
  handoff/ — журнал решений и передачи работы
  artifacts/ — замечания, отчёты, сравнения
  executions/<executionId>/ — материалы исполнений
  view-state.json — просмотренная версия

□ 38. В meta.json предусмотреть версию схемы, ID, тип review, заголовок, createdAt, updatedAt, рабочий проект, состояние процесса, итоговый вердикт, версии изменений и ссылки на материалы. Хранить время с часовым поясом; формат ДД.ММ.ГГГГ ЧЧ:ММ относится к отображению. Точный контракт полей уточнить при реализации.

□ 39. Ссылки на задачи хранить упорядоченным массивом tasks: URL, идентификатор, заголовок при наличии. Первая задача — основная и наиболее приоритетная; её ID показывать в истории. Если задач несколько, агент определяет порядок по постановке и содержанию: например, родительская или наиболее важная первой. Не сортировать по URL и не терять остальные задачи. Если задача не указана или ещё не определена, не выдумывать ссылку.

□ 40. Отдельно хранить ссылки на изменения (PR / MR или аналог), дизайн и дополнительные источники. URL и идентификаторы не зависят от провайдера. Сохранять полученный агентом текст задач и прочие материалы в context/, чтобы последующие агенты могли прочитать их без восстановления истории чата.

□ 41. В executions/<executionId>/ сохранять метаданные исполнения, поручение, локальные события и логи, память, результаты и передачу следующему агенту. При использовании workflow переиспользовать его обычные workflow.json, meta.json, task.md, events.jsonl и memory/. Повторные попытки сохранять отдельно, не перезаписывая предшествующие. Все исполнения физически находятся под каталогом review.

□ 42. Записывать связи между review, исполнениями и Codex thread/turn. Логи и нужные для анализа материалы должны быть доступны внутри review, а не только по ссылке на внешний чат Codex. Не обещать сохранение скрытых внутренних рассуждений: хранить доступные события, сообщения, команды, результаты и явную память.

□ 43. Для навигации по материалам использовать относительные пути от каталога review. В журнале передачи фиксировать выполненную работу, решения, оставшиеся вопросы и ссылки на результаты. Не дублировать большие журналы: общий events.jsonl отражает события review и ссылки на исполнения, локальные — подробности агента.

□ 44. Переиспользовать гарантии runstore: резервирование ID без перезаписи, атомарная публикация метаданных, синхронизация JSONL-журнала и блокировка единственного координатора. Агенты не должны параллельно перезаписывать общую meta.json: её обновляет координатор через проверенный контракт. После сбоя сохранять ранее записанные данные для продолжения и анализа.

□ 45. Адаптировать существующий runstore к типу review и вложенным исполнениям. Сейчас загрузка run ожидает workflow.json; не подставлять фиктивный workflow. Сохранить совместимость обычных workflow-run и корректную работу их поиска, блокировок и восстановления. Конкретное расширение формата и API решить при реализации.

□ 46. Историю строить по meta.json, не читая все логи. updatedAt меняется от содержательных событий, состояние просмотра хранится отдельно и не переставляет карточку. База данных не требуется.

Основание в текущем коде: README.md → «Хранилище и восстановление»; internal/runstore/store.go (Create, loadSnapshot, newID); locked.go (атомарная запись и блокировки); events.go (events.jsonl); internal/coordinator/agent_prepare.go (память и контекст исполнений). Существующий run хранит workflow.json, task.md, meta.json, events.jsonl и memory/<execution-id>.md.

08 — Сохранённый контекст и шапка review

□ 47. Вместо общего Code Review показывать title конкретного review, одинаковый с историей. Перед названием — кнопка с иконкой FileText из Gravity UI с подсказкой «Исходная постановка»; по нажатию открыть сохранённый task.md. Постоянную строку «Ваша задача» убрать.

□ 48. Под названием показать createdAt и updatedAt с явными подписями «Создано» и «Обновлено», в формате ДД.ММ.ГГГГ ЧЧ:ММ. В истории остаётся только updatedAt.

□ 49. В шапке показывать кликабельные ссылки-лейблы: все задачи в порядке приоритета, ссылки на проверяемый код при наличии, все источники дизайна. Для локальных изменений без внешнего URL ссылку на код не создавать. Лейблы шапки открывают исходный источник; лейбл тикета в истории отдельного перехода не имеет.

□ 50. После запуска управляющий агент собирает контекст и формирует title, ссылки, подписи и содержимое сущности review. UI отображает полученный контракт, не разбирает ссылки под конкретные сервисы. Не показывать предполагаемые материалы как уже полученные.

□ 51. Для каждой задачи сохранять снимок описания и всех доступных комментариев, их порядок, авторов и время при наличии, URL источника и время получения. Показывать описание и комментарии внутри review. Неполную выгрузку или недоступность явно отмечать.

□ 52. Для каждого источника дизайна сохранять доступные изображения, экспортированные экраны и необходимые материалы внутри review, с названием, ссылкой на источник и временем получения. Предоставить галерею и просмотр изображения для сравнения с UI; одной внешней ссылки недостаточно.

□ 53. Сохранять фактически проверяемые изменения отдельным diff-файлом: пути, добавленные и удалённые строки, контекст. Поддержать просмотр файлов и diff внутри review. Агент получает изменения средствами пользовательской инфраструктуры; UI не зависит от Git. Зафиксировать базовую и проверяемую ревизии или идентификатор локального снимка, если доступны. Бинарные изменения отмечать отдельно, не имитировать текстовый diff.

□ 54. Сохранять дополнительные материалы, необходимые для анализа и передачи работы другим агентам, внутри того же review. Повторное получение контекста не должно незаметно менять снимок, по которому уже проводилась проверка; связывать результаты с версией контекста.

Актуализация структуры данных:
meta.json: title, createdAt, updatedAt; tasks[] по приоритету; changeSources[]; designs[]; contextVersion; ссылки на локальные материалы и состояния их получения.
tasks[]: id?, title?, url, descriptionPath, commentsPath, fetchedAt, fetchState.
changeSources[]: label, url? (нет для локального кода), kind, baseRef?, headRef?, snapshotId?, diffPath, filesPath, fetchedAt, fetchState.
designs[]: label, url?, manifestPath, fetchedAt, fetchState.
context/tasks/<id>/description.md + comments.json
context/changes/<snapshotId>/changes.diff + files.json
context/designs/<id>/manifest.json + images/
context/attachments/ — прочие материалы.
Все пути относительные от review; ID каталогов внутренние безопасные, не произвольные URL. Манифест дизайна содержит файлы, названия экранов и источники. Точный формат экспортов и контракта уточнить при реализации.

□ 55. Организовать основной экран вокруг контекста: разделы «Задачи», «Изменения», «Дизайн» с числом материалов; выбранный раздел показывает сохранённое содержимое. Под ссылками показывать цепочку компактных этапов-кнопок со стрелками, без широких табов. Детальные состояния загрузки, комментариев, diff и галереи прорабатываем поэтапно.

09 — Получение контекста и автоматическое обновление

□ 56. Шаг 03 — сразу после запуска: название skeleton, createdAt уже известно, updatedAt первоначально равно createdAt. Нет выдуманных задач, ссылок, файлов или счётчиков. В истории временно «Новое ревью», без тикета. Шаг 04 — контекст получен. Оба состояния имеют один reviewId и URL.

□ 57. Показывать загрузку контекста и добавлять реальные материалы постепенно по данным агента. Различать «ещё получаем», «получено», «отсутствует» и «ошибка», не заменять отсутствие данных нулевым счётчиком. Вкладки в порядке: задачи → дизайн → изменения → контекст проекта.

□ 58. Задачи — исходные требования с комментариями. Дизайн — собранные изображения и материалы из ссылок и вложений, если есть. Изменения — diff и список изменённых файлов. Дополнительные файлы, фрагменты и команды начального сбора показывать отдельно во вкладке «Контекст проекта».

□ 59. Для изменений показывать два отдельных лейбла с иконками Gravity UI: Code — добавленные и удалённые строки, File — добавленные и удалённые файлы. Модифицированные, переименованные и дополнительные контекстные файлы учитывать отдельно; не путать количество файлов с числом добавленных и удалённых строк. Плюс зелёный, минус красный. Нулевые показатели скрывать; если все показатели лейбла нулевые — скрывать лейбл. Во время загрузки отсутствие данных не считать нулём.

□ 60. Автоматически обновлять updatedAt при любом сохранённом изменении содержимого сущности review: текстов, ссылок, состояния, замечаний, метаданных контекста или его файлов. Не полагаться на ручное выставление даты агентом. Приложение должно наблюдать изменения файлов review, включая запись агентом, и обновлять версию сущности и историю. Повторное чтение, heartbeat, файлы блокировок и запись служебного updatedAt/view-state не считаются изменением содержимого и не должны вызывать цикл обновлений.

□ 61. Модель: contextItems[] — реестр всех собранных материалов с id, kind, title, relativePath, source?, fetchState, fetchedAt, version и связями с задачей/изменениями. files.json содержит статус каждого изменённого файла; дополнительные файлы помечаются как контекст, а не как изменения. Счётчики выводятся из реестра файлов. Снимки контекста и результаты связаны версиями.

□ 62. При реализации наблюдения учесть атомарную замену файлов, пачки записей и восстановление после перезапуска. Изменение сущности должно приводить к обновлению UI и признака непросмотренного; способ watcher/reconcile выбрать при реализации.

□ 63. Этапы под ссылками: «Сбор контекста», «Проверка», «Результат», разделённые стрелками ArrowRight. Компактные кнопки: синий — в работе, зелёный — успешно завершён, красный — ошибка, нейтральный — ещё не начат. Экран загрузки показывает сбор синим; полученный контекст — сбор зелёным, проверка автоматически запускается и отображается синим. Переходы и действие нажатия на этапы проработать отдельно.

□ 64. Убрать нижние подписи «Материалы появятся…» и «Контекст сохранён…». Статус сообщается цепочкой этапов.

□ 65. Модель статистики изменений: linesAdded, linesDeleted, filesAdded, filesDeleted; отдельно filesModified и filesRenamed. Вычислять из сохранённого снимка изменений, исключая дополнительные контекстные файлы. Каждый лейбл имеет подсказку, различающую строки и файлы.

□ 66. Модель этапов: collection, review, result с собственным status (pending/running/succeeded/failed), временем и ошибкой при наличии. Не смешивать технический статус этапа с вердиктом approve / обязательными исправлениями.

□ 75. После успешного завершения сбора контекста автоматически запускать проверку, без дополнительного нажатия пользователя. В шаге 04 collection.status = succeeded, review.status = running, result.status = pending. Кнопка «Остановить» управляет текущей проверкой. Переход фиксируется в журнале и обновляет updatedAt.

10 — Компактная шапка, задачи и повторные попытки

□ 67. Уплотнить шапку: порядок createdAt → updatedAt, жирные только подписи «Создано:» и «Обновлено:», дата и время обычные, компактный разделитель-точка. В ссылках использовать выровненную SVG-иконку ArrowUpRight Gravity UI, не текстовый символ. Исходная постановка — явная кнопка с рамкой и FileText.

□ 68. Выделить цепочку этапов контрастной фоновой полосой без внешней рамки под ссылками (рамки самих вкладок сохранить): она отделяет метаданные от контента. Статистику строк и файлов визуально объединить со вкладкой «Изменения», сохранив отдельные лейблы.

□ 69. Вкладка «Дизайн 6» означает шесть сохранённых изображений, а не экранов или источников. Вкладка задач показывает число задач. Счётчики вычисляются из данных, в макете — 3 задачи и 6 изображений.

□ 70. Карточка задачи: ID отдельным нейтральным лейблом, название заголовком, краткое Markdown-превью. Поддержать заголовки, списки, выделения, ссылки, код и цитаты. Длинное описание ограничивать по высоте; «Полный текст» раскрывает описание, «Комментарии · N» открывает комментарии. Убрать неоднозначную кнопку «Показать».

□ 71. При ошибке сбора контекста или проверки показывать явную кнопку «Повторить» для неудавшегося этапа. Новая попытка сохраняется отдельно в том же review; предыдущие логи и результаты не теряются. Во время попытки исключить дублирующий запуск. Детальный экран ошибки проработать отдельно.

□ 72. Данные: исходный Markdown описания и comments[] сохраняются; превью — представление, не обрезанная версия источника. Число дизайнов вычисляется по манифестам изображений. Для retry хранить stageId, attemptId, status, startedAt, finishedAt, error и ссылки на материалы попытки.

□ 73. Между заголовком review и строкой дат — 8 px. Кнопка исходного промпта стоит перед названием. «Остановить» с иконкой Stop Gravity UI размещается справа в полосе управления этапами.

□ 74. Агент формирует конкретный label для каждой внешней ссылки: «Pull request», «Merge request» или понятное название сущности в пользовательской инфраструктуре; для дизайна, например, «Figma · форма входа». Не использовать неоднозначное «Изменения» для внешней ссылки. Не зашивать поставщика в UI: label, kind, url и название источника поступают от агента и сохраняются в метаданных. Локальным изменениям без URL внешнюю ссылку не создавать.

11 — Начальный контекст проекта

□ 76. Под полосой этапов добавить вкладку «Контекст проекта» после задач, дизайна и изменений. В ней показывать только базовый контекст, собранный агентом на этапе collection для начала ревью: дополнительные файлы, прочитанные фрагменты, другие материалы проекта, команды и скрипты с результатами. Это отдельный раздел, не часть diff и не счётчик изменённых файлов.

□ 77. На этапе сбора сохранять всё фактически прочитанное агентом и использованное для формирования начального контекста. Для файла — путь в проекте, сохранённый снимок содержимого, время чтения и ревизию/хеш при наличии. Для фрагмента — точные диапазоны строк и прочитанный текст; явно показывать, что сохранён фрагмент, а не весь файл. Не заменять снимок ссылкой на текущий файл, который может позднее измениться.

□ 78. Для каждой команды сохранять точную команду или текст bash-скрипта, рабочую директорию, время запуска и завершения, код выхода, stdout и stderr. Если агент прочитал только часть вывода, фиксировать доступный ему фрагмент и факт усечения. Логировать не только имя скрипта, но и использованную версию его текста. Не сохранять секреты окружения; сокрытие чувствительных данных явно отмечать.

□ 79. В UI контекста проекта предусмотреть список файлов и фрагментов с просмотром сохранённого содержимого, а также список команд/скриптов с просмотром запуска и вывода. Связать материалы с исполнением агента, которое их собрало. Не утверждать, что чтение произошло, только по плану агента: источником служат фактические события и сохранённые материалы.

□ 80. После завершения collection зафиксировать версию начального контекста и передать её проверке. Дополнительные чтения и команды этапа review не добавлять в этот исходный контекст и не отображать в данном разделе. Их отдельное журналирование и просмотр во время проверки проработаем позже; это не требование прекратить технические журналы исполнений.

□ 81. Модель: initialContext с version, collectionExecutionId, startedAt, completedAt и items[]. Элемент: id, kind (file/fragment/command/script/other), title, sourcePath?, snapshotPath?, lineRanges?, sourceRevision?, collectedAt, executionId. Для команд: command/scriptPath, cwd, startedAt, finishedAt, exitCode, stdoutPath, stderrPath, truncation/redaction. Материалы и снимки — внутри context/project/ соответствующего review.

Файловое дополнение:
context/project/manifest.json — реестр начального контекста
context/project/files/<itemId>/ — снимки файлов и фрагментов
context/project/commands/<itemId>/ — command.json, script.sh при наличии, stdout.txt, stderr.txt
context/project/other/<itemId>/ — дополнительные материалы.

□ 82. Результаты проверки ссылаются на конкретную версию initialContext. Повторный сбор создаёт новую версию, сохраняя связь старых результатов с предыдущей. Пока сбор идёт, раздел дополняется постепенно; после завершения его содержимое не пополняется действиями проверки.

12 — Навигация этапов, методы и затраты

□ 83. «Контекст / Проверка / Результат» — вкладки и одновременно статусы процесса. Выбранную вкладку выделять толщиной рамки 2 px вместо 1 px, сохраняя цвет её статуса. Светлую или белую обводку выбора не использовать. При начале проверки автоматически открыть «Проверка». Пользователь может вернуться в «Контекст», не останавливая процесс; очередное обновление статуса не должно возвращать его обратно.

□ 84. В «Контексте» показывать начальные материалы; в «Проверке» — текущие действия и методы ревью; в «Результате» — итоги и сравнение. В MVP одна методика: агент с возможностью субагентов. Merilo + workflow — после MVP.

□ 85. Для каждого этапа и метода показывать длительность, токены и фактическую модель/модели. Сохранять входные, кэшированные входные и выходные токены отдельно по модели и вызову. Неизвестные показатели отображать как недоступные, не как нули.

□ 86. API-эквивалент считать по сохранённым тарифам конкретной модели и типам токенов. Сохранять источник/дату и версию тарифа, валюту, стоимость в USD, курс 100 RUB/USD и рассчитанную стоимость в RUB. Это оценка API, не фактическое списание подписки Codex. При отсутствии тарифа показывать недоступность оценки. Цифры и модели A/B в макете исключительно иллюстративные, не проверенные тарифы.

□ 87. Длительность этапа — прошедшее время, не сумма параллельных методов. Токены и стоимость агрегировать без двойного учёта управляющего агента и дочерних запусков; общий контекст учитывать один раз.

□ 88. Модель: activeStage отдельно от выбранной пользователем вкладки; methods[] с id, kind, config, status, currentActivity, executionIds и resultRef. Метрики этапов/методов с duration, usageByModel, pricingSnapshot и estimatedCost. Конфигурацию методов сохранять для сопоставимого сравнения. Подробное сравнение результатов проектируем следующим шагом.

□ 89. Шапку review разделить на две колонки: слева название, даты и ссылки; справа постоянный блок общих затрат всего review (время, токены, API-эквивалент USD и RUB). Блок находится в потоке layout, не плавает. Убрать общие метрики из отдельной строки под этапами.

□ 90. Общие затраты обновляются динамически и одинаковы при переключении между «Контекстом», «Проверкой» и «Результатом». Время — полная длительность review; токены и деньги — сумма без двойного учёта. Детализацию по этапам, методам и моделям открывать из блока затрат; её экран проработать отдельно. При отсутствии usage/тарифа показывать «—», не ноль. Пример 28 000 токенов и $0.13 условный.

□ 91. При ширине 1280 px правый блок — 280 px, слева гибкая область; ссылки переносятся строками. При расширении окна растёт левая колонка. Хранить агрегаты/их источники в модели метрик review, выбранная вкладка на значения не влияет.

□ 92. Блок затрат компактный, около 112 px высотой при обычной трёхстрочной шапке. Заголовок «Затраты ревью» жирный, длительность рядом обычным мелким текстом. Ниже три строки: Input, Cache, Output — количество токенов и API-стоимость каждого типа; внизу суммарный API-эквивалент всех запросов в USD и RUB. Большие цифры и отдельную строку курса убрать; курс и тарифы доступны в детализации.

□ 93. Input в таблице означает некэшированные входные токены; Cache — кэшированные входные; Output — выходные. Если provider сообщает общий input и его cached-подмножество, некэшированные вычислять как input − cached, не считать кэш дважды. Использовать фактическую статистику Codex по вызовам, сохраняя исходные usage-поля и нормализованную разбивку.

□ 94. При отсутствии cache-breakdown или тарифов показывать «—» для неизвестных значений. Не угадывать долю кэша или стоимость. Достоверный общий расход токенов можно показывать в детализации даже без разбивки; неполную оценку стоимости обозначать явно. Цены по типам суммировать по моделям и запросам до округления. Значения в макете — иллюстративные.

□ 95. Не растягивать блок затрат по высоте при переносе ссылок слева. Он занимает собственную необходимую высоту и выровнен по верхнему краю шапки.

13 — Результат как экскурсия и сравнение методик

□ 96. После MVP добавить четвёртую вкладку процесса «Сравнение» после «Результата». Результат отдельный для каждой методики, но формат представления и контракт единые: агент, Merilo/workflow и другие методы должны подготовить обоснованные выводы. Макеты 05 и 06 концептуальные, требуют дальнейшей проработки.

□ 97. Каждое замечание — самостоятельная мини-экскурсия: краткий тезис, критичность, причина, условия воспроизведения, наблюдаемый эффект и последовательный путь доказательства. Пользователь проходит шаги и понимает, почему замечание валидно и что нужно исправить.

□ 98. Шаг экскурсии может выделять строку, диапазон или функцию целиком с пояснением. Ссылаться можно на новые, старые и неизменённые строки любого файла проекта. Хранить снимок/ревизию, путь, сторону diff и диапазон, чтобы привязка не менялась вместе с рабочей копией.

□ 99. Обосновывать замечания кодом, требованиями или дизайном. Для несоответствия задаче приводить конкретное требование и объяснять расхождение с реализацией. Для дизайна показывать рядом сохранённое изображение/его область и ссылку на источник. Не подменять доказательство общей ссылкой.

□ 100. Если нет кода, к которому можно привязать замечание, не строить искусственный flow. Показать обычное обоснованное замечание с явной пометкой «Нет привязки к коду», причиной отсутствия и ссылкой на требования или иное основание.

□ 101. Результаты могут содержать дополнительные снимки-доказательства из этапа проверки. Хранить их в artifacts/results/<methodId>/evidence/, не дополняя зафиксированный initialContext. Экскурсия должна быть воспроизводимой по сохранённым материалам.

□ 102. Модель результата: methodId, verdict, findings[]. Замечание: id, title, severity/blocking, explanation, reproduction, observedEffect, expectedBehavior, evidence[], tourSteps[], noCodeAnchorReason?. Шаг: order, explanation, evidenceRef, filePath?, revision?, lineRange?, functionRange?, diffSide?. Основания включают ссылки на сохранённые задачи/комментарии/дизайн и снимки кода.

□ 103. После MVP — сравнение методик: сопоставлять одинаковые замечания, показывать совпадения и уникальные находки, расхождения вердиктов, доказательства, время, токены и API-эквивалент. Сравнивать на одной версии контекста; несовпадения входов явно обозначать. Не объявлять метод лучше только по числу замечаний.

□ 104. После MVP предусмотреть оценку валидности находок пользователем и выбор предпочтительной методики на основе качества и стоимости. Модель сравнения: contextVersion, methodResultRefs, findingMatches, uniqueFindings, validationDecisions, metrics, conclusion/preferredMethodId?. Автоматическое сопоставление и правила выводов ещё проработать.

□ 105. Хранить результаты, экскурсии и сравнение файлами внутри review. Каждая методика отвечает за собственный законченный результат в общем формате. Историю попыток и версии выводов сохранять; не затирать другие методы.

14 — Агентская проверка MVP; workflow после MVP

□ 106. После MVP поддержать две методики: agent — один агент с возможностью привлекать субагентов; merilo_workflow — Merilo в составе workflow. Результаты, сравнение, конфигурация и затраты группируются по этим двум методикам.

□ 107. Агентская проверка автономна: выполняет ревью и возвращает результат, не задавая пользователю вопросов. Показывать фактический статус работы, доступ к журналу и завершение/ошибку. Не выдумывать этапы или процент прогресса, которых нет в событиях агента. Субагенты относятся к этой же методике, их работа и затраты входят в неё.

□ 108. После MVP: для Merilo + workflow переиспользовать существующий UI графа WorkflowGraph и состояния WorkflowNode: реальные шаги, завершённые, текущий и ожидающие. Открытие узла должно давать существующий просмотр деталей/логов workflow. Демонстрационные названия узлов макета не задают обязательную структуру workflow.

□ 109. Данные: method.kind = agent | merilo_workflow; executionIds, parent/subagent связи, workflowRunId для второго метода. Прогресс брать из существующих состояний исполнений и событий. Вопросы по сбору контекста относятся к этапу «Контекст»; этап агентской проверки не предусматривает диалоговых уточнений.

□ 110. После MVP: добавить результаты двух методик и их сравнение. Общий контракт доказательных экскурсий сохраняется. Детальную работу с графом, журналом и итогами проработать дальше.

□ 111. В MVP компактная горизонтальная панель показывает статус «Агент выполняет ревью», справа кнопка «Журнал». Модель и effort не дублировать в панели: они показаны под соответствующей кнопкой этапа. Инструкции и действия постоянно показаны ниже панели. Пояснение о самостоятельной проверке и субагентах не показывать. По умолчанию агент проверки использует gpt-6-astra с effort high; показывать сохранённую фактическую конфигурацию запуска.

□ 112. Модель и effort получать из фактической конфигурации текущего исполнения и сохранять в его метаданных: model, reasoningEffort. Если значения неизвестны, показывать «—». Изменения конфигурации между попытками сохранять в истории исполнений.

□ 113. Под панелью агента постоянно показывать Markdown-представление фактического первоначального запроса текущей попытки и список действий. Показывать правила проверки, переданные инструкции скиллов и конфигурацию субагентов/делегирования. Это не исходная постановка пользователя — у неё отдельная кнопка документа в шапке.

□ 114. Сохранять точный собранный запрос перед запуском в executions/<executionId>/prompt.md; рядом — manifest с model, reasoningEffort, promptVersion, skills (ID, версия/источник, снимок доступных инструкций), delegationConfig и ссылками на контекст. Не подменять фактические данные актуальными версиями скиллов после запуска. Скрытые системные инструкции провайдера не обещать.

□ 115. Встроенная область: список действий слева и прокручиваемый Markdown справа; модель/effort/попытка относятся к выбранному исполнению. Просмотр только для чтения, не меняет работающий запрос. Фактические вызовы скиллов и запуски субагентов отличать от настроенных возможностей; события доступны в журнале. Отсутствующие данные явно обозначать, не выдумывать.

□ 116. «Инструкции и действия агента» — постоянная область вкладки «Проверка» под панелью статуса, без модалки и отдельной кнопки открытия. По умолчанию открыт сохранённый промпт Agent Reviewer. Слева кликабельный список: основной агент, фактически прочитанные/вызванные скиллы, фактически запущенные субагенты; справа Markdown выбранного документа. Список динамически обновляется, выбранный документ самопроизвольно не меняется.

□ 117. Для скилла показывать имя, подтверждённый вид события (прочитан / вызван, если такой вызов наблюдаем), время и сохранённый текст именно использованной версии. Чтение не объявлять выполнением. Если выполнение скилла не имеет отдельного события, не выдумывать его.

□ 118. Для субагента показывать поручение/название, состояние и время запуска. По нажатию открывать точный исходный промпт и переданное поручение; модель и effort относятся к выбранному исполнителю. Его собственные скиллы и дочерние агенты связывать с ним через parentExecutionId.

□ 119. Данные попытки: activityEvents[] с eventId, executionId, parentExecutionId?, kind, timestamp, documentRef и status; skillUses[] со skillId, source, contentHash/version, snapshotPath и read/invocation событиями; subagentExecutions[] с promptPath, taskPath, model, effort, status. Хранить документы и события в executions/<executionId>/, не добавлять их в замороженный initialContext.

□ 120. На старте списки пусты; показывать «Скиллы ещё не прочитаны» и «Субагенты ещё не запускались». Не подставлять настроенные возможности вместо фактических действий. Если наблюдаемость отсутствует, явно показывать недоступность данных. Снимок документа сохранять при его использовании, чтобы поздняя правка файла не изменила историю.

□ 121. Кнопка «Журнал» открывает отдельную модалку с непосредственными логами агента; закрытие крестиком и Escape. Логи не подменяют встроенные инструкции, скиллы и поручения субагентам. Содержимое модалки журнала проработать отдельно. При росте списка и документов предусмотреть прокрутку, не обрезать доступ к данным.

□ 122. Главный экран «Результат» — список всех замечаний, а не сразу открытая экскурсия. Каждая карточка содержит приоритет, заголовок, краткое объяснение, основание/место при наличии и действие «Разобрать замечание», открывающее доказательную экскурсию.

□ 123. P0 и P1 — блокирующие, приводят к Request changes. P2 и P3 — неблокирующие рекомендации. При отсутствии P0/P1 и успешном завершении проверки — Approve, даже если есть рекомендации. Приоритет обязателен в модели finding.priority; blocking определяется согласованным отображением P0/P1.

□ 124. Рядом с вкладкой «Результат» показывать два компактных счётчика как в истории: красный — P0+P1, серый — P2+P3. Общие правила 18 px, gap 3, 9+ и подсказка с точным количеством сохраняются. Показанный пример: P1 — 1, неблокирующих — 2. Список сортировать по приоритету; экскурсии остаются содержимым отдельных замечаний.

□ 125. Если замечание связано с задачей/требованием, показывать task ID отдельным нейтральным лейблом в заголовке карточки у правого края. При нескольких задачах — отдельный лейбл каждой. Не добавлять лейбл без подтверждённой связи.

□ 126. Действия карточки: «Разобрать замечание» с ChevronRight Gravity UI и «Скопировать промпт» с иконкой Copy. Копирование помещает в буфер только промпт для исправления выбранного замечания, не запускает агента и не изменяет код. Показывать подтверждение «Промпт скопирован»; при ошибке копирования — понятное сообщение.

□ 127. Промпт исправления включает ID review/замечания, приоритет, описание проблемы, ожидаемое поведение, воспроизведение, доказательства и ссылки/пути к сохранённым материалам, связанные требования и критерии проверки исправления. Попросить агента проверить актуальный код и исправить причину; не придумывать способ исправления без оснований.

□ 128. Модель finding: relatedTaskIds[], fixPromptPath и версия источника промпта. Сохранять Markdown-промпт рядом с результатом: artifacts/results/<executionId>/findings/<findingId>/fix-prompt.md. Обновлять при изменении замечания; копируемый текст должен соответствовать показываемой версии.

□ 129. Кнопки карточки выровнять по правому краю: слева «Скопировать промпт», справа «Разобрать замечание». Для разбора использовать именно ChevronRight, не стрелку ArrowRight и не текстовый символ.

□ 130. В результате сразу под навигацией этапов и до замечаний показать единую кнопку-плашку «Обзор изменений» с крупным ChevronRight справа. Подзаголовка и вложенной кнопки нет. Нажатие в любом месте плашки открывает обзор; поддержать Enter/Space и видимый фокус. Это обзор всего набора изменений, независимый от наличия замечаний и итогового вердикта.

□ 131. Агент сначала разбирается в назначении и работе изменений, затем на этой основе проверяет корректность и формирует замечания. В итоговом результате сохраняет готовую обзорную экскурсию. Нажатие открывает сохранённый материал, а не запускает новую генерацию.

□ 132. Экскурсия объясняет цель, объём и границы изменений, поведение до/после, связанные задачи и требования, основные участки кода и их взаимодействие. Порядок смысловой: от цели и точки входа к основному сценарию и последствиям, не по алфавиту файлов. Каждый шаг опирается на сохранённый код, diff, требования или дизайн. Не придумывать мотивацию: неизвестные причины явно отмечать.

□ 133. Общий viewer поддерживает два вида экскурсий: overview — понимание изменений, finding — доказательство конкретного замечания. Пользователь может сначала пройти обзор, затем открыть замечания; обязательного прохождения обзора нет. Просмотр помогает самостоятельно оценить смысл и соответствие изменений требованиям, не подменяя это вердиктом агента.

□ 134. Модель результата: overviewTour с title, summary, purpose, scope, requirementRefs, contextVersion и упорядоченными steps[]. Шаг: id, title, explanation, before/after при необходимости, evidenceRefs и привязки к файлам/диапазонам/функциям. Использовать общий контракт шагов с экскурсиями замечаний; различать tour.kind.

□ 135. Хранить обзор в artifacts/results/<executionId>/overview-tour.json и связанные доказательства рядом. Даже при approve без замечаний обзор сохраняется и доступен. Неполные доказательства и отсутствие связи с требованиями явно обозначать. Детальный viewer обзорной экскурсии проработать следующим макетом.

□ 136. Убрать экран сравнения из текущего дизайна MVP. Вместо него viewer общего обзора и замечания: модалка почти на весь viewport, внешние отступы 16 px, закрытие крестиком/Escape с возвратом в результат.

□ 137. Viewer: слева смысловой маршрут шагов, в центре код и комментарии к строке/диапазону/функции, справа связанные требования, комментарии задач, дизайн или воспроизведение. Внизу «Назад / Следующий шаг» и номер шага. Области прокручиваются, навигация остаётся доступной.

□ 138. Показывать точные сохранённые снимки кода с номерами строк, выделением диапазонов и визуальной связью комментария с кодом. Переход между шагами выбирает нужный файл и диапазон. Поддержать изменённые и неизменённые файлы, старую/новую сторону diff и просмотр полного файла.

□ 139. Связанные основания открываются рядом без потери шага: текст требования и источник задачи, сохранённое изображение дизайна с областью. Если связи нет, явно указать это. Иллюстративный код макета не является реальным найденным дефектом.

□ 140. Отмечать просмотренные шаги без дополнительных текстовых счётчиков в боковой панели и без принудительной блокировки переходов. Для полного разбора предложить пройти все шаги. Хранить состояние просмотра отдельно от содержимого review: tourId, tourVersion, selectedStepId, visitedStepIds. Чтение не обновляет updatedAt.

□ 141. Viewer фокусирует внимание на одной мысли текущего шага. Убрать боковые подписи «Шаг / Просмотрено», пояснение о diff и файлах проекта, анонсы «Что проверяем дальше». Номер шага остаётся только в нижней навигации. Показывать минимум необходимых элементов управления; дополнительные детали раскрываются по запросу.

□ 142. Обзор строить от продуктовой цели: какую бизнесовую или техническую задачу решают изменения, для кого и зачем. Каждый шаг объясняет, как показанная реализация помогает достичь этой цели; не пересказывает синтаксис и названия функций. Техническая оптимизация тоже имеет цель: например, сократить ожидание или расход ресурсов.

□ 143. Писать простыми словами для младшего разработчика и менеджера. Заголовок отражает смысл шага, пояснение — одна короткая мысль (обычно 1–2 предложения). Термины вводить только при необходимости и объяснять. Сложную причинную цепочку разбивать на дополнительные шаги, а не длинный абзац. Не терять точность ради краткости.

□ 144. На шаге показывать только необходимый фрагмент кода и связанное с ним основание из требования/дизайна. Пояснение связывает цель, действие системы и наблюдаемый эффект. Для замечаний сохранять причинную доказательность и воспроизведение, но не отвлекать анонсами следующих шагов.

□ 145. В контракте overviewTour сохранять productGoal (бизнесовая или техническая цель) и для каждого шага смысловой заголовок, краткое explanation, goalRef и evidenceRefs. Недоказанную связь с целью явно отмечать, не придумывать требования.

□ 146. В областях просмотра кода использовать JetBrains Mono с поддержкой лигатур, включая номера строк. Основной текст интерфейса оставить в Inter. В frontend включить font-variant-ligatures для отображения кода; сохранять точный исходный текст при копировании.

□ 147. Пояснение к фрагменту формулировать как конкретное действие текущего шага: что происходит, при каком событии и с какими данными. Например: «При нажатии “Войти” отправляем введённые почту и пароль на проверку». Не использовать шаблон «Зачем нужен этот код / Чтобы…» и не пересказывать синтаксис. Короткие пояснения по шагам должны складываться в общую картину работы системы. Общую цель объяснять в начале обзора, не повторять её в каждом комментарии; направление запросов и другие детали указывать только при наличии подтверждения в коде.

□ 148. У пояснения к коду нет отдельного заголовка: только короткое тело комментария, связанное с выделенными строками. Не дублировать его смысл заголовком.

□ 149. Если шаг ссылается на элемент интерфейса (например, кнопку «Войти»), рядом с задачей показывать соответствующее сохранённое изображение дизайна, чтобы пользователь видел, о какой форме идёт речь. Превью открывается в увеличенном виде; при необходимости выделять связанную область. Использовать реальные assets из context/designs/, не генерировать подмену дизайна. При отсутствии подходящей картинки явно отметить отсутствие. Превью формы в текущем макете — иллюстрация, а не выгрузка источника.

□ 150. В evidenceRefs шага хранить designAssetId, локальный путь/версию и необязательную область выделения; задача и дизайн могут одновременно быть основаниями одного шага.

□ 151. Дизайн в viewer — изображение (единый asset), не интерактивная форма и не заново свёрстанные контролы. Предпочитать уже сохранённые изображения начального контекста. Если агент дополнительно экспортировал дизайн во время проверки, сохранить новый asset в evidence текущего исполнения и связать с шагом, не менять замороженный initialContext.

□ 152. Для изображения хранить источник, время экспорта, локальный путь, хеш/версию и фазу получения (collection/review). Не генерировать замену исходному дизайну. В макете PNG получен из демонстрационной формы и явно помечен как пример; в приложении подставлять фактически выгруженный дизайн.

□ 153. Под изображением дизайна не показывать кнопку увеличения и технические пояснения о PNG/ассете. Нажатие на само изображение открывает увеличенный просмотр; доступ с клавиатуры и понятное accessible name сохранить. Источник и версия остаются в данных, не занимают место постоянными подписями.

□ 154. Цвет выделения кода обозначает происхождение: зелёный — добавленный код, красный — удалённый, синий — контекст для понимания без утверждения, что код менялся. В diff сохранять маркеры +/−, не полагаться только на цвет.

□ 155. Ошибка не меняет diff-цвет кода на красный. Отмечать её отдельным небольшим жирным красным заголовком «Место ошибки» у соответствующего диапазона. Добавленная строка с ошибкой остаётся зелёной. Комментарий объясняет проблему отдельно. В модели разделять changeKind (added/deleted/context) и findingAnchor; одно не выводить из другого.

□ 156. Пояснение, относящееся к месту ошибки, показывать на фоне danger-light с красной предупреждающей иконкой Gravity UI. Обычные пояснения остаются информационными. Цвет блока комментария не меняет семантику цветов diff: добавленный код остаётся зелёным, удалённый — красным.

15 — Публикация ревью и передача доказательств следующему агенту

□ 157. Если объект проверки — переданный PR/MR или аналог в инфраструктуре пользователя, агент-ревьюер публикует найденные замечания в этой сущности. Если проверяются только локальные изменения без PR, ничего внешне не публиковать: файлы review и интерфейс Lawa остаются местом хранения и просмотра.

□ 158. Для замечания с привязкой к коду создавать комментарий к соответствующей строке или диапазону проверяемой версии PR. Использовать интеграцию и инструменты пользователя через агента, без привязки UI к GitHub или другому провайдеру. Если сервис не поддерживает диапазон, неизменённый файл или старую строку, публиковать обоснование в доступном месте PR со ссылками на точные пути/ревизии/строки; не создавать неверную привязку. Для замечания без кода явно написать, что привязки к коду нет и почему.

□ 159. Текст комментария — полноценное Markdown-представление замечания: ID, приоритет P0–P3, блокирует ли принятие изменений, краткий тезис, требование/ожидаемое поведение, условия воспроизведения, фактическое последствие и последовательность проверяемых доказательств. Путь доказательства отражает те же шаги, код и пояснения, которые человек видит в viewer. Это структурированное обоснование по источникам, а не скрытые внутренние рассуждения модели.

□ 160. Включать ссылки на задачу, ТЗ, конкретные требования и комментарии, дизайн и фрагменты кода. Приводить необходимые цитаты, фрагменты и пояснения прямо в комментарии, чтобы следующий агент мог восстановить логику проблемы без доступа к локальному UI Lawa. Ссылки на локальные файлы не выдавать за доступные внешнему читателю. Если изображение нужно для доказательства, прикрепить сохранённый asset средствами сервиса при поддержке либо дать доступную ссылку на источник и текстовое описание соответствующей области. Недоступность источника явно отмечать.

□ 161. UI, Markdown-комментарий, промпт исправления и машинный результат строятся из одного сохранённого набора finding/tour/evidence. Не генерировать независимые противоречащие версии. Сохранять полный Markdown каждого замечания локально до публикации. Общий обзор изменений тоже сохранять в Markdown; при публикации обзора связывать его с итогом ревью PR.

□ 162. Следующий агент должен по опубликованному тексту независимо проверить актуальность замечания, пройти путь проблемы и подготовить исправление. Указывать проверенную ревизию/снимок и условия применимости, отличать наблюдённое поведение от предположения. Повторную проверку на актуальном коде не подменять авторитетом первого ревьюера.

□ 163. Публикация — отдельное состояние результата: pending/publishing/published/partial/failed/not_applicable. Технический сбой публикации не уничтожает локальный результат и не меняет найденный вердикт. Сохранять ошибку и возможность повторить публикацию. Повторная попытка не должна создавать дубликаты: связывать локальный findingId с ID/URL внешнего комментария и версией опубликованного содержимого. При неизвестном результате запроса сначала сверять внешнее состояние.

□ 164. Если PR изменился после анализа, проверить применимость привязок к ревизии; не публиковать старые номера строк как актуальные. Отметить устаревший результат/необходимость перепроверки. Не изменять код, не сливать PR и не закрывать замечания автоматически в рамках публикации ревью.

Модель и файловое дополнение:
artifacts/results/<executionId>/review.md — текстовый итог
artifacts/results/<executionId>/overview.md — обзор изменений
artifacts/results/<executionId>/findings/<findingId>/comment.md — полное обоснование для PR и следующего агента
artifacts/results/<executionId>/publication.json — состояние публикации, target URL/ID, provider-neutral target kind, reviewed revision, findingId → externalCommentId/URL, publishedContentVersion/hash, timestamps, ошибки и попытки.

□ 165. В контракте агента требовать как структурированный результат для viewer, так и согласованный Markdown-экспорт. Действия публикации и ссылки на созданные комментарии фиксировать в журнале review. Детальное отображение ошибок/повторов публикации проработать отдельно; внешняя публикация является частью требований PR-ревью MVP.

16 — Три агента, конфигурация перед запуском и CLI review

□ 166. Разделить выполнение на три этапа с независимыми настройками: collection собирает начальный контекст; review анализирует код и сохраняет замечания; presentation — отдельный агент, который готовит обзор изменений, доказательные экскурсии и Markdown-представление результатов.

□ 167. Проверяющий агент не обязан писать готовый storytelling, но обязан сохранить фактические основания, привязки, сценарий проблемы и доступные доказательства, достаточные для передачи. Агент презентации не выдумывает обоснования ради убедительности: при нехватке доказательств помечает неполноту или запрашивает внутреннюю перепроверку. Итог готов только после презентации.

□ 168. Для каждого этапа настраивать model, reasoningEffort, инструкции/скиллы и правила субагентов. Отображать фактически выбранные model/effort рядом с этапом и в подробностях исполнения. Не использовать одну конфигурацию автоматически для всех этапов. Подтверждённые настройки по умолчанию: collection и presentation — model gpt-6-sol, reasoningEffort high; review — model gpt-6-astra, reasoningEffort high.

□ 169. В MVP на главном экране до запуска показывать три группы настроек модели и effort: «Контекст», «Проверка», «Результат». Заполнить подтверждёнными значениями по умолчанию; пользователь может изменить их до нажатия «Запустить ревью». Отдельную страницу настроек и её кнопки не реализовывать. Фиксировать resolvedConfig и источник значений при запуске, фактическую конфигурацию каждой попытки — отдельно.

□ 170. Добавить команду lawa review с исходным промптом, эквивалентным вводу в UI. По умолчанию поднимать/показывать UI конкретного review. Флаг --no-ui отключает UI полностью; выполнение, запись результатов и публикация PR работают независимо от браузера. Команда должна быть описана в CLI help и инструкциях Lawa для агентов.

□ 171. Предлагаемый контракт CLI: lawa review --prompt <текст> [--config <файл.json> | --config-json <JSON>] [--no-ui]. Файл и inline JSON взаимоисключающие; используют одну версионированную схему stage config. Валидировать до запуска, выдавать понятную ошибку неизвестной модели/effort. Способ передачи большого промпта через stdin/файл уточнить при реализации.

□ 172. После запуска review конфигурация неизменяема для всей его жизни, включая повторные попытки. Это одинаково для UI и CLI. В существующем review показывать фактически использованные модели и effort только для чтения. Другую конфигурацию можно задать только перед созданием нового review.

□ 173. В MVP использовать встроенные подтверждённые defaults и переопределения только при запуске (UI либо CLI-файл/JSON). Редактор глобальных/проектных настроек и сложное наследование отложить. Сохранять resolved-config.json внутри review. Структура: schemaVersion, stages.collection/review/presentation с model, reasoningEffort, agentConfig; origin по полям. Метрики каждого этапа и его агента учитываются отдельно и в сумме без дублей.

□ 174. Обновить прежний контракт этапов: результат — выполняемый этап презентации, а не только статичная вкладка. На его запуске показывать running, после готовности — итог. PR-публикация использует окончательный доказательный Markdown после презентации; сохранять отдельное состояние публикации.

□ 175. Модель и effort показывать под кнопкой каждого этапа отдельной подписью: 9 px, secondary, по горизонтальному центру кнопки, без рамки и без действия. Внутри кнопки — только название этапа и статус. Эти данные только для чтения; для другой конфигурации пользователь останавливает текущий review при необходимости и создаёт новый.

Как поддерживать задачу

После каждого согласованного решения одновременно обновлять макет, пункты реализации, модель данных и файловую структуру. Новые сущности и поля, обсуждённые при проектировании UI, являются требованиями к данным, а не только к отображению.

Для каждого поля фиксировать: какой сущности оно принадлежит, смысл и тип, обязательность, источник значения, место хранения и условия обновления. Например, заголовок review хранится в его метаданных; список проверяемых изменений требует отдельного поля или коллекции у соответствующей сущности, а не только текста на экране. Большие материалы хранить отдельными файлами с явными ссылками из модели.

Различать сохранённые данные и вычисляемое представление: исходный timestamp хранится, формат даты вычисляется; точное количество замечаний сохраняется или считается по замечаниям, «9+» — только отображение. Не дублировать одну информацию без необходимости.

Поддерживать раздел структуры данных как актуальное описание, заменяя устаревшие поля и правила, а не накапливая противоречащие дополнения. Для ещё не согласованных деталей явно отмечать вопрос; не оставлять требование без места в модели. Контракт обмена с агентами уточнять вместе с моделью.

Нерешённые вопросы не считать готовыми требованиями. Галочки отмечать после реализации и проверки. Старые требования, противоречащие новому решению, заменять.
