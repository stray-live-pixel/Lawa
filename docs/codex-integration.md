# Интеграция Lawa с Codex

Дата решения: 2026-08-31. Связанная задача:
[GitHub issue #57](https://github.com/stray-live-pixel/Lawa/issues/57).

## Решение

Lawa поддерживает один runtime: официальный Codex App Server, запущенный как
`codex app-server --stdio`. Публичный CLI не раскрывает процессы, RPC, thread и
turn: пользователь работает с `run`, `resume`, `status`, `logs` и `serve`.

App-native runtime удалён. Lawa не создаёт нативные задачи Codex Desktop и не
обещает, что App Server thread будет отображён в приложении.

## Почему не Codex Desktop

На дату решения у Codex Desktop нет публично документированного программного API,
через который внешний Go-процесс Lawa мог бы:

- создать нативную задачу с точным cwd и настройками;
- получить устойчивый task/thread ID;
- подписаться на её lifecycle и финальный результат;
- продолжить или прервать конкретный turn;
- восстановить управление после перезапуска без дубликата.

Фраза относится именно к API задач Desktop. У Codex есть официальный App Server,
и Lawa использует его напрямую.

Технически управляющий агент в уже открытом Desktop мог бы вызывать инструменты
создания и чтения задач. Этот путь отвергнут как runtime-архитектура: каждый шаг
workflow требует дополнительных модельных turn управляющего агента, добавляет
задержку и стоимость, а один controller становится узким местом для 20 и более
параллельных workflow. После завершения или сбоя controller задача теряет
надёжного владельца.

Решение можно пересмотреть, только если появится публичный API Desktop с
программным созданием, наблюдением и восстановлением задач без модельного
агента-посредника.

## Почему App Server

[Официальная документация App Server](https://learn.chatgpt.com/docs/app-server)
описывает его как протокол для богатых клиентов Codex. Он предоставляет
инициализацию, создание и чтение thread, запуск и прерывание turn, потоковые
уведомления, approvals и историю. Эти примитивы позволяют Lawa быть обычным
детерминированным процессом:

1. До сетевого запроса Lawa получает общий root-level слот и атомарно резервирует
   поместившуюся часть готовой волны в `meta.json`.
2. Для каждого кубика запускается отдельный App Server, поэтому независимые turn
   работают параллельно и не делят RPC writer.
3. Thread ID сохраняется до `turn/start`.
4. Turn ID сохраняется сразу после ответа `turn/start`, до ожидания событий.
5. Один read-only App Server переиспользуется для `thread/read` при reconcile.
6. Новый thread получает структурированные `run_child` и `run_children` через
   официальный `dynamicTools`; встречный `item/tool/call` обрабатывает Lawa.
7. На SIGINT/SIGTERM Lawa отправляет `turn/interrupt` через исходную stdio-сессию.
8. `resume` продолжает только подтверждённо interrupted thread.

Отдельная сессия на активный turn изолирует сбой процесса и RPC-ID одного кубика
от остальных. Настраиваемый `--max-parallel N` ограничивает суммарное число turn
для всех процессов Lawa с одним root. Файловые `flock`-слоты не требуют общего
controller-процесса и освобождаются ядром после штатного завершения или crash.
Внешние лимиты Codex продолжают действовать независимо.

## Универсальность окружения

На личном macOS/Linux и на Linux-сервере действует одинаковый контракт. Наличие
Codex Desktop не проверяется и не меняет runtime. Обязательны:

- поддерживаемая ОС;
- доступный исполняемый файл `codex`;
- авторизация Codex CLI/App Server;
- существующий абсолютный cwd;
- доступ пользователя процесса к root Lawa.

На сервере dashboard по умолчанию остаётся на loopback. Для удалённого доступа
рекомендуется SSH port forwarding. Явная публикация на другом интерфейсе возможна,
но Lawa предупреждает о доступе к постановкам, памяти и журналам. Потоковый вывод
команд может содержать секреты, поэтому публикация dashboard без внешней защиты
небезопасна.

### Проверка и настройка авторизации

Перед `run` или `resume` оператор и скилл должны выполнить `codex login status` от
того же системного пользователя, который запускает Lawa. Проверка наличия бинарника
и `codex --version` недостаточна: они не подтверждают, что App Server сможет
выполнять turn. Вход в Codex Desktop также не является переносимой гарантией для
отдельного пользователя, SSH-сессии, контейнера или сервера.

На машине с браузером используется `codex login`. Для удалённого или
headless-окружения предпочтителен `codex login --device-auth`: обычный браузерный
flow зависит от localhost callback, недоступного в части серверных конфигураций.
Device code предварительно разрешается в настройках аккаунта или workspace.

Для доверенной неинтерактивной автоматизации официальный CLI поддерживает вход
через API key:

```sh
printenv OPENAI_API_KEY | codex login --with-api-key
```

Этот способ тарифицируется через OpenAI Platform. Ни агент, ни инструкция Lawa не
должны просить пользователя отправить API key, access token или
`~/.codex/auth.json` в чат, workflow, task, issue либо журнал. `auth.json` содержит
токены и обрабатывается как пароль. Актуальные способы входа и headless fallback
описаны в [официальной документации авторизации Codex](https://learn.chatgpt.com/docs/auth).

## Observability Lawa

Нативное приложение не является источником состояния. Lawa сохраняет:

- scheduler state, thread ID и последний turn ID в `meta.json`;
- lifecycle App Server с PID, exit code или signal;
- thread/turn lifecycle;
- тип item, его текущую активность и финальный текст `agentMessage`;
- выбранный live-вывод для dashboard: сообщения агента, reasoning summary, план,
  команду и потоковый вывод команды;
- краткие ошибки и числовые token usage;
- время каждого события.

Интерфейсы:

```sh
lawa status <run-id>
lawa logs <run-id> [step-id] [--follow]
lawa serve
```

`status` и `logs` читают только файлы run и не запускают App Server. Они выводят
краткое, безопасное для терминала представление и не показывают сохранённое поле
live-вывода. Dashboard также read-only, перечитывает атомарные snapshot других
процессов и сопоставляет потоковые delta по `turn.id` и `item.id`.

В компактном виде dashboard показывает workflow по времени последней активности,
новые сверху, счётчик успешных шагов и только выполняющиеся шаги. После раскрытия
видны все шаги, также отсортированные от новых к старым. Клик по шагу открывает
боковую панель; она дочитывает только дописанный хвост `events.jsonl`, не запускает
модель и не создаёт управляющего агента.

`logs --follow` хранит byte-позицию последней полной JSONL-строки и читает только
дописанный хвост. Терминальный `meta.json` не завершает follow, пока журнал не
содержит итоговое состояние того же turn: coordinator записывает эти два файла
последовательно, и без такой проверки последнее событие могло бы потеряться.

## Граница приватности

App Server присылает больше данных, чем нужно для оператора. Lawa делит журнал на
краткие поля для безопасного CLI и подробное поле `content` для приватной боковой
панели. Нормализатор никогда не сохраняет:

- raw reasoning и его delta;
- file diff;
- MCP/tool arguments и results;
- неизвестный сырой payload;
- внутренний rollout Codex.

CLI дополнительно экранирует управляющие C0/C1-символы в `status`, `logs` и
финальной ошибке. Например, ESC выводится как `\u001B`, поэтому сохранённая
диагностика не может выполнить ANSI/OSC-команду в терминале оператора. Само
содержимое run не меняется: экранирование относится только к представлению.

В подробное поле попадают только явно разрешённые события протокола: delta и
финальный текст `agentMessage`, читаемый `reasoning/summaryTextDelta`, обновление
плана, команда и `commandExecution/outputDelta`. Для MCP сохраняются только имя
сервера и инструмента, для file change — тип изменения и путь без diff. Финальные
агрегированные command/tool payload не дублируются.

Сообщения и отдельные delta ограничиваются по размеру и пишутся в приватный
`events.jsonl` с правами 0600. Однако команда, её вывод и ответ агента могут
содержать секреты, поэтому файл и dashboard нельзя считать публичными. Ошибка
журнала останавливает новые запросы: workflow не должен продолжаться без
обещанной наблюдаемости.

## Approvals

Lawa запускает сам процесс App Server с `approval_policy="on-request"` и
`approvals_reviewer="auto_review"`, а также повторяет эти значения в RPC thread и
turn. Managed restrictions остаются обязательными.
Неизвестный встречный запрос App Server без обработчика превращается в
`waiting_for_approval`; Lawa не отправляет молчаливое согласие.

## Нативные дочерние run

`run_child` и `run_children` — единственные встроенные действия Lawa, доступные
агенту. Они принимают структурированные `workflow`, `cwd`, `task`/`taskFile` и
`parentRun`, проверяют связь с текущим run и не исполняют shell. Дочерний cwd
ограничен workspace родителя; входные файлы можно читать только из workspace или
read-only папки родительского run.

После валидации процесс Lawa вызывает обычный `runstore.Create`. Возвращаемый
`runId` уже переживёт crash, потому что `meta.json` опубликован и каталоги
синхронизированы. Одинаковый повтор сначала ищет совпадающий опубликованный child
в существующем хранилище и возвращает его ID. Затем дочерний координатор работает
в том же процессе, получает общий root-level capacity pool и может тем же способом
создавать потомков. Верхняя команда ждёт всё дерево, поэтому daemon или новое
хранилище не нужны.

## Форматы и миграция

Новые run и серии имеют version 3. Сам номер означает единственный app-server
runtime; отдельное поле mode/driver не нужно.

Исторические app-server run v1/v2 остаются совместимыми. Выпущенные ранее
app-native и app-server run использовали одинаковый `meta.json`, поэтому
классификация опирается на защитные marker-файлы `app-create-*` и
`app-continue-*`. Если marker найден:

- `status`, `logs` и dashboard продолжают читать run;
- `resume` возвращает понятную ошибку;
- автоматическая миграция и создание новых задач запрещены.

Это консервативное правило исключает дубликат уже созданной Desktop-задачи.
Историческая v2 app-native серия определяется однозначно по `driver: "app"` и
также остаётся read-only. Полностью незапущенный v2 run без marker неотличим от
старого app-server run; его разрешено продолжить, потому что устойчивого
свидетельства внешней Desktop-задачи нет.

## Не-гарантии

- App Server thread может сохраняться в общем хранилище Codex, но его отображение
  в Desktop не является контрактом Lawa.
- Lawa не использует приватные socket, внутренний layout sessions или reverse
  engineering Desktop.
- Lawa не оценивает смысл финального ответа агента.
- Lawa не задаёт timeout turn. Общий root-level параллелизм можно ограничить
  `--max-parallel N`; настройка сохраняется и действует для `run` и `resume`.
