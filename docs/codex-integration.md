# Интеграция Lawa с Codex

Дата решения: 2026-08-31. Связанная задача:
[GitHub issue #57](https://github.com/stray-live-pixel/Lawa/issues/57).

## Решение

Lawa поддерживает один runtime: официальный Codex App Server, запущенный как
`codex app-server --stdio`. Публичный CLI не раскрывает процессы, RPC, thread и
turn: пользователь работает с `run`, `resume`, `status`, `logs` и `serve`.

App-native runtime удалён. Lawa не создаёт нативные задачи Codex Desktop и не
обещает, что App Server thread будет отображён в приложении.

## Почему не Codex Desktop

На дату решения у Codex Desktop нет публично документированного программного API,
через который внешний Go-процесс Lawa мог бы:

- создать нативную задачу с точным cwd и настройками;
- получить устойчивый task/thread ID;
- подписаться на её lifecycle и финальный результат;
- продолжить или прервать конкретный turn;
- восстановить управление после перезапуска без дубликата.

Фраза относится именно к API задач Desktop. У Codex есть официальный App Server,
и Lawa использует его напрямую.

Технически управляющий агент в уже открытом Desktop мог бы вызывать инструменты
создания и чтения задач. Этот путь отвергнут как runtime-архитектура: каждый шаг
workflow требует дополнительных модельных turn управляющего агента, добавляет
задержку и стоимость, а один controller становится узким местом для 20 и более
параллельных workflow. После завершения или сбоя controller задача теряет
надёжного владельца.

Решение можно пересмотреть, только если появится публичный API Desktop с
программным созданием, наблюдением и восстановлением задач без модельного
агента-посредника.

## Почему App Server

[Официальная документация App Server](https://learn.chatgpt.com/docs/app-server)
описывает его как протокол для богатых клиентов Codex. Он предоставляет
инициализацию, создание и чтение thread, запуск и прерывание turn, потоковые
уведомления, approvals и историю. Эти примитивы позволяют Lawa быть обычным
детерминированным процессом:

1. До сетевого запроса Lawa атомарно резервирует готовую волну в `meta.json`.
2. Для каждого кубика запускается отдельный App Server, поэтому независимые turn
   работают параллельно и не делят RPC writer.
3. Thread ID сохраняется до `turn/start`.
4. Turn ID сохраняется сразу после ответа `turn/start`, до ожидания событий.
5. Один read-only App Server переиспользуется для `thread/read` при reconcile.
6. На SIGINT/SIGTERM Lawa отправляет `turn/interrupt` через исходную stdio-сессию.
7. `resume` продолжает только подтверждённо interrupted thread.

Отдельная сессия на активный turn изолирует сбой процесса и RPC-ID одного кубика
от остальных. Параллелизм ограничен готовой волной workflow и внешними лимитами
Codex, а не controller-агентом.

## Универсальность окружения

На личном macOS/Linux и на Linux-сервере действует одинаковый контракт. Наличие
Codex Desktop не проверяется и не меняет runtime. Обязательны:

- поддерживаемая ОС;
- доступный исполняемый файл `codex`;
- авторизация Codex CLI/App Server;
- существующий абсолютный cwd;
- доступ пользователя процесса к root Lawa.

На сервере dashboard по умолчанию остаётся на loopback. Для удалённого доступа
рекомендуется SSH port forwarding. Явная публикация на другом интерфейсе возможна,
но Lawa предупреждает о доступе к постановкам, памяти и журналам.

## Observability Lawa

Нативное приложение не является источником состояния. Lawa сохраняет:

- scheduler state, thread ID и последний turn ID в `meta.json`;
- lifecycle App Server с PID, exit code или signal;
- thread/turn lifecycle;
- безопасный тип item и финальный текст `agentMessage`;
- краткие ошибки и числовые token usage;
- время каждого события.

Интерфейсы:

```sh
lawa status <run-id>
lawa logs <run-id> [step-id] [--follow]
lawa serve
```

`status` и `logs` читают только файлы run и не запускают App Server. Dashboard
также read-only и перечитывает атомарные snapshot других процессов.

## Граница приватности

App Server присылает больше данных, чем нужно для оператора. Нормализатор Lawa
никогда не сохраняет:

- reasoning и его delta;
- аргументы, stdout/stderr и полный результат command execution;
- file diff;
- MCP/tool arguments и results;
- неизвестный сырой payload;
- внутренний rollout Codex.

Из `item/completed` сохраняется текст только для типа `agentMessage`. Для token
usage сохраняются лишь числовые листья. Сообщения ограничиваются по размеру и
пишутся в приватный `events.jsonl` с правами 0600. Ошибка журнала останавливает
новые запросы: workflow не должен продолжаться без обещанной наблюдаемости.

## Approvals

Lawa запускает turn с `approvalPolicy: on-request` и
`approvalsReviewer: auto_review`. Managed restrictions остаются обязательными.
Неизвестный встречный запрос App Server без обработчика превращается в
`waiting_for_approval`; Lawa не отправляет молчаливое согласие.

## Форматы и миграция

Новые run и серии имеют version 3. Сам номер означает единственный app-server
runtime; отдельное поле mode/driver не нужно.

Исторические app-server run v1/v2 остаются совместимыми. Выпущенные ранее
app-native и app-server run использовали одинаковый `meta.json`, поэтому
классификация опирается на защитные marker-файлы `app-create-*` и
`app-continue-*`. Если marker найден:

- `status`, `logs` и dashboard продолжают читать run;
- `resume` возвращает понятную ошибку;
- автоматическая миграция и создание новых задач запрещены.

Это консервативное правило исключает дубликат уже созданной Desktop-задачи.
Историческая v2 app-native серия определяется однозначно по `driver: "app"` и
также остаётся read-only. Полностью незапущенный v2 run без marker неотличим от
старого app-server run; его разрешено продолжить, потому что устойчивого
свидетельства внешней Desktop-задачи нет.

## Не-гарантии

- App Server thread может сохраняться в общем хранилище Codex, но его отображение
  в Desktop не является контрактом Lawa.
- Lawa не использует приватные socket, внутренний layout sessions или reverse
  engineering Desktop.
- Lawa не оценивает смысл финального ответа агента.
- Lawa не вводит собственный глобальный лимит параллелизма или timeout.
