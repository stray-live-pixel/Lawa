# Проверка интеграции Lawa с Codex App

Первичная проверка: 2026-08-28. Повторная проверка: 2026-08-29.
Требования: [MVP](../product/1.md).

## Вывод

**Создание задачи и немедленный запуск команды без перезапуска Desktop проверены.**
Отдельный официальный `codex app-server --stdio` создал чат, выполнил один короткий
запрос, а задача и ответ появились в списке и истории Desktop. После остановки
тестового сервера новый процесс восстановил тот же чат и прочитал единственный
завершённый turn. Это проверка способа интеграции, ещё не адаптер или команда Lawa.

Права памяти отдельно проверены на macOS. Живое управление из Desktop, запросы
разрешений, сохранение работающего агента после выхода Lawa и восстановление при
потере ответа создания пока не подтверждены. Общий сервер с Desktop не является
обязательным условием самого создания видимого чата: первоначальный вывод был
слишком широким. Подробности реального теста приведены ниже.

Повторная проверка выявила дополнительное ограничение: одного флага
`CODEX_APP_SERVER_USE_LOCAL_DAEMON=1` для установленной версии недостаточно.
Выбор этого транспорта блокируют параметры, которые передаёт само приложение;
подробности и границы проверки приведены ниже.

По решению пользователя разработка начинается с независимой офлайн-проверки
workflow на Go; она не требует завершения интеграции. Подключение и исполнение
остаются отдельным этапом, а не условием готовности команды `validate`.

Предварительные проверки не запускали модель или агентов и не создавали чаты.
Последующая проверка автоматического запуска, выполненная с разрешением через
инструмент выполнения, создала тестовые записи и отправила один запрос модели.
Настройки Codex не менялись, Desktop не перезапускался.

## Первоначально найденные способы подключения

Встроенный JavaScript просмотрен **только для чтения**, без загрузки его как модуля
и без изменения установленного приложения. Источник: `ChatGPT.app/Contents/Resources/app.asar`,
файлы `.vite/build/main-BvHpyFqC.js` и `.vite/build/src-4lLVrYxe.js`.

- `CODEX_APP_SERVER_WS_URL` выбирает WebSocket URL вместо локального процесса.
  Альтернатива в коде — поле `websocket_url` конфигурации хоста.
  При `CODEX_APP_SERVER_FORCE_CLI=1` этот выбор отключается.
- `CODEX_APP_SERVER_USE_LOCAL_DAEMON=1` может подключить локальное приложение
  к стандартному Unix control socket. Код дополнительно проверяет версию daemon,
  отсутствие некоторых overrides, `CODEX_CLI_PATH` и других условий.
  Если условия не выполнены, он возвращается к stdio. Поэтому одна переменная
  окружения ещё не доказывает, что приложение подключилось к общему серверу.

Это наблюдения **для установленной версии**, не документированное обещание
совместимости Desktop. В просмотренных официальных страницах контракт этих
переменных не установлен. Не использовать их как гарантированный production API.

Первоначальный кандидат для теста: приложение и клиент Lawa подключаются к одному
app-server, предпочтительно через локальный Unix socket с ограниченным доступом.
Это отличается от запуска второго независимого сервера рядом с текущим Desktop.
Нужно доказать, что оба клиента видят одни и те же живые чаты и события.
Переключение транспорта потребует согласованного перезапуска; оно может прервать
текущую работу приложения. Нельзя незаметно запускать daemon, менять launch settings
или открывать сетевой listener. Проверка только подключения не требует модели;
создание агентских turn и расход запросов согласуются отдельно.

## Повторная проверка подключения: 2026-08-29

Встроенный CLI по-прежнему имеет версию `0.150.0-alpha.12.2`. Команда
`app-server daemon version` сообщает об отсутствии стандартного control socket.
У процесса сервера приложения нет флага `--listen`; `lsof` не показывает ни
именованного Unix listener, ни слушающего TCP-порта. Это подтверждает отсутствие
доступного общего endpoint в проверенном запуске, а не невозможность интеграции
вообще. Дополнительный сервер не запускался, настройки приложения не менялись.

В тех же файлах установленного `app.asar` проверен порядок выбора транспорта:

- `wH.connect` в `src-4lLVrYxe.js` допускает local daemon только при пустом
  массиве `getConfigOverrides`, помимо остальных условий.
- Для локального приложения `y5` в `main-BvHpyFqC.js` передаёт `getConfigOverrides`,
  вызывающий `JE`. Эта функция возвращает непустой массив: настройку MCP
  `codex_app` либо явное отключение этого MCP при недоступности его компонентов.
  Поэтому данный путь подключения к daemon не выбирается даже с включённым флагом.
- Ветка `CODEX_APP_SERVER_WS_URL` выбирается раньше, но сама не переносит эти
  параметры в отдельно запущенный сервер. Сохранение инструментов приложения,
  профилей доступа и остальных настроек при переключении ещё нужно проверить.

Исходники приложения только прочитаны: их функции не вызывались, приватный IPC,
БД и файлы истории не использовались. Обходить условия через изменение приложения
или отключение его настроек нельзя. Возможный следующий эксперимент — обратимый
мост транспорта, сохраняющий передаваемые Desktop параметры и окружение сервера.
Его работоспособность не подтверждена; нужен отдельно согласованный перезапуск.

Повторная генерация JSON Schema не обнаружила клиентского ID или ключа
идемпотентности в `ThreadStartParams`. Это по-прежнему не позволяет считать
повторный `thread/start` безопасным после потери ответа. Поиск способа достоверного
восстановления связи остаётся обязательным до реализации создания чатов.

Актуальная [документация App Server](https://learn.chatgpt.com/docs/app-server)
описывает Unix/WebSocket транспорт, `thread/start`, `thread/read` и `thread/resume`,
а встроенный CLI помечает команду app-server как экспериментальную. Схема и
документация не заменяют проверку совместимости и видимости чатов в Desktop.
Модели, тестовые чаты и работающие пользовательские задачи эта проверка транспорта
не запускала и не прерывала. Последующая проверка отдельного сервера описана ниже.

## Автоматический запуск через отдельный сервер: 2026-08-29

Поводом стал код локального проекта Focus. Его клиент запускает официальный
`codex app-server --stdio`; контроллер создаёт чат, задаёт название, закрепляет его,
добавляет пустой элемент истории и снимает подписку. Отдельная кнопка открывает
`codex://threads/<id>`, предварительно перезапуская собственный сервер Focus.
Focus не отправляет `turn/start`: его сценарий не подтверждает автоматическое
выполнение команды, работу живого чата в двух процессах или доставку разрешений.

Для проверки использован встроенный CLI `0.150.0-alpha.12.2`, отдельная временная
рабочая папка, `sandbox: read-only` и `approvalPolicy: on-request`. Модель осталась
настроенной пользователем; для короткого теста выбрано `effort: low`. Единственная
команда требовала ответить `LAWA_AUTOSTART_OK` без инструментов и изменения файлов.
Диагностический скрипт и ответы тестовых RPC сохранены вне репозитория; это не
продуктовая реализация и не замена автоматических тестов будущего адаптера.

Подтверждённая последовательность:

1. Запуск своего процесса и обмен `initialize` → `initialized`.
2. `thread/start` с `historyMode: paginated`, сохранение ID и `thread/name/set`.
3. Однократный `turn/start` с текстовым `input`, без ручной отправки в Desktop.
4. Получение `turn/started` и `turn/completed` со статусом `completed`.
5. Чтение созданного ID через инструменты Desktop: задача есть в списке задач,
   история содержит тестовый запрос и ответ `LAWA_AUTOSTART_OK`. Проверен список
   приложения, не визуальное отображение активного диалога и не ввод в нём.
6. Остановка только тестового сервера после окончания turn. Новый сервер выполняет
   `thread/resume`, `thread/read` и `thread/turns/list` для сохранённого ID: тот же
   чат, тот же единственный turn со статусом `completed`, без нового запроса модели.

Первый тест выявил несовместимость Focus и установленной версии: запрос
`thread/metadata/update` с `isPinned: true` вернул `-32600` и сообщение
`thread metadata update must include at least one field`. Поля `isPinned` нет
и в сгенерированной схеме этой версии; закрепление не требуется для видимости.
При остановке сервера до первого turn у созданного пустого чата не оказалось
rollout: `thread/resume` вернул `no rollout found for thread id`. Его ID сохранён,
модель в нём не запускалась; запись не удалена. После этой явно неуспешной
диагностики отдельно согласован новый тест без закрепления, описанный выше.
Это не алгоритм автоматического повтора для Lawa: при неизвестном результате
создания рабочей задачи новый чат по-прежнему запрещён.

Desktop прочитал завершённую историю со статусом thread `notLoaded`, тогда как
сервер-исполнитель сообщил `idle`. Следовательно, чтение общей истории не означает
подписку на живую работу другого сервера. Успех нужно определять по актуальному
turn, а не по `idle`/`notLoaded`; маршрутизация запросов пользователя ещё требует
проверки. Останавливать свой stdio-сервер во время работы, как это делает Focus
при открытии чата, нельзя считать безопасной передачей выполнения в Desktop.

Прямой запуск скилла описан в [официальной документации](https://learn.chatgpt.com/docs/app-server#start-a-turn-invoke-a-skill):
`turn/start` принимает текст с `$<skill>` и отдельный элемент `type: skill` с именем
и путём. Реальный тест выше проверяет обычный текст, не исполнение скилла.

## Что установлено по схеме встроенной версии

Схема получена командой, которая не запускает агентские задачи:

```sh
/Applications/ChatGPT.app/Contents/Resources/codex app-server generate-json-schema --experimental --out <temporary-directory>
```

- `ThreadStartParams` содержит `cwd`, `developerInstructions`, `config`, `permissions`;
  `ThreadResumeParams` принимает сохранённый `threadId`.
- `permissions` — имя профиля, несовместимое с одновременной передачей `sandbox`.
- `ThreadStatus`: `notLoaded`, `idle`, `systemError`, `active`.
- `TurnStatus`: `completed`, `interrupted`, `failed`, `inProgress`.
- В просмотренном `ThreadStartParams` нет клиентского ID чата или ключа идемпотентности.
  Это не доказывает отсутствие другого механизма восстановления связи.

Следствие для будущей реализации: `idle` и `notLoaded` нельзя считать успехом.
Нужно сопоставлять текущую работу и её `turnId`, учитывать ожидание подтверждения,
ошибку и ручное продолжение. Устаревший успех предыдущего turn не должен запускать
зависимости, если актуальная работа ещё выполняется. Это проектное требование,
а не уже проверенный алгоритм.

Официальная документация описывает создание, чтение и продолжение thread, события
работы и транспорты stdio, WebSocket и Unix socket. Но запуск отдельного сервера
сам по себе не подтверждает управление теми же живыми чатами Desktop App.
WebSocket помечен экспериментальным; гарантию production-интеграции из этого
описания вывести нельзя. См. [App Server](https://learn.chatgpt.com/docs/app-server).

## Проверка прав памяти

По [документации Permissions](https://learn.chatgpt.com/docs/permissions)
профили могут задавать точные пути и разделять чтение и запись. Они не заменяют
отдельные ограничения MCP, браузера и разрешённых повышений прав.
Обещать абсолютную защиту памяти лишь на основании промпта или chmod нельзя:
координатор и агент работают от одного пользователя ОС.

Первая команда с точечным ключом `-c` отклонила конфигурацию с ошибкой
`FilesystemPermissionToml`. Повтор с передачей **всего профиля одним TOML-значением**
успешен на той же версии и тех же фикстурах. Следовательно, это не подтверждённая
несовместимость permission profiles; проблема была в форме передачи overrides,
содержащих путь с точками. Внутренний разбор точечного ключа не исследовался.

Рабочая форма; путь нужно заменить на заранее созданный одноразовый файл:

```sh
/Applications/ChatGPT.app/Contents/Resources/codex sandbox \
  --include-managed-config -P lawa-probe \
  -c 'permissions.lawa-probe={extends=":read-only",filesystem={"<absolute-own-memory-path>"="write"}}' \
  -- node <temporary-check-script>
```

Диагностический скрипт намеренно не включён в коммит по просьбе пользователя;
на машине исследования он сохранён локально и игнорируется Git. Это не относится
к unit-тестам Go-приложения: они входят в исходники и проверяют продуктовый код.

Локальный тест создаёт свежие приватные фикстуры в системной временной папке, использует
`:workspace`, сужает права папки запуска до чтения и разрешает запись только
в тестовый проект и собственный файл памяти. Все параметры действуют лишь
для дочерней команды; `--include-managed-config` сохраняет managed restrictions.
Фикстуры остаются по напечатанному пути для проверки, ничего пользовательского
тест не удаляет. Node.js нужен только диагностике, не является требованием Lawa.

Подтверждено на `0.150.0-alpha.12.2`, macOS:

| Операция | Результат |
|---|---|
| Создать результат в тестовом проекте | Разрешено |
| Прочитать чужую память | Разрешено |
| Дополнить и полностью перезаписать собственную память | Разрешено |
| Изменить, удалить, переименовать чужую память, workflow, task или meta | Запрещено |
| Создать соседний файл в папке запуска или памяти | Запрещено |

Не проверены Linux, другие инструменты агента, атомарная замена собственного файла,
сохранение профиля после ручного продолжения и компактификации. Редакторы, создающие
временный файл рядом с памятью, не совместимы с проверенным запретом соседних файлов.
Не переносить результат теста sandbox на MCP или разрешённое повышение прав.

## Что остаётся до готовности полной интеграции

1. Для выбранного отдельного сервера подтвердить жизнь активных задач после выхода
   Lawa, отображение текущей работы и безопасное ручное продолжение в Desktop.
   Чтение сохранённой истории не подменяет проверку владения живой задачей.
   Общий endpoint остаётся альтернативой, а не обязательным перезапуском приложения.
2. Проверить применение профиля к реальным агентским инструментам, сохранение
   ограничений после продолжения и такой же тест sandbox на Linux.
3. С отдельным разрешением на тестовые чаты и расход запросов проверить цепочку
   A → B: ошибка/отмена A, ручное продолжение того же чата, успех A и однократный B.
   Подтвердить видимость обоих чатов в приложении.
4. Отключить только клиент Lawa, продолжить A в приложении, подключиться повторно
   по сохранённому ID и проверить статус без нового чата. Подтвердить сохранение
   правил памяти после продолжения и компактификации.
5. Проверить потерю ответа создания чата: как восстановить связь после сбоя между
   ответом сервера и записью `codexThreadId`. При неоднозначности остановиться,
   не создавать чат повторно. Отдельно проверить маршрутизацию запросов разрешений.

До этих проверок нельзя объявлять выполненным интеграционный критерий MVP.
Изменение настроек приложения и его перезапуск не выполнялись. Проверен один
короткий turn; полный сквозной сценарий workflow, ошибки и ручные повторы ещё не
проверены. Нельзя переносить успешную проверку завершённого чата на эти сценарии.
