# Проверка интеграции Lawa с Codex App

Дата: 2026-08-28. Требования: [MVP](../product/1.md).

Это снимок первичного исследования. Последующая реализация отдельного Go-клиента,
координатора, `run`/`resume` и их ограничения описаны в
[контракте клиента](../README.md#контракт-клиента-codex). Общий живой сервер с Desktop
по-прежнему не проверен; исторические выводы ниже относятся к первоначальному тесту.

## Реализованный контур

Lawa запускает официальный app-server по stdio отдельно для каждого нового turn
и операции `thread/read`. `run` проверяет рукопожатие до создания папки запуска,
сохраняет полученный `codexThreadId` до `turn/start` и запускает независимые шаги
параллельно. `resume` читает последний turn сохранённого чата; активная ручная работа
имеет приоритет над прежним терминальным результатом. `completed` открывает зависимости,
`failed` и ожидание пользователя оставляют flow незавершённым, а `interrupted`
получает один новый turn `continue` в том же чате на один вызов `resume`.

Для каждого нового чата Lawa передаёт отдельный профиль: `:workspace` для проекта,
read для папки run и write только для `memory/<свой-threadId>.md`. Профиль задаётся
одним аргументом `-c` без shell и выбирается полем `permissions` в `thread/start`.
Managed restrictions остаются верхней границей и могут сузить эти права.

Сигнал прекращает опрос и новые волны. Для каждого известного `threadId`/`turnId`
отдельный app-server делает `thread/resume` и `turn/interrupt`; исходная stdio-сессия
сохраняет терминальный `interrupted`. Если подтверждение не пришло за пять секунд,
локальная сессия закрывается, а фактический статус проверяется следующим `resume`.
Неоднозначный `Starting` без ID останавливает run: в проверенном протоколе нет клиентского ключа
идемпотентности, позволяющего безопасно создать чат повторно. Автотесты используют
подставной app-server и не расходуют запросы модели.

## Вывод

**Права памяти проверены на macOS. Сквозная интеграция с приложением пока не подтверждена.**
Работающее приложение использует stdio; внешнего listener у этого процесса не найдено.
В установленном коде есть альтернативы подключения к общему серверу, но их проверка
требует отдельного разрешения на изменение запуска и перезапуск приложения.
На момент предварительного исследования это ещё не было работающим адаптером Lawa;
текущая реализация описана выше.

По решению пользователя разработка началась с независимой офлайн-проверки workflow
на Go. Подключение и исполнение были добавлены позже и не изменили контракт `validate`.

Проверка не запускала модель или агентов, не создавала чаты, не меняла настройки
Codex и не запускала дополнительный app-server. Запросы модели не расходовались.

## Найденные способы подключения

Встроенный JavaScript просмотрен **только для чтения**, без загрузки его как модуля
и без изменения установленного приложения. Источник: `ChatGPT.app/Contents/Resources/app.asar`,
файлы `.vite/build/main-BvHpyFqC.js` и `.vite/build/src-4lLVrYxe.js`.

- `CODEX_APP_SERVER_WS_URL` выбирает WebSocket URL вместо локального процесса.
  Альтернатива в коде — поле `websocket_url` конфигурации хоста.
  При `CODEX_APP_SERVER_FORCE_CLI=1` этот выбор отключается.
- `CODEX_APP_SERVER_USE_LOCAL_DAEMON=1` может подключить локальное приложение
  к стандартному Unix control socket. Код дополнительно проверяет версию daemon,
  отсутствие некоторых overrides, `CODEX_CLI_PATH` и других условий.
  Если условия не выполнены, он возвращается к stdio. Поэтому одна переменная
  окружения ещё не доказывает, что приложение подключилось к общему серверу.

Это наблюдения **для установленной версии**, не документированное обещание
совместимости Desktop. В просмотренных официальных страницах контракт этих
переменных не установлен. Не использовать их как гарантированный production API.

Кандидат для следующего теста: приложение и клиент Lawa подключаются к одному
app-server, предпочтительно через локальный Unix socket с ограниченным доступом.
Это отличается от запуска второго независимого сервера рядом с текущим Desktop.
Нужно доказать, что оба клиента видят одни и те же живые чаты и события.
Переключение транспорта потребует согласованного перезапуска; оно может прервать
текущую работу приложения. Нельзя незаметно запускать daemon, менять launch settings
или открывать сетевой listener. Проверка только подключения не требует модели;
создание агентских turn и расход запросов согласуются отдельно.

## Что установлено по схеме встроенной версии

Схема получена командой, которая не запускает агентские задачи:

```sh
/Applications/ChatGPT.app/Contents/Resources/codex app-server generate-json-schema --experimental --out <temporary-directory>
```

- `ThreadStartParams` содержит `cwd`, `developerInstructions`, `config`, `permissions`;
  `ThreadResumeParams` принимает сохранённый `threadId`.
- `permissions` — имя профиля, несовместимое с одновременной передачей `sandbox`.
- `ThreadStatus`: `notLoaded`, `idle`, `systemError`, `active`.
- `TurnStatus`: `completed`, `interrupted`, `failed`, `inProgress`.
- В просмотренном `ThreadStartParams` нет клиентского ID чата или ключа идемпотентности.
  Это не доказывает отсутствие другого механизма восстановления связи.

Этот вывод применён в реализации: `idle` и `notLoaded` сами по себе не считаются успехом.
Нужно сопоставлять текущую работу и её `turnId`, учитывать ожидание подтверждения,
ошибку и ручное продолжение. Устаревший успех предыдущего turn не должен запускать
зависимости, если актуальная работа ещё выполняется. Это проектное требование,
а не уже проверенный алгоритм.

Официальная документация описывает создание, чтение и продолжение thread, события
работы и транспорты stdio, WebSocket и Unix socket. Но запуск отдельного сервера
сам по себе не подтверждает управление теми же живыми чатами Desktop App.
WebSocket помечен экспериментальным; гарантию production-интеграции из этого
описания вывести нельзя. См. [App Server](https://learn.chatgpt.com/docs/app-server).

## Проверка прав памяти

По [документации Permissions](https://learn.chatgpt.com/docs/permissions)
профили могут задавать точные пути и разделять чтение и запись. Они не заменяют
отдельные ограничения MCP, браузера и разрешённых повышений прав.
Обещать абсолютную защиту памяти лишь на основании промпта или chmod нельзя:
координатор и агент работают от одного пользователя ОС.

Первая команда с точечным ключом `-c` отклонила конфигурацию с ошибкой
`FilesystemPermissionToml`. Повтор с передачей **всего профиля одним TOML-значением**
успешен на той же версии и тех же фикстурах. Следовательно, это не подтверждённая
несовместимость permission profiles; проблема была в форме передачи overrides,
содержащих путь с точками. Внутренний разбор точечного ключа не исследовался.

Рабочая форма; путь нужно заменить на заранее созданный одноразовый файл:

```sh
/Applications/ChatGPT.app/Contents/Resources/codex sandbox \
  --include-managed-config -P lawa-probe \
  -c 'permissions.lawa-probe={extends=":read-only",filesystem={"<absolute-own-memory-path>"="write"}}' \
  -- node <temporary-check-script>
```

Диагностический скрипт намеренно не включён в коммит по просьбе пользователя;
на машине исследования он сохранён локально и игнорируется Git. Это не относится
к unit-тестам Go-приложения: они входят в исходники и проверяют продуктовый код.

Локальный тест создаёт свежие приватные фикстуры в системной временной папке, использует
`:workspace`, сужает права папки запуска до чтения и разрешает запись только
в тестовый проект и собственный файл памяти. Все параметры действуют лишь
для дочерней команды; `--include-managed-config` сохраняет managed restrictions.
Фикстуры остаются по напечатанному пути для проверки, ничего пользовательского
тест не удаляет. Node.js нужен только диагностике, не является требованием Lawa.

Подтверждено на `0.150.0-alpha.12.2`, macOS:

| Операция | Результат |
|---|---|
| Создать результат в тестовом проекте | Разрешено |
| Прочитать чужую память | Разрешено |
| Дополнить и полностью перезаписать собственную память | Разрешено |
| Изменить, удалить, переименовать чужую память, workflow, task или meta | Запрещено |
| Создать соседний файл в папке запуска или памяти | Запрещено |

Не проверены Linux, другие инструменты агента, атомарная замена собственного файла,
сохранение профиля после ручного продолжения и компактификации. Редакторы, создающие
временный файл рядом с памятью, не совместимы с проверенным запретом соседних файлов.
Не переносить результат теста sandbox на MCP или разрешённое повышение прав.

## Что требуется для ручной production-проверки

1. С отдельным разрешением подготовить обратимый запуск Desktop с общим локальным
   сервером и проверить подключение двух клиентов без вызова модели.
   Не подменять это чтением rollout-файлов или инструментами только текущего чата.
2. Проверить применение профиля к реальным агентским инструментам, сохранение
   ограничений после продолжения и такой же тест sandbox на Linux.
3. С отдельным разрешением на тестовые чаты и расход запросов проверить цепочку
   A → B: ошибка/отмена A, ручное продолжение того же чата, успех A и однократный B.
   Подтвердить видимость обоих чатов в приложении.
4. Отключить только клиент Lawa, продолжить A в приложении, подключиться повторно
   по сохранённому ID и проверить статус без нового чата. Подтвердить сохранение
   правил памяти после продолжения и компактификации.
5. Проверить потерю ответа создания чата: как восстановить связь после сбоя между
   ответом сервера и записью `codexThreadId`. При неоднозначности остановиться,
   не создавать чат повторно. Отдельно проверить маршрутизацию запросов разрешений.

До этих проверок нельзя объявлять выполненным интеграционный критерий MVP.
Изменение настроек приложения, его перезапуск и платный сквозной тест в рамках
предварительной проверки не выполнялись.
