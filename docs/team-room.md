# Команда офиса

Новые командные заказы создаются через CLI с `meta.order.team=true`. Только такие корневые
заказы исполняет `internal/teamruntime.Engine`, живущий в `lawa serve`.
Старый coordinator отклоняет их `Execute` и `Reply`. Фиксированные workflow и
CLI-заказы сохраняют прежнюю логику. Handler без Serve не запускает модель.

## Состав команды через JSON

Состав, личности и внешность задаются при запуске Lawa:

```sh
lawa serve --team-config examples/office/team.json \
  --cwd /absolute/project --task-file goal.md
```

Команда создаёт один заказ, печатает `runId` и ссылку `/office?run=…`, затем
запускает Босса. Повторный запуск с целью создаёт новый заказ. Для продолжения
сохранённых команд запускайте `lawa serve --root <тот-же-root>` без цели и конфига.
`--task` — альтернатива `--task-file`; вместе они запрещены. Для нового заказа
обязателен `--cwd`. Конфиг без новой цели не применяется к существующим комнатам.
Сначала проверяется JSON, затем открывается порт, и только потом сохраняется
заказ: занятый порт не оставляет заказ, который мог бы запустить другой сервер.

В UI нет создания заказов, импорта конфига или изменения личностей/внешности.
Телефон позволяет открыть существующий заказ и читать его состояние; общение
с уже работающей командой через чат сохраняется. Галерея — только справочник ID.
Готовый пример с Боссом, Разработчиком и Дизайнером —
[`examples/office/team.json`](../examples/office/team.json):

```json
{
  "characters": {
    "designer": {
      "name": "Дизайнер",
      "history": "Продуктовый дизайнер с опытом сложных интерфейсов.",
      "instructions": "Исследуй сценарий, предложи интерфейс и проверь доступность.",
      "avatar": "pixel-designer"
    }
  }
}
```

Ключ `designer` — рабочий ID и адрес `@designer`. `name`, `history` и
`instructions` обязательны. Необязательный `avatar` — ID образа из галереи,
общий для стола и аватарки. Профессия картинки не задаёт поведение личности.
Неизвестный безопасный ID внешности показывает стандартного сотрудника.
ID содержит 1–64 символа: строчные латинские буквы, цифры, `_`, `-`, начинается
с буквы. `human` и `system` зарезервированы. Максимум — 20 личностей с Боссом.

Без файла используется прежняя команда Босс + Разработчик. Явный каталог
полностью задаёт доступных сотрудников; отсутствующий `boss` добавляется
автоматически, остальные не добавляются. Поэтому `{"characters":{}}` — один Босс.
В офисе сначала появляется только Босс, даже если каталог содержит 20 личностей.
Он видит описания всех доступных коллег и приглашает нужных через `team_summon`.
Файл конфига содержит только `characters`, не граф `steps`; обычные workflow
сохраняют прежний контракт личностей и способ запуска.

HTTP API создания команды отсутствует: `POST /api/teams` возвращает 405.
CLI проверяет весь каталог до запуска, включая неиспользуемые личности.
`workflow.json.characters` хранит исходную постановку; `team.json.room.catalog`
получает её неизменяемый снимок для командного runtime. Активные сотрудники живут
в `room.actors`. Для каждого turn prompt собирается из описания личности,
правил команды, текущей цели и адресных сообщений. Полномочия инструментов
проверяет сервер: инструкции личности не дают права приглашать коллег или
напрямую отвечать Челу в обход Босса.

Изменение файла влияет только на следующий заказ. Каталог существующего заказа
не редактируется: Codex закрепляет набор dynamic tools при создании thread.
Старые комнаты без `room.catalog` читаются как Босс + Разработчик; обычный GET
ничего не мигрирует на диске. Следующая запись сохраняет совместимый каталог.

## Сообщения и полномочия

`team.json` содержит дословную цель, реестр участников, append-only сообщения и
`room.actors`. Изначально единственный сотрудник — `boss`; `human` не агент.
Постановка цели записывает короткое первое обращение `@boss`, без обрезки pin.

Только ведущий `@id` приглашённого сотрудника или `@human` задаёт `to`. Цитата или упоминание
в середине текста не будит адресата. Одно сообщение — один адресат, до 50 слов.
Автор dynamic tool захвачен сервером; модель не может передать чужое авторство.
`team_summon` доступен только Боссу и только для сотрудников каталога. Участник, рабочее
место и техническая реплика добавляются атомарно и идемпотентно.

Агент пишет только во время своего адресного хода. Ответ разрешён отправителю
текущей порции (`replyTo`, полный набор — `replyToIds`). Исключения: Босс делегирует сотрудникам/уточняет у Чела;
Сотрудник отвечает на прямой запрос Чела через Босса. Прямой `сотрудник → human`
отклоняется сервером. Решение «не могу сам» у Босса задаётся инструкцией, а не
формальной проверкой текста. `team_read` даёт всю общую историю. Собственный final
не копируется в чат: результат нужно явно отправить `team_post`.

## Таймер, память и доставка

Первый ход Босса готов немедленно. Новая личность сотрудника начинает личный
пятиминутный таймер при приглашении. После завершения хода таймер отсчитывается
заново. Обращение Чела будит адресата сразу; ответ сотрудника на него сразу будит Босса.
Если сотрудник занят, обращение сохраняется до конца текущего хода и затем
обрабатывается без пятиминутной задержки.
Пустая проверка продвигает курсор и таймер, не вызывает LLM. Статус monitoring
означает, что Босс делегировал работу; это ожидание без активной модели.

Один Codex thread хранит историю личности на один заказ. `Cursor` — число
обработанных сообщений. `Delivery` фиксирует их ID и верхнюю границу `End` до
запуска сети; входящие во время turn будут обработаны следующей порцией.
После подтверждённого завершения Cursor становится End. ThreadID и TurnID
сохраняются callback-ами до дальнейшего протокола. Перед Continue проверяется,
что предыдущий собственный turn завершён и никто не продолжил thread вручную.

`team.lock` защищает только короткие правки JSON; сеть под ним запрещена.
`team-<id>.lock` удерживаются весь ход или восстановление.
Один общий capacity pool ограничивает одновременно активные новые turn с
фиксированными workflow. Ожидающий сотрудник слот не занимает. Файлы сохраняются
атомарно с fsync. Повтор tool-call с тем же ID возвращает прежнее сообщение.

## Сбои и границы первого варианта

После падения процесса Engine наблюдает именно `Delivery.TurnID`, а не старый
`actor.TurnID`. Завершение подтверждает доставку; активный turn наблюдается через
одну сессию. Неизвестный или несовпавший ID блокирует повтор. При остановке сервера
его исходная сессия получает interrupt с ограниченным временем ожидания.

Телефон показывает ошибку. Retry возможен только если клиент подтвердил, что
создание/отправка не предпринимались. После неоднозначной ошибки сначала требуется
ручная проверка истории Codex; автоматического сброса или кнопки слепого повтора
нет. Незавершённую доставку нельзя удалить через старый dashboard; занятый actor
защищён отдельной блокировкой и не останавливается по PID прежнего coordinator.

Состав команды задаётся каталогом; автоматической смены личностей, сводки
истории или планирования вне сообщений нет. Общие правила задаёт `command`
runtime; персональное поведение — сохранённые `history` и `instructions`. Техническое состояние старого графа заказа не является состоянием
команды: его источник — room.actors и `/office`.

Проверки: `internal/teamruntime/engine_test.go` — полный цикл с управляемыми
часами, реальными файлами и fake Codex; `internal/dashboard/team_test.go` — HTTP;
`ui/src/pages/Office.test.tsx`, `TeamPhone.test.tsx` — сцена и чат. Эти тесты не
оценивают качество решений реальной модели.

## Плеер истории

В `/office` плеер под сценой управляет общим курсором времени. В телефоне
плеера нет; телефон показывает выбранный кадр и позволяет вернуться в live.
Доступны перемотка, соседние события, воспроизведение 1×/5×/20×/60× и возврат
«К текущему». Исторический кадр одновременно задаёт состав офиса, статусы,
публичные облачка и видимый префикс чата. В Header телефона метка «История» и кнопка возврата в текущий чат.
Поле отправки доступно всегда: сообщение уходит в текущий чат и возвращает live.
Retry ошибок сотрудников доступен только в текущем состоянии.
Просмотр локален: runtime продолжает работать, пауза плеера не останавливает агентов.
Новые сообщения не сдвигают выбранный курсор; смена заказа возвращает live.

`team.json.history` хранит `recordedFrom`, `recovered` и `frames`. Кадр содержит
`at`, `goal`, `messageCount` и копию публичных полей акторов; thread ID, delivery и
внутренние рассуждения в него не попадают. `UpdateTeam` сохраняет изменённый
кадр атомарно с сообщениями. Правки служебных полей без видимого изменения не
создают дубликаты. Отступление системных часов не нарушает порядок кадров.
Для старого файла первый изменяющий вызов сохраняет исходное состояние перед
правкой: оно не выдаётся за состояние начала заказа.

У старых заказов кнопка «Восстановить из Codex» вызывает same-origin
`POST /api/teams/{run}/history/recover`. Read-only `thread/read` читает только
сохранённые thread ID, проверяет проект и соединяет начало/конец ходов с репликами.
Никакие ходы не запускаются и рабочие курсоры не меняются. Нативные кадры после
`recordedFrom` имеют приоритет; повторный импорт идемпотентен. Сеть выполняется
вне `team.lock`, после неё повторно проверяются ID сотрудников.

Ранняя история имеет ограниченную точность: Codex даёт секунды для границ ходов,
а промежуточные действия ранее не сохранялись. Облачка восстанавливаются из
публичных сообщений; во время известного хода без реплики — «Работает над
поручением». Неизвестное состояние помечается «Статус не записан». Происхождение
записано в `history.recovered`; служебной подписи в UI нет. Новые публичные действия
записываются непосредственно при изменении состояния.

Проверки плеера: `team_history_test.go` в runstore, `history_test.go` в
teamruntime/codex и `ui/src/components/TeamPlayer.test.tsx` — согласованность
кадров, отсутствие будущих данных, read-only импорт и возврат из истории в live.

Пустые тики личного таймера не создают кадры. `team_read` использует
`ReadTeamForAgent` и исключает `history`, чтобы плеер не увеличивал контекст LLM.

## Поручения и ответственность Босса

`room.tasks` хранит обязательства, автоматически создаваемые каждым сообщением
Босса или Чела приглашённому сотруднику. ID поручения равен ID сообщения.
Завершение Codex turn и ответ в чате не закрывают поручение: вопрос, промежуточный
отчёт и готовый результат различает Босс, проверяя фактические артефакты.

Босс вызывает `team_accept` с `task_ids`, `result_id` сообщения сотрудника и
`evidence` — описанием выполненной проверки до 40 слов. Runtime проверяет роль,
получение поручения, порядок сообщений, завершение хода и отсутствие блокировки.
Приёмка атомарно сохраняет описание проверки и событие в общем чате.
Один отчёт может покрывать несколько поручений одного сотрудника, только по
явному решению Босса. При замечаниях он выдаёт уточняющее поручение; исходное
остаётся открытым до приёмки исправленного результата. Сервер проверяет эти
условия, но не подменяет смысловую оценку результата моделью Босса.

Любое непринятое поручение запрещает `team_complete`, даже если сотрудник ещё
не дождался своего таймера. У старых активных комнат реестр восстанавливается
из сообщений после последнего достижения цели без записи при GET. Завершённые
исторические цели не открываются задним числом. Конфиг и правила обычных
workflow не меняются. Реестр и приёмки принадлежат командному заказу.

Сбой сотрудника или завершение без сообщения Боссу создают системный `@boss`
в чате и немедленно готовят следующий ход Босса. Он может запросить отчёт об уже
выполненной работе или воспользоваться `team_retry` с ID сотрудника, если
отправка доказанно не предпринималась. Неоднозначную доставку повторять нельзя.
Босс может сообщить Челу статус, препятствие или уточнить вопрос до ответа
сотрудника. Это не принимает поручение и не разрешает завершить цель. Повтор
ошибки одной попытки не дублируется, новая попытка после retry создаёт новое
уведомление.

Если Босс получил отчёт до `turn/completed` коллеги, приёмка пока запрещена.
После завершения коллеги дополнительный адресный сигнал возвращает Босса к
проверке. В обычном случае действует исходный пятиминутный таймер сообщения.
Старые Codex thread используют те же операции через `team_post`:
`/accept {"task_ids":["…"],"result_id":"…","evidence":"…"}` и `/retry developer`.

Проверки в `internal/teamruntime/responsibility_test.go` покрывают раннее
закрытие, явную приёмку, устаревший отчёт, права, идемпотентность, сбои,
отсутствие отчёта, повторный сбой, гонку приёмки и совместимость старых комнат.

## Достижение цели

Только Босс во время своего поручения вызывает `team_complete` с итогом
`@human` до 50 слов: что готово, где результат и как проверено. Это явное
решение, а не распознавание фразы «готово» в переписке. Codex фиксирует tools
при создании thread, поэтому старый Босс использует `team_post` с командой
`/complete @human <итог>`. Runtime обрабатывает её тем же методом и убирает
командный префикс из опубликованного текста; авторство по-прежнему серверное.

`CompleteTeam` под общей блокировкой записывает `room.achievedAt`, событие
`achievement` и финальную реплику Босса Челу последней. Повтор того же call ID
возвращает прежний финал. До решения нужно дождаться завершения turn остальных
сотрудников: активная или неоднозначная доставка коллеги запрещает закрытие.
Это не позволяет лишить выполняющуюся работу владельца или скрыть её результат.

После достижения все `nextCheck` обнуляются; сотрудники спят до нового обращения
Чела. Он всегда может написать в чат. Сообщение без тега оставляет цель достигнутой.
`@boss` возобновляет Босса. `@id` любого сотрудника возобновляет его и Босса: сервер сохраняет
`notifyBoss`, Босс получает копию обращения и ждёт результат сотрудника. При этом он может
общаться с Челом, не выдавая неполученный результат за проверенный. Сообщение
Босса не закрывает поручение: достижение по-прежнему требует явной приёмки.
После повторного запроса отчёта приёмка связывает результат с исходным поручением;
совпадение replyTo с первоначальным вопросом Чела для отправки сообщения не нужно.
Сотрудник отвечает Челу только через Босса.
Повтор отправки не создаёт второго события возобновления. Неоднозначная старая
доставка остаётся заблокированной: сообщение не является разрешением её повторить.
Свой уже выполняющийся turn Босс заканчивает обычным final. После сбоя runtime
восстанавливает его доставку через Observer; пришедшие в это время новые
обращения сохраняются для следующего хода. Поздние уведомления активности не меняют облачко завершённой цели.

Pin, событие в чате и облачко Босса получают зелёную галочку. `achievedAt` входит
в кадры плеера, поэтому до времени достижения галочек нет. Конец шкалы
завершённой цели фиксирован. Проверки `completion_test.go` покрывают права,
повторы, активного коллегу, остановку таймеров и совместимость старого tool.

Кнопки адресатов над полем ввода расположены в одну горизонтально прокручиваемую
строку без полосы прокрутки. Статус показывает цветная точка, отсчёт до проверки —
лейбл в углу кнопки. У работающих, заблокированных и завершивших работу сотрудников
таймер скрыт. Подсказка об обязательном теге находится под полем ввода, справа от счётчика слов.
Кнопка PaperPlane расположена внутри поля. Начальный `@` открывает список текущих
сотрудников с аватарами: поиск по имени и ID, стрелки вверх/вниз, выбор через Enter
или клик. Escape закрывает список; выбор заменяет адрес, сохраняя текст черновика.
При просмотре истории адресаты берутся из текущего состава команды. Полный
начальный `@id` существующего сотрудника подсвечивается в черновике цветом
упоминаний чата; неизвестные и незавершённые ID остаются обычным текстом.

Телефон — немодальное плавающее окно без затемнения и блокировки офиса.
Компактная верхняя панель объединяет узкий остров камеры с объективом, название,
статус истории и кнопки. Вся свободная область панели служит ручкой
перетаскивания, нижний правый угол — ручкой размера. Короткая закруглённая линия толщиной 2,5 px
расположена снаружи телефона с зазором 6 px от рамки. Экран обрезает содержимое отдельно от рамки,
поэтому ручка ресайза не перекрывается. Три точки под камерой обозначают перетаскивание.
Обе ручки видны постоянно, без анимации; длинной полосы снизу нет.
На точках и ручке ресайза доступны стрелки (Shift ускоряет шаг). Окно остаётся в границах
экрана, включая уменьшение viewport. Клик снаружи его не закрывает; Escape внутри
телефона и крестик закрывают. Позиция и размер сохраняются до закрытия окна.

## Новая цель в том же чате

Босс различает вопрос и новую постановку. Для новой цели он вызывает
`team_set_goal`; старый thread — `team_post` с `/goal <цель>`. Только Босс во время
активного поручения может обновить pin. Событие `goal_updated` хранит новую цель,
кадры сохраняют её версию; перемотка до обновления показывает старую. Исходный
`meta.task` сохраняется для аудита. Обычный вопрос не меняет закреплённую цель.
Pin закреплён внутри области переписки поверх сообщений. В компактном виде
видны две строки; вся карточка раскрывает и сворачивает полный текст. Непрозрачная
подложка закрывает сообщения сверху и по бокам карточки, без дополнительной полосы
снизу; нижний край скруглён, лёгкая тень отделяет пин от сообщений. Отдельная
кнопка копирует исходную цель и не меняет раскрытие. Сообщения рендерятся как
Markdown/GFM без исполнения HTML и автоматической загрузки изображений.
Абсолютные пути, файловые Markdown-ссылки и пути в inline code открываются
через `vscode://file`; требуется установленный обработчик VS Code. Пути с
пробелами оформляются ссылкой или inline code. Командные URL VS Code запрещены.

`followup_test.go` проверяет возобновление, ожидание ответа коллеги, повтор
старого завершения, обращение во время завершающего хода и историю целей.

## Внешность сотрудников

Отдельная кнопка «Галерея персонажей» открывает справочник всех 42 образов
(40 новых и два исходных). У каждой карточки есть стабильный ID внешности и
кнопка его копирования; поиск работает по ID, имени и профессии. Галерея не
меняет внешность сотрудников и доступна без заказа. ID образа отличается от
рабочего @id агента. В конфиге команды этот ID задаётся в `characters.<id>.avatar`.

Внешность берётся из сохранённого `characters.<id>.avatar`: один спрайт
используется для стола в комнате и лица в чате, включая подсказки адресатов.
Все наблюдатели видят один образ. Прежние настройки внешности в `localStorage`
больше не читаются; настройки темы и положения телефона остаются локальными.

Реестр находится в `ui/src/assets/office/characters/catalog.json`, изображения
и промпт генерации — рядом. Профессия в реестре описывает художественный образ,
а не ограничивает его использование. Исходные Босс и Разработчик остаются
стандартными образами и не входят в эти 40 вариантов.

Проверки конфигурируемого состава: `catalog_test.go` — приглашение Дизайнера,
персональный prompt, таймер, возобновление thread и relay через Босса;
`cmd/lawa/office_test.go` — флаги, JSON, создание при старте и отсутствие
повторного создания без цели; `TestTeamAPI` — запрет HTTP-создания;
`Office.test.tsx` — произвольный ID, образ и отсутствие настроек в UI.
