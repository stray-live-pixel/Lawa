# Статический анализ Lawa

Одна команда собирает измерения и формальный статус проекта. Отчёт не исправляет
исходники и не заменяет ревью, тесты или проверку поведения после сбоев.

## Запуск

Нужны Python 3.9+, Git, версия Go из `go.mod`, Node.js из `ui/.nvmrc` и cloc
(`brew install cloc` на macOS, `sudo apt install cloc` на Debian/Ubuntu).
Первый запуск устанавливает закреплённые версии инструментов:

```sh
python3 scripts/analyze.py --install
```

Установка пишет только в `bin/analysis/`, `tools/analysis/node_modules/`,
`ui/node_modules/` и штатные кеши Go/npm. `npm ci` восстанавливает зависимости
по lock-файлам; `go.mod`, `go.sum` и npm-манифесты приложения не обновляются.
Анализаторы UI установлены отдельно от приложения. Их зависимости не попадают
в сборку UI и не учитываются в метриках размера.

Дальше достаточно:

```sh
python3 scripts/analyze.py
```

Можно вызвать скрипт по абсолютному пути из любой директории. Для запуска нужен
интернет: govulncheck и npm audit обращаются к актуальным базам уязвимостей.
Если запрос или инструмент не сработал, отчёт получает `ERROR`, а не нулевую
метрику. Инструменты могут писать в свои кеши; исходники остаются неизменными.

## Результат и статусы

Каждый запуск создаёт новую папку `reports/analysis/<UTC-дата>/`:

- `report.md` — таблица результатов, пороги и ссылки на диагностику.
- `report.json` — те же метрики, версии, команды, commit, состояние рабочей папки,
  хеш исходников и распределение замечаний по правилам.
- `raw/` — исходные JSON-отчёты, stdout и stderr каждого инструмента.

Markdown и терминал разделены на **GO**, **UI**, **NPM** и **Общее**. У каждого
раздела свой статус; размер Go/UI указан рядом с его метриками. В JSON принадлежность
метрики к разделу хранится в `policy.metrics.<ключ>.group`.

`--output <новая-папка>` задаёт другой путь. Существующий каталог не перезаписывается.
Отчёты и установленные анализаторы исключены из Git.
Все запуски сохраняются локально без автоматической очистки. В GitHub они не
отправляются: для долговременного хранения или переноса нужно сохранить всю папку
запуска вместе с `raw/`. Старый JSON используют через `--compare`, а конкретные
места для улучшений смотрят в подробных диагностиках по файлам и строкам.

| Статус | Значение |
|---|---|
| PASS | Все настроенные проверки завершились, численные пороги соблюдены. |
| WARN | Есть рекомендации: например, сложные функции или неиспользуемые экспорты. |
| FAIL | Нарушен хотя бы один обязательный порог. |
| ERROR | Проверка не завершилась, формат отчёта неизвестен либо код изменился во время анализа. |

Приоритет: `ERROR`, затем `FAIL`, затем `WARN`, затем `PASS`.
Обычный запуск возвращает `0`, если полный отчёт получен, даже при `FAIL`;
`2` означает неполный анализ. Для автоматического контроля:

```sh
python3 scripts/analyze.py --check
```

С `--check` статус `FAIL` возвращает `1`; `WARN` по-прежнему возвращает `0`.
Так можно сначала собрать исходное состояние проекта, а затем включить
обязательные ограничения в CI. Пороги не подгоняются под текущие нарушения.

## Методика

Численные пороги задаёт [policy.json](../tools/analysis/policy.json).
Правила инструментов лежат рядом. Это политика данного проекта, а не
общепринятая оценка качества или доказательство наличия бага.

| Измерение | Инструмент и область | Порог |
|---|---|---|
| Размер | cloc; собственные Go, TS/TSX, CSS и HTML без тестов, зависимостей и сборок | Информация, без PASS/FAIL |
| Замечания Go | golangci-lint: govet, staticcheck, errcheck, ineffassign, unused; `cmd`, `internal`, `assets`, без тестов | FAIL при числе >0 |
| Сложность Go | gocyclo и gocognit; сообщения для функций со значением >15 | WARN при числе сообщений >0 |
| Замечания UI | ESLint, typescript-eslint с типами, правила React Hooks | Ошибки: FAIL >0; предупреждения: WARN >0 |
| Сложность UI | ESLint complexity; число функций со значением >15 | WARN >0 |
| Типы UI | Собственный `tsc` приложения, весь `ui/tsconfig.json`, включая тесты | FAIL при числе ошибок >0 |
| Неиспользуемый код | Knip в production-режиме: файлы, экспорты, типы, зависимости и другие категории замечаний | WARN при числе элементов >0 |
| Дублирование | jscpd, режим weak без комментариев; блоки от 10 строк и 70 токенов | WARN >5%, FAIL >10% |
| Связи UI | dependency-cruiser от `src/main.tsx`, включая динамические импорты; циклы и неразрешимые импорты | FAIL при числе нарушений >0 |
| Безопасность Go | govulncheck без тестов: уникальные OSV с вызываемым уязвимым символом | FAIL >0 |
| Безопасность npm | npm audit по lock-файлу UI, включая devDependencies сборки и тестов | high/critical: FAIL >0; остальные: WARN >0 |

npm audit считает уязвимые пакеты по `metadata.vulnerabilities`, а не уникальные CVE.

Одна Go-функция может породить два сообщения сложности: цикломатическая
считает ветвления, когнитивная дополнительно учитывает структуру и вложенность.
В отчёте указано число сообщений, а не число уникальных сложных функций.
ESLint complexity вынесен из остальных warning, чтобы не считать его дважды.

jscpd считает долю по собственным строкам, а не по строкам кода cloc. Встроенные
языковые фрагменты могут учитываться отдельно. Поэтому число его источников
может отличаться от числа файлов cloc. Стандартные ограничения jscpd на размер
файла переопределены по фактической выборке: крупные исходники не пропускаются.

Knip исключает тесты: экспорт, используемый только тестом, может стать замечанием.
Это повод проверить необходимость публичного экспорта, а не автоматически
удалять функцию. Суффикс `!` у entry/project в конфиге необходим для production-режима.
Граф импортов учитывает `package.json exports`, как сборка Vite.

Для typescript-eslint закреплён совместимый TypeScript 6.0.3: его заявленная
поддержка пока не включает TypeScript 7 приложения. Это ограничение линтера;
отдельный запуск реального `tsc` приложения обязателен и не заменён этой версией.
Отчёт хранит версии анализаторов; npm-версии закреплены отдельным lock-файлом,
Go-версии — в policy.json. Версия cloc берётся из среды и записывается в отчёт.

## Сравнение запусков

```sh
python3 scripts/analyze.py --compare reports/analysis/<предыдущая-дата>/report.json
```

Колонка `Δ` показывает изменение каждой формальной метрики. Для всех этих
метрик меньше — лучше с точки зрения выбранного правила; это не предписание
удалять код или упрощать его любой ценой.

Сравнение разрешено только для полных отчётов с одинаковыми версиями инструментов,
платформой, настройками и кодом счётчика. Несопоставимые отчёты дают `ERROR`.
Базы уязвимостей меняются независимо от проекта, поэтому разницу их показателей
нужно проверять по исходным диагностикам. Автоматический checkout другой ветки
не выполняется: исходное состояние получают отдельным запуском в нужной ветке.

## Проверка инструментов

После установки:

```sh
python3 -B -m unittest discover -s scripts -p 'test_*.py'
```

Тесты проверяют границы порогов, сбои процессов, неполные JSON-отчёты,
дедупликацию уязвимостей и сопоставимость запусков. Реальные Knip, jscpd и
dependency-cruiser запускаются на маленьких временных проектах: это защищает
production-входы, анализ больших файлов и разрешение npm exports.

Документация инструментов: [golangci-lint](https://golangci-lint.run/docs/linters/),
[typescript-eslint](https://typescript-eslint.io/getting-started/typed-linting/),
[React Hooks](https://react.dev/reference/eslint-plugin-react-hooks),
[Knip](https://knip.dev/features/production-mode),
[jscpd](https://github.com/kucherenko/jscpd),
[dependency-cruiser](https://github.com/sverweij/dependency-cruiser),
[govulncheck](https://go.dev/doc/tutorial/govulncheck),
[npm audit](https://docs.npmjs.com/cli/v11/commands/npm-audit/).
