# Lawa: MVP

## Назначение и запуск

Lawa — Go-утилита для выполнения JSON-workflow из кубиков — задач для AI-агента. Независимые кубики запускаются параллельно. Для первого выпуска предлагаются macOS и Linux и один исполнитель — Codex; модель, доступ и права настраиваются в нём. Утилита должна создавать thread в приложении Codex, чтобы за работой агента можно было следить в Codex App.

### Запуск из чата Codex

Workflow запускается для реализации уже сформулированной задачи. Основной интерфейс пользователя — отдельный чат-инициатор в Codex, а не терминал Lawa.

1. Пользователь создаёт новый чат в Codex и вместе с агентом прорабатывает задачу.
2. В чате появляется финальное понятное описание того, что нужно сделать.
3. Пользователь вызывает скилл `/lawa <название-workflow> [комментарий]`. Этот вызов — явное указание запустить выбранный workflow для обсуждённой задачи.
4. Агент берёт финальное описание задачи и комментарий, выбирает workflow по названию и запускает Lawa в рабочей папке проекта. Пользователю не нужно вручную собирать команду или копировать постановку в каждый кубик.
5. Агент остаётся в чате-инициаторе, следит за запуском и сообщает существенные изменения статуса: что выполняется, что ждёт зависимостей, где требуется вмешательство и когда работа завершена. Здесь же пользователь может запросить текущий статус или попросить продолжить остановленный запуск через `resume`.

Если задача ещё не сформулирована или выбранный workflow не найден однозначно, агент уточняет недостающее до запуска. Само обсуждение задачи не запускает Lawa.

Чат-инициатор не является кубиком workflow. Он ставит задачу и служит UI управления Lawa; отдельные чаты кубиков выполняют работу. Скилл `lawa` должен быть доступен в Codex. Координацию зависимостей и сохранение состояния выполняет утилита, а агент-инициатор запускает её и объясняет пользователю состояние run.

Финальное описание задачи и комментарий фиксируются как общий вход конкретного запуска и доступны всем его кубикам вместе с их собственными промптами. Полная история чата-инициатора для выполнения не требуется. Последующие сообщения в этом чате не меняют постановку уже запущенного workflow автоматически.

### Команды утилиты

```sh
lawa run <workflow.json> --cwd <project>
lawa resume <run-id>
lawa help
lawa skill
```

`run` создаёт новый запуск workflow, передаёт готовые кубики в Codex App и наблюдает за их чатами. `resume <run-id>` продолжает сохранённый запуск после остановки Lawa. Собственных ограничений параллельности и времени нет; настройки и ограничения Codex остаются в силе.

При запуске через скилл агент также передаёт Lawa постановку задачи, комментарий пользователя и ID чата-инициатора. После запуска он сохраняет в контексте этого чата `runId`, чтобы наблюдать за нужным run и продолжать его без создания нового.

`help` выводит справку по командам и параметрам. `skill` выводит самодостаточную инструкцию для скилла `lawa`: запуск выбранного workflow из чата с готовой задачей, передача постановки и комментария, наблюдение и сообщения о статусе, продолжение через `resume`, поля JSON, зависимости, примеры workflow и правила работы агентов с памятью. Обе команды печатают встроенный текст без запуска агентов и создания файлов; команда `skill` сама не устанавливает скилл в Codex.

## Workflow

Единая схема JSON:

- У workflow обязательны непустой `id` и непустой массив `steps`.
- У кубика обязательны уникальный непустой `id`, `type: agent`, непустой `prompt` и массив `dependsOn`.
- `dependsOn` содержит ID кубиков, успешного завершения которых нужно дождаться.
- Пустой `dependsOn` разрешает старт сразу. Независимые кубики выполняются параллельно.
- Для последовательного выполнения каждый следующий кубик зависит от предыдущего. Порядок элементов в `steps` не влияет на запуск.

Для каждого кубика в конкретном запуске Lawa создаёт один чат. Пользователь может продолжать и перезапускать работу в этом чате вручную, в том числе пока Lawa выключена. До создания задач проверяются JSON, поля, ссылки, уникальность ID, отсутствие циклов, рабочая папка и доступность подключения к Codex App. Некорректный workflow отклоняется целиком.

## Исполнение

`lawa` — координатор workflow, не собственный harness. Вызовы модели, инструменты, контекст агента, разрешения и выполнение задач остаются в Codex App.

Кубики работают автономно: без ручной отправки команды, с выполнением обычных действий
в выданных правах. Запросы дополнительных прав проверяет встроенный агент Codex
(`on-request` + `auto_review`). Sandbox и ограничения организации сохраняются;
Lawa не подтверждает запросы автоматически. Ввод данных и авторизация внешних сервисов
могут потребовать пользователя; это не считается успешным завершением кубика.

Продуктовое решение автора от 2026-08-30: схема workflow намеренно не выбирает
между `read-only` и `workspace-write`. Все кубики получают текущий профиль на базе
`:workspace`: обычные права проекта, чтение служебной папки run и запись только в
собственный файл памяти. Это ожидаемое поведение и для аудитов, и для доработок;
назначение кубика выражается его prompt, а не отдельным режимом доступа в JSON-схеме.
Managed restrictions Codex остаются верхней границей и могут сузить выданные права.
Изменение этого контракта требует нового явного продуктового решения.

- Для каждого готового кубика Lawa один раз создаёт задачу в Codex App и передаёт исходный промпт, общую постановку задачи с комментарием пользователя, `cwd` и инструкцию по работе с памятью. Независимые задачи передаются сразу. Связь кубика с чатом сохраняется в `meta.json`; контекст между кубиками передаётся через память и файлы результатов.
- `lawa` следит за текущей работой в чате, включая ручные продолжения, а не только за первой попыткой. Успех определяется статусом в Codex, не кодом процесса и не текстом ответа. Ожидание подтверждения пользователя не считается успехом; качество результата не проверяется.
- Ошибка или отмена работы в чате не завершают flow. Зависимые кубики остаются в ожидании, независимые продолжаются. Утилита не перезапускает failed-кубик сама и не ограничивает время его ожидания. При явном `resume` только последний статус `interrupted` получает один новый turn `continue` в том же чате.
- Пользователь перезапускает работу в том же чате: ошибка → выполняется → успех. После успеха `lawa` запускает готовые зависимые кубики. Новый чат для повтора не создаётся; повторные события не дублируют запуск следующего кубика.
- Flow успешно завершается, когда все кубики достигли успеха. Ошибки, исправленные вручную, не делают итог неуспешным. Уже запущенные зависимые кубики автоматически не пересчитываются.
- Ctrl+C или SIGTERM прекращают наблюдение и новые запуски и отправляют `turn/interrupt` всем активным turn. Lawa ждёт подтверждённый статус `interrupted` в пределах короткого окна остановки и возвращает `130`/`143`. При следующем `resume` interrupted-чаты получают `continue`; `failed` и `completed` не перезапускаются. Внутренняя ошибка Lawa прекращает новые волны и сохраняет доступные терминальные результаты, не выдавая их за сигнал пользователя.
- Если Codex отказал до попытки `thread/start`, Lawa возвращает кубик в ожидание, сохраняет исходную ошибку и рекомендует агенту повторить тот же run через явный `resume`. Если запрос создания мог уйти, но ID не подтверждён, автоматический повтор запрещён из-за риска дубликата; ошибка должна прямо объяснять это агенту и просить передать пользователю `runId`, ID кубика и диагностику Codex.
- В терминале — ID запуска, кубиков и чатов, текущие статусы и ожидающие кубики; полный вывод — в Codex App. Коды выхода утилиты: `0` — все кубики достигли успеха; `2` — ошибка ввода/интеграции; `130`/`143` — прерывание сигналом. Ошибка кубика сама по себе не завершает утилиту.

Перед реализацией нужно подтвердить интеграцию с Codex App: создание видимых задач, подключение по сохранённым ID, наблюдение за ручными продолжениями и права записи на отдельные файлы памяти. [Codex App Server](https://learn.chatgpt.com/docs/app-server) — отправная точка для проверки. Собственный harness не разрабатывается.

Параллельные кубики не должны одновременно изменять общие файлы результатов. Если нужен завершённый результат коллеги, это задаётся через `dependsOn`. Права на рабочие файлы и память обеспечивает Codex; Lawa не обходит его ограничения, а `cwd` сам по себе не является песочницей.

## Папка запуска и продолжение

Каждый запуск получает уникальный `runId`, каждый кубик в нём — уникальный `threadId` Lawa. Они не меняются при продолжении. `id` из схемы используется в `dependsOn`, ID чата Codex хранится отдельно.

В `~/.light-ai-workflows/<run-id>/` находятся:

- `workflow.json` — неизменяемая копия исходной схемы. Правки исходного файла не влияют на уже созданный run.
- `task.md` — неизменяемая постановка задачи на момент запуска и отдельно обозначенный комментарий пользователя к вызову скилла.
- `meta.json` — `runId`, `cwd`, ID чата-инициатора Codex и связи кубиков: `id` из схемы, `threadId` Lawa, `codexThreadId`, состояние запуска и последний известный статус. До создания чата кубика его `codexThreadId` пустой.
- `memory/<threadId>.md` — память соответствующего агента; отдельный файл на каждый кубик.

Lawa создаёт папку, копию схемы, постановку задачи, метаданные и пустые файлы памяти до запуска агентов. Файлы доступны только владельцу. `workflow.json`, `task.md` и `meta.json` агенты не изменяют; `meta.json` обновляет только Lawa.

Метаданные обновляются атомарно. Намерение создать чат фиксируется до запроса, полученный ID — сразу после ответа. Ошибка сохранения запрещает новые запуски.

`lawa resume <run-id>` читает `workflow.json`, `task.md` и `meta.json`, подключается к сохранённым чатам и обновляет их статусы из Codex. Если последний turn имеет статус `interrupted`, Lawa отправляет в тот же чат один новый turn с текстом `continue`. `failed` требует ручного продолжения, а `completed` не повторяется. Результаты, появившиеся за время отсутствия Lawa, учитываются. Существующая память не очищается; исходная постановка задачи сохраняется.

Готовые, но ещё не запущенные кубики стартуют; существующие чаты и уже выполненные запуски не дублируются. Если создание чата завершилось до сбоя, но его ID не сохранился, сначала восстанавливается связь. При неоднозначности — ошибка, не новый чат вслепую.

Отсутствующий или повреждённый `workflow.json`, `task.md` либо `meta.json` — ошибка `resume`, не новый run. Одним `runId` одновременно управляет только один процесс Lawa.

## Память агентов

- Lawa сообщает агенту его `threadId`, абсолютный путь к собственному файлу памяти и соответствие кубиков файлам памяти коллег в этом run. Правила памяти передаются отдельно от исходного промпта и не меняют `workflow.json`.
- Агент записывает только полезное для своей задачи: важные факты, решения, найденные данные, ссылки на результаты, на чём остановился и что осталось сделать. Память — краткая рабочая заметка, не копия диалога или полный лог.
- Агент обновляет память по ходу работы. Он может дополнять, исправлять и полностью перезаписывать свой файл, сохраняя актуальную полезную информацию.
- При начале и продолжении работы, в том числе после компактификации, агент читает собственную память и восстанавливает контекст. Путь и правило чтения должны оставаться доступны в инструкциях чата.
- Перед завершением работы агент записывает в свой файл итоговый отчёт: что сделано, какой результат получен, где лежат результаты и какие ограничения остались.
- Все агенты run могут читать память коллег. Чужая память может быть незавершённой; её наличие не заменяет ожидание успеха нужного кубика через `dependsOn`.
- В папке run агент может изменять только `memory/<свой-threadId>.md`. Чужую память, `workflow.json`, `task.md` и `meta.json` редактировать, удалять или перезаписывать нельзя.
- После ручного перезапуска и `resume` используется тот же файл памяти. Lawa не пишет отчёты за агентов и не оценивает их содержание; запуск зависимых кубиков по-прежнему определяется статусом в Codex.

## Границы MVP и проверка

Без собственного harness, изменения плана, циклов, автоматических повторов failed-агента, отдельной БД, хранилища полных логов, проверки артефактов, других провайдеров, отдельного UI и сервера. Единственный автоматический повтор — один `continue` для interrupted-чата на явный вызов `resume`. Скилл `lawa` и чат-инициатор как интерфейс запуска и наблюдения, папка запуска, память агентов и продолжение run входят в MVP. `run` всегда создаёт новый запуск; для продолжения используется `resume`. Созданные агентами файлы не откатываются; новый независимый запуск не должен конфликтовать с ещё работающими задачами.

Критерии готовности:

- Пользователь формулирует задачу в отдельном чате Codex и вызывает `/lawa <название-workflow> [комментарий]`. Агент запускает выбранный workflow с этой постановкой и комментарием; до явного вызова запуск не начинается. При недостающей постановке или неоднозначном названии агент сначала уточняет ввод.
- Чат-инициатор остаётся интерфейсом управления: агент сообщает `runId`, существенные изменения статуса, необходимость вмешательства и итог. По запросу пользователя показывает текущий статус и продолжает остановленный run через `resume`, не создавая новый. Для кубиков создаются отдельные чаты.
- Каждый кубик получает общую постановку задачи и комментарий вместе со своим промптом. Изменения обсуждения в чате-инициаторе не меняют сохранённый вход run; при `resume` используется тот же `task.md`.
- Цепочка зависимостей выполняется последовательно, независимо от порядка кубиков в `steps`.
- Независимые кубики запускаются без лимита Lawa; сборщик ждёт всех успешных входов. Ошибка одной ветки не останавливает остальные и не завершает flow.
- Кубик падает, пользователь перезапускает тот же чат, его статус меняется на «выполняется», затем на успех. Зависимые кубики стартуют только после успеха и ровно один раз. После успеха всех кубиков утилита возвращает `0`, несмотря на прежнюю ошибку.
- Новый run создаёт папку `~/.light-ai-workflows/<run-id>/` с `workflow.json`, `task.md`, `meta.json` и `memory/<threadId>.md`. ID запуска, чата-инициатора, кубиков и их чатов сохраняются при `resume`; изменение исходной схемы не меняет run.
- Lawa остановлена, пользователь исправляет упавший кубик в том же чате. После `resume` утилита видит успех и ровно один раз запускает зависимые кубики, не создавая повторно прежние чаты.
- Ctrl+C прерывает активные turn и завершает Lawa с `130`. Следующий `resume` отправляет ровно один `continue` только чатам с последним статусом `interrupted`; `failed` и `completed` не получают новых turn.
- Сбой при сохранении метаданных, неоднозначное создание чата и одновременный `resume` не приводят к дублированию задач или потере сохранённого состояния.
- После компактификации агент читает свою память и продолжает с сохранённого места; перед завершением записывает итоговый отчёт. Ручной повтор и `resume` сохраняют этот файл.
- Агент может читать память коллег и перезаписывать свою. Попытки изменить чужую память, `workflow.json`, `task.md` или `meta.json` запрещаются настройками доступа Codex.
- `help` и `skill` работают без настроенного агента; примеры JSON проходят проверку формата, инструкция объясняет запуск из чата-инициатора, наблюдение за run и правила памяти. Скилл `lawa` доступен для вызова в Codex.
- Невалидный граф отклоняется до создания задач. Сигналы адресно отменяют активные turn и останавливают утилиту. Проверки выполняются с подставным клиентом Codex App.
- Интеграционный тест: чаты видны в Codex App; `lawa` замечает ручное продолжение после ошибки и запускает зависимые кубики после успеха. Нужны настроенный доступ и разрешение на расход запросов; собственные агентские процессы `lawa` не запускает.
