# Lawa: продуктовый контракт

## Назначение

Lawa исполняет статический JSON-DAG через отдельные Codex App Server thread.
Готовые независимые кубики запускаются параллельно, зависимости открываются только
после успеха, а состояние сохраняется для наблюдения и продолжения.

## Пользовательский интерфейс

Основной интерфейс одинаков на рабочем компьютере и Linux-сервере:

```sh
lawa validate workflow.json
lawa run workflow.json --cwd /absolute/project --task-file task.md
lawa resume <run-id>
lawa status <run-id>
lawa logs <run-id> [step-id] [--follow]
lawa serve
```

Lawa скрывает запуск процессов, RPC, thread и turn. Выбора runtime нет.

## Runtime

Единственный runtime — `codex app-server --stdio`. Наличие Codex Desktop не
меняет исполнение и не гарантирует отображение thread в приложении.

App-native runtime не поддерживается: у Desktop нет публичного программного API
для внешнего процесса, а agent-mediated orchestration добавляет задержку,
стоимость и ограничивает массовый параллелизм.

## Workflow

Workflow содержит непустой `id` и массив `steps`. Кубик содержит:

- уникальный `id`;
- `type`;
- непустой `prompt`;
- необязательный `depends_on`;
- необязательные model/effort/speed overrides.

Ссылки ведут только на существующие кубики, граф ацикличен. Независимые ready
кубики образуют одну параллельную волну.

## Исполнение

До внешнего запроса Lawa сохраняет Starting для всей волны. После `thread/start`
сохраняется thread ID, после `turn/start` — turn ID. Ошибка без ID после попытки
создания считается неоднозначной и не повторяется автоматически.

Каждый активный turn получает отдельный процесс App Server. Одна read-only сессия
используется для последовательного reconcile известных неактивных thread.

На SIGINT/SIGTERM новые волны не запускаются, активным turn отправляется точечный
interrupt. `resume` автоматически продолжает только interrupted turn.

## Хранилище

Run хранит неизменяемые `workflow.json` и `task.md`, атомарный `meta.json`,
нормализованный `events.jsonl`, память кубиков и локальные отчёты. Один run
защищён межпроцессным lock.

Кубик читает файлы run и память коллег, но пишет только собственную память.
Постановка, prompt и память не должны содержать секреты.

## Наблюдаемость

`status` показывает scheduler state, thread/turn, PID и последнюю активность.
`logs` и dashboard используют только нормализованные события Lawa.

Reasoning, command/tool payload, diff и raw rollout не сохраняются. Ошибка записи
журнала останавливает новые запросы.

## Серии

Immediate, after и cron создают последовательные самостоятельные run. Одновременно
активен не более одного run серии. После failed/interrupted действует
stop-on-failure; `series-stop` запрещает будущие run, не прерывая текущий.

## Совместимость

Новые данные имеют формат v3. Исторические app-server v1/v2 продолжают работать.
Исторические app-native данные с marker-файлами доступны только для чтения, чтобы
не создавать дубликаты задач Desktop.
