# Lawa: продуктовый контракт

## Назначение

Lawa исполняет версионированные JSON-workflow через отдельные Codex App Server
thread. Legacy-режим остаётся строгим DAG, а version 2 разрешает агенту выбрать
один из статически заданных маршрутов, включая ограниченный цикл. Lawa не
вычисляет бизнес-условия: смысл результата всегда оценивает отдельный агент.

## Пользовательский интерфейс

Основной интерфейс одинаков на рабочем компьютере и Linux-сервере:

```sh
lawa validate workflow.json
lawa run workflow.json --cwd /absolute/project --task-file task.md
lawa resume <run-id>
lawa status <run-id>
lawa logs <run-id> [step-id] [--visit <visit-id>] [--follow]
lawa serve
```

Lawa скрывает запуск процессов, RPC, thread и turn. Выбора runtime нет.

## Runtime

Единственный runtime — `codex app-server --stdio`. Наличие Codex Desktop не
меняет исполнение и не гарантирует отображение thread в приложении.

App-native runtime не поддерживается: у Desktop нет публичного программного API
для внешнего процесса, а agent-mediated orchestration добавляет задержку,
стоимость и ограничивает массовый параллелизм.

## Workflow

Workflow содержит непустой `id` и массив `steps`. Общие поля кубика:

- уникальный `id`;
- `type`;
- непустой `prompt`;
- необязательные model/effort/speed overrides.

Контракты взаимоисключающие:

- отсутствие `version` или `version: 1`: каждый кубик имеет явный `dependsOn`,
  ссылки ведут на существующие кубики, граф ацикличен, зависимость открывается
  только после технического успеха;
- `version: 2`: workflow имеет непустой `start`, каждый кубик — явный `after`, а
  кубик решения — непустой `decisions`. `after` ждёт любой терминальный
  технический исход и не является бизнес-условием.

Решение содержит именованный ключ и ровно один статический маршрут: непустой `to`
либо terminal `finish: succeeded|failed`. Агент передаёт один ключ и необязательное
объяснение только через `choose_decision`. Отсутствующий, неизвестный, повторный
или конфликтующий ключ завершает run с диагностикой, ничего не запуская по
умолчанию. Технически `failed` кубик решения не применяет маршрут. Обычный
рабочий кубик не вызывает `choose_decision` и не обязан возвращать типизированный
JSON. Один `to` может атомарно открыть несколько параллельных кубиков.

Цикл допустим только через маршрут кубика решения. Каждый входящий в цикл кубик
решения имеет положительный `maxVisits`; `onLimit` задаёт terminal и по умолчанию
равен `failed`. Статический after-цикл запрещён. `when`, `successWhen`,
`failureWhen`, `eval` и выполнение пользовательского кода в маршрутизации не
поддерживаются. Каждый кубик должен быть достижим из `start` и иметь путь к
естественному листу, `finish` либо явному `onLimit`.

## Исполнение

До внешнего запроса Lawa сохраняет Starting для всей волны. После `thread/start`
сохраняется thread ID, после `turn/start` — turn ID. Ошибка без ID после попытки
создания считается неоднозначной и не повторяется автоматически.

Для version 2 каждое посещение имеет собственный `visitId`, thread, turn и память.
Агент решения получает исходную задачу, причинные технические статусы и безопасную
диагностику, номер посещения/итерации и доступную память. Выбор сохраняется раньше
планирования следующего маршрута; повтор после crash не меняет его и не создаёт
уже материализованные visits заново. Не выбранные достижимые ключи отмечаются
`skipped`. Внутри одного plan порядок задают массив `to` и порядок `steps`, а уже
сохранённые переходы не переигрываются при resume; хронология независимых волн
может зависеть от времени завершения агентов.

Каждый активный turn получает отдельный процесс App Server. Одна read-only сессия
используется для последовательного reconcile известных неактивных thread.

На SIGINT/SIGTERM новые волны не запускаются, активным turn отправляется точечный
interrupt. `resume` автоматически продолжает legacy interrupted turn и
`cancelled` visit v2 в том же чате. Технический `failed` visit не перезапускается,
но может удовлетворить `after` кубика восстановления.

## Хранилище

Run хранит неизменяемые `workflow.json` и `task.md`, атомарный `meta.json`,
нормализованный `events.jsonl`, память исполнений и локальные отчёты. Legacy run
использует metadata v3 и состояния steps; version 2 — append-only metadata v4 с
общим `runState`, visits, решениями, попытками, итерациями, skipped и причиной
остановки. Один run защищён межпроцессным lock.

Кубик читает файлы run и память коллег, но пишет только собственную память.
Постановка, prompt и память не должны содержать секреты.

## Наблюдаемость

`status` показывает scheduler state, thread/turn, PID и последнюю активность. Для
v2 он также выводит visit/iteration, решение, маршрут, skipped, лимит и причину
остановки. `logs --visit` и dashboard адресуют точное посещение, а поиск по step ID
собирает всю его историю. Dashboard показывает каждое посещение отдельно.

Raw reasoning, полные command/tool payload, diff и raw rollout не сохраняются.
Разрешённая краткая reasoning summary доступна только в приватном dashboard.
Ошибка записи журнала останавливает новые запросы.

## Серии

Immediate, after и cron создают последовательные самостоятельные run. Одновременно
активен не более одного run серии. После failed/interrupted действует
stop-on-failure; `series-stop` запрещает будущие run, не прерывая текущий.

## Совместимость

Новые legacy-workflow получают metadata v3, workflow version 2 — metadata v4.
Новые series сохраняют собственный формат v3. Исторические app-server metadata
v1/v2 и сохранённые v3 продолжают работать без изменения поведения.
Исторические app-native данные с marker-файлами доступны
только для чтения, чтобы не создавать дубликаты задач Desktop.
