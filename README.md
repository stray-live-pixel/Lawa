# Lawa

Go-утилита для JSON-workflow из задач AI-агентов. Требования полного приложения:
[продуктовое описание](product/1.md).

## Что уже работает

**Офлайн-проверка workflow.** Команда `validate`
проверяет обязательные поля, типы, уникальность ID, ссылки и отсутствие циклов.
Она не обращается к Codex, не создаёт запусков и не изменяет файлы.
`validate` — дополнительная диагностическая команда к командам целевого MVP.

**Планировщик зависимостей** ([`internal/scheduler`](internal/scheduler/scheduler.go)) выбирает готовые кубики по
полному снимку состояний. Независимые кубики готовы одновременно, сборщик ждёт
успеха всех зависимостей. Ошибка, отмена и ожидание подтверждения не считаются
успехом; ручное продолжение учитывается новым снимком того же запуска.
Это внутренний модуль для будущего исполнителя, не новая команда CLI.

**Папки запусков** ([`internal/runstore`](internal/runstore/store.go)) сохраняют исходный
JSON, постановку с комментарием, ID и начальные состояния шагов, пустые файлы памяти.
Повторное чтение сохраняет эти данные и не очищает память. На macOS/Linux
`OpenLocked` блокирует run для одного координатора, а `Update` атомарно сохраняет
статусы и постоянные связи с чатами. Это внутренний модуль, не команда запуска.

**Клиент Codex** ([`internal/codex`](internal/codex/client.go)) запускает отдельный
официальный app-server, создаёт чат, сразу отправляет текст или явный вызов скилла
и читает события до завершения одного turn. Это внутренний Go API, не команда CLI.

**Инструкция скилла.** Команда `skill` печатает самодостаточные правила запуска
workflow из чата Codex, наблюдения, `resume` и работы агентов с памятью. Она ничего
не устанавливает и перед запуском требует проверить, доступны ли будущие `run` и
`resume`, поэтому текущая версия не создаёт ложный запуск.

**Исполнение workflow пока не реализовано:** нет `run` и `resume`
и управления живыми задачами через Codex App. Успешная валидация не подтверждает доступность Codex,
корректность рабочей папки, качество промптов или выполнимость задач агентами.

## Сборка и использование

Нужен Go 1.27.0 или новее; это последний стабильный релиз на 2026-08-28
([релизы Go](https://go.dev/dl/)). Версия закреплена в `go.mod`; внешних
Go-зависимостей нет. При стандартном `GOTOOLCHAIN=auto` более старый Go
загрузит нужную версию для проекта, не заменяя системную установку.

```sh
go build -o bin/lawa ./cmd/lawa
./bin/lawa help
./bin/lawa skill
./bin/lawa validate examples/review.json
```

Код выхода `0` означает успешную проверку/справку; `2` — ошибку. Диагностика ошибок
пишется в stderr, успешный результат — в stdout. Нужен ровно один JSON-объект;
неизвестные поля, другой регистр имён, повторные ключи и зависимости отклоняются.
`dependsOn` обязателен: `[]` допустим, пропуск и `null` — нет. Строки не исправляются
автоматически: повреждённый UTF-8 и непарные суррогаты в JSON отклоняются.
Пример специально записан не в порядке выполнения: метрики →
два независимых ревью → сборщик, ожидающий оба ревью.

## Проверки и устройство

```sh
go test -race ./...
go vet ./...
```

`internal/workflow` содержит общую проверку схемы и графа без побочных эффектов.
Разбор выполняет стандартный `encoding/json/v2`: он отклоняет неоднозначный JSON
и читает до EOF. Проверки обязательных полей и графа остаются в нашем `Validate`.
`cmd/lawa` отвечает за аргументы, чтение файла и вывод. Будущий исполнитель должен
использовать ту же проверку до создания задач и отдельно проверять среду и подключение.
Оставшиеся интеграционные вопросы описаны в [проверке Codex](docs/codex-integration.md).

### Контракт клиента Codex

`codex.Run(ctx, Command)` выполняет один новый запрос. Нужны абсолютный `CWD`
и непустой `Text`; `Executable` по умолчанию — `codex` из PATH. `Title` необязателен.
Для явного скилла передайте `Skill{Name, Path}`: клиент добавит `$Name` в текст
и отдельный input типа `skill`. Скилл уже должен быть доступен Codex для этого cwd:
используйте имя и путь из `skills/list`, произвольный SKILL.md не заменяет установку.
Файл читает Codex. Модель и права берутся
из настроек Codex; необязательный `Sandbox` проверяет сам сервер. `cwd` не задаёт
границу доступа. Shell, закрепление чата и изменение настроек Desktop не нужны.

Кубики работают автономно: в `thread/start` и `turn/start` передаются
`approvalPolicy: "on-request"` и `approvalsReviewer: "auto_review"`. Обычные действия
идут внутри sandbox, запросы дополнительных прав проверяет встроенный агент Codex.
Lawa не выдаёт автоматическое согласие и не меняет настройки Desktop. Отказ
managed restrictions возвращается без обхода. Ручной ввод и авторизация внешних
сервисов всё ещё могут потребовать пользователя. См. [автопроверку Codex](https://learn.chatgpt.com/docs/sandboxing/auto-review).

`OnThread` получает ID до отправки команды: ошибка сохранения запрещает turn.
Намерение создания вызывающий код сохраняет **до Run**. На ошибке возвращается
частичный `Result` с известными ID и консервативными флагами попыток; пустой ID
не означает отсутствия чата. Автоматических повторов, удаления чатов и восстановления
между вызовами нет. `runstore` ещё не подключён: повтор Run создаёт новую задачу.

Сообщение с ID и `Method` от сервера — встречный запрос, на который нужен ответ. `Respond`
получает все такие запросы — не только разрешения и ввод. Обработчик должен
выбрать форму ответа по `Event.Method` и проверить `Event.Params`. Для неподдерживаемого
метода он возвращает `InteractionRequired`; без `Respond` клиент делает это сам.
Только служебный `currentTime/read` обрабатывается автоматически. `Notify` получает уведомления.
Nil error означает
получение терминального статуса. `completed` — завершение без ошибки исполнения,
но не проверка смысла ответа; `failed` и `interrupted` остаются отдельными результатами.
Для `failed` поле `Result.TurnError` сохраняет сообщение, дополнительные сведения
и исходный `codexErrorInfo`. Последний остаётся JSON, потому что протокол допускает
как строковые коды, так и объекты с параметрами и может добавлять новые варианты.
Ошибки RPC доступны через
`errors.As` к `*codex.RPCError`, ошибки обработчиков сохраняются в `errors.Is`.

Клиент владеет своим процессом до возврата Run. Отмена контекста, ошибка или возврат
закрывают его и могут прервать активного агента. Это **не** готовый механизм фонового
исполнения workflow: будущий координатор должен обеспечить отдельный жизненный цикл
сервера и безопасную передачу живой задачи. Текущий клиент не заменяет Desktop и
не обещает доставку разрешений в его окно.

Обычные тесты используют подставной процесс без модели. `TestIntegration` требует
явно заданного `LAWA_CODEX_INTEGRATION_BIN` и разрешения на расход запросов: он создаёт
тестовый чат и проверяет запуск скилла в read-only sandbox, допуская чтение инструкций.
Автоматически этот тест пропускается. Он использует автопроверку Codex и не отвечает
согласием на запросы дополнительных прав из Lawa. Чтение инструкций и передача их содержимого
модели требуют разрешения пользователя до запуска теста.

Проверка на 2026-08-29 с `codex 0.150.0-alpha.12.2` из Codex Desktop прошла:
клиент создал задачу, сам отправил команду со скиллом и получил `LAWA_CLIENT_OK`.
Задача `01a04ac8-6206-76a3-bfe1-c4438faca8e5` доступна через API Desktop;
её история подтверждает чтение инструкций и завершение turn. В сохранённом контексте
проверены `on-request`, `auto_review` и `read-only`. Ручная отправка и подтверждения,
перезапуск Desktop и изменения его общих настроек не понадобились. Проверено чтение,
но не запись рабочими агентами или передача живого исполнения в Desktop.

Первоначальный `untrusted` требовал согласия даже на чтение. Попытку `never` отвергли
локальные MDM requirements: разрешены только `untrusted` и `on-request`.
Это объясняет выбор автопроверки Codex, а не отключения контроля. Политика передаётся
также в `turn/start`: одного `thread/start` в проверенной версии было недостаточно.

### Контракт планировщика

`scheduler.Evaluate` получает проверяемый workflow и явное состояние каждого шага.
Пропущенные/лишние шаги и неизвестные состояния отклоняются целиком. Результат —
готовые `Ready`, ожидающие зависимостей `Waiting` и `Complete`, означающий успех
всех шагов в текущем снимке. Уже начатых шагов в списках нет. Порядок списков
совпадает с `steps`, но все готовые задачи можно запускать параллельно без лимита Lawa.

До запроса создания чата координатор должен сохранить `Starting` и передавать
обновлённый снимок дальше. При ошибке записи запрос запрещён; при неизвестном
результате создания требуется восстановить связь, а не возвращать шаг в `Pending`.
Повторное вычисление само ничего не резервирует: тот же снимок даёт тот же план.
Блокировку и запись статусов предоставляет `runstore.OpenLocked`; будущий адаптер
Codex должен использовать их до запросов. Планировщик сам по себе не гарантирует
однократность сетевых запросов.

Только `Succeeded` открывает зависимости. Новый `Running` после успеха снова
блокирует ещё не начатые шаги с прямой зависимостью от него; уже начатые не отменяются
и не запускаются заново. Успешные промежуточные шаги остаются успешными: повтор предка
не обесценивает их результаты и не добавляет неуказанные зависимости.
Снимок должен описывать актуальную работу в чатах, включая ручные продолжения;
потеря подтверждённого статуса передаётся как `Unknown`, а не как прежний успех.
Пакет не интерпретирует протокол Codex и не проверяет качество результатов агентов.

### Контракт хранения

`runstore.Create(root, input)` проверяет workflow, постановку, ID чата-инициатора
и существование рабочей папки. Root передаётся явно; будущий CLI выберет
`~/.light-ai-workflows`. Каждый вызов создаёт новый `runId` и отдельные `threadId`;
ID из workflow остаются ключами графа и никогда не используются как пути.
JSON копируется побайтно, `task.md` содержит отдельные разделы постановки и комментария.
Каталоги создаются с правами `0700`, файлы — `0600`. Это приватность на уровне ОС,
не замена профиля доступа Codex для агентов с тем же пользователем ОС.

`meta.json` версии 1 публикуется переименованием после записи и `Sync` остальных
файлов. Агенты могут стартовать только после успешного возврата `Create`.
Перед созданием run имена новых каталогов `root` сохраняются через `Sync` их
родителей, от существующего предка к дочерним папкам. Существующая папка тоже
сохраняется через `Sync` её родителя: она могла остаться после неудачной попытки.
При отказе run не создаётся; общие пустые папки могут остаться для повтора.
Предки выше найденной существующей папки считаются ранее сохранёнными и не должны
удаляться или перемещаться во время `Create`. Родители должны быть доступны для `Sync`.
При обычной ошибке после создания run удаляется только новая папка. Возвращается
пустой снимок и `*runstore.CreateError`: абсолютный `RunDir`, исходная `Cause`
и отдельная `CleanupErr` (nil, если удаление удалось). Через `errors.As` можно
получить эти поля, через `errors.Is` — проверить системные причины. Текст ошибки
содержит операцию и путь из ошибки ОС, результат очистки и подсказку: проверить
место/квоту, лимит размера файла, права либо состояние диска. Такие внешние сбои
возможны и при корректном коде. Если удаление тоже отказало, сообщение это явно
указывает: после устранения причин нужно удалить только этот новый `RunDir`.
Права и чужие файлы автоматически не меняются. Повторить создание можно после
устранения причин: агенты нового run ещё не запускались, старые run не затрагиваются.
Это правило нельзя применять к ошибкам сохранения уже работающих агентов.
Сбой процесса/питания может оставить неполный run: очистка не гарантируется,
её результат не синхронизируется для защиты от потери питания.
`Load(root, runId)` проверяет входы, связи, состояния и наличие файлов памяти.
Чаты кубиков должны отличаться друг от друга и от чата-инициатора; совпадение ID — ошибка.
Конфликт с инициатором возвращает `ErrInitiatorAsExecutor` с ID запуска и шага;
его можно распознать через `errors.Is`. Это защита от искусственного тестового
случая, невозможного при корректной штатной записи связей, а не известный реальный
инцидент. Контекст и правила обработки описаны рядом с ошибкой в `internal/runstore`:
автоматически создавать нового агента нельзя, поскольку прежний может ещё работать.
Неполные/повреждённые данные отклоняются целиком; чтение ничего не создаёт и не очищает.
Выход через пути и симлинки за границы хранилища запрещён; root должен быть доверенным.
Содержимое памяти и смысл Markdown не проверяются, контрольных сумм входов пока нет.
Сохранённые статусы не подтверждают текущую работу чатов: будущий `resume` должен
сначала получить актуальные статусы из Codex под блокировкой запуска.

### Обновление состояний и блокировка

`OpenLocked(root, runId)` проверяет сохранённый run и возвращает владельца с
методами `Load`, `Update(stepId, state, codexThreadId)` и `Close`. Он удерживает
блокировку всё время работы координатора, включая запросы Codex. Второй процесс
получает `ErrRunLocked` без ожидания. `coordinator.lock` создаётся с `0600` и не
удаляется: блокировку снимает ОС при закрытии или выходе процесса. Наличие файла
не означает занятость. Это контракт локальной ФС macOS/Linux; сетевые ФС не проверены.

Сначала `Update` сохраняет `Starting` без ID, затем разрешён запрос создания чата.
Полученный или достоверно восстановленный ID привязывается к этому же шагу.
Начатый шаг нельзя сбросить в `Pending`, известный чат — заменить или стереть.
Ручные продолжения меняют статус того же чата, в том числе `Succeeded → Running`.
Проверка готовности зависимостей и сверка с Codex остаются задачей координатора.

Новая meta записывается в отдельный файл с `0600`, проходит `Sync`/`Close`, затем
атомарно заменяет прежнюю; после этого синхронизируется каталог. Ошибка сохранения
запрещает новые запросы и дальнейшие `Update`/`Load` у этого владельца. После ошибки
нужны `Close`, повторное открытие и сверка с Codex: новая meta уже могла стать видна.
Отката, удаления run и очистки памяти нет. Незавершённые `.meta-*.tmp` не читаются
и не мешают следующей записи. Агенты не должны изменять эти файлы и `coordinator.lock`;
пока координатор работает, нельзя заменять/удалять run, его root или lock-файл.

## Что осталось до рабочего MVP

1. **Подключение к Codex App:** подтвердить общий сервер и видимость чатов, затем
   реализовать создание, наблюдение, восстановление связи и права памяти.
   Перезапуск приложения и тестовые запросы требуют отдельного разрешения;
   условия описаны в [проверке интеграции](docs/codex-integration.md).
2. **Команды `run` и `resume`:** соединить хранение, планировщик и адаптер; передавать
   постановку и память, показывать статусы, учитывать ручные продолжения и сигналы.
3. **Запуск из чата:** установить выведенную командой `skill` инструкцию как
   `/lawa`; выбор workflow и наблюдение уже описаны, но зависят от `run`/`resume`.
4. **Сквозная проверка:** параллельные ветки и сборщик, ошибка и ручной повтор,
   остановка Lawa и `resume` без дубликатов; реальный Codex на macOS/Linux.
