# Commit: проверенные изменения → коммит → пуш → PR

## Договор с пользователем

Явный вызов `/commit` или `$commit` означает коммит относящихся к задаче изменений,
пуш рабочей ветки и создание либо обновление PR. Дополнительный текст можно использовать
как тему коммита. Если обычная просьба явно ограничена локальным коммитом или запрещает
публикацию, выполни только разрешённую часть. Автоматический выбор скилла сам по себе
не разрешает внешние действия. Слияние в этот сценарий не входит.

Пример: `$commit Добавить проверку циклов workflow`.

## Проверить и определить границы

1. Прочитай `AGENTS.md`. Проверь `git status --short --branch`, staged и unstaged diff,
   untracked-файлы, remotes и историю. Определи файлы и коммиты именно текущей задачи.
2. Получи свежие ссылки `git fetch origin`. Проверь, что GitHub-репозиторий соответствует
   `origin`; передавай его явно в `gh` через `--repo`. В этом проекте PR направляется
   в `main`. Не создавай remote или fork без запроса.
3. Найди PR текущей ветки через `gh pr list --head <ветка> --base main --state all`.
   Учитывай состояние PR: не отправляй новую доработку в ветку уже слитого или закрытого
   PR. При неоднозначном соответствии задачи, ветки и PR сначала уточни цель.
4. На `main` не коммить и не пушь. Если готовые изменения находятся там, создай
   `codex/<имя-задачи>` от текущего HEAD с сохранением файлов, затем проверь историю
   относительно `origin/main`. Не переноси изменения поверх чужой работы.

## Проверки перед коммитом

- Просмотри полный diff будущего PR от merge-base с `origin/main`, а не только последний
  коммит. Учти текущие и новые файлы. Оцени сумму добавлений и удалений полного diff,
  включая код, тесты и документацию, а не чистый прирост. Ориентир — 500 строк.
- При размере от 501 до 1200 строк продолжай коммит, push и создание PR без
  дополнительного согласования. Явно предупреди пользователя о крупном PR, укажи
  точный размер в описании PR и итоговом сообщении.
- При размере больше 1200 строк остановись до `git add`, коммита и публикации.
  Предложи разбиение на самостоятельные готовые PR и согласуй его с пользователем.
- PR должен содержать законченную работоспособную часть, готовую к production.
- Не исправляй несвязанные проблемы и не урезай тесты или пояснения ради лимита.
  Размер до 1200 строк сам по себе не требует переработки реализации.
- Запусти подходящие проверки проекта либо используй результаты текущей сессии,
  только если относящиеся к ним файлы с тех пор не изменились. Выполни `git diff --check`.
  Не называй непроведённые проверки успешными. Не отключай hooks и CI ради коммита.
- Проверь отсутствие секретов и случайных артефактов. Не добавляй файл только потому,
  что он оказался untracked. Не включай посторонние staged-изменения и не снимай их
  с индекса без согласия; при смешанном индексе сначала уточни границы.

## Коммит и публикация

1. Проверь настроенные имя и email автора. Если их нет, запроси у пользователя;
   не выдумывай автора и не меняй глобальные настройки Git.
2. Добавляй файлы по явным путям через `git add -- <пути>`, не через `git add .`.
   Для смешанных изменений в одном файле сначала согласуй разделение, не коммить
   весь файл вслепую. Проверь staged diff и `git diff --cached --check`.
3. Создай обычный коммит с понятной темой, например `feat: validate workflow cycles`.
   Не делай amend и не переписывай историю без отдельного запроса.
4. Если изменений для нового коммита нет, не создавай пустой коммит. Проверь уже
   существующие коммиты, состояние удалённой ветки и PR и продолжи недостающий этап.
   Если нет ни изменений, ни отличий ветки от `origin/main`, сообщи, что публиковать
   нечего; не создавай пустой PR.
5. Отправь ветку явно: `git push -u origin <рабочая-ветка>`. При отказе из-за расхождения
   истории проверь причину и остановись; не используй force-push или автоматический reset.
6. Если открытый PR уже существует, новые коммиты обновят его автоматически.
   При необходимости обнови только описание этого PR. Иначе создай PR с явными
   `--repo`, `--base main`, `--head <ветка>`, `--title` и `--body`.
   В описании укажи законченный результат, причины решений, проверки и ограничения.
7. При потере ответа на push или создание PR сначала перечитай удалённое состояние
   и найди PR по head/base. Не создавай дубликат при повторном вызове.

Git и GitHub CLI должны быть доступны и настроены. При отсутствии доступа сообщи
точный завершённый этап и препятствие; не устанавливай инструменты, не меняй права
и не выполняй вход в чужую учётную запись автоматически.

## Завершение

Сообщи хеш коммита, ссылку на PR, размер изменения и существенные ограничения проверок.
Если выполнен только локальный коммит или push без PR, назови это явно.
Не переходи к merge автоматически.
