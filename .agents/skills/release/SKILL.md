# Release: актуальная main → проверенная сборка → публичная версия

## Договор с пользователем

Явный вызов `/release` или `$release` запускает подготовку, но не разрешает создать
или отправить release-тег, пока пользователь не согласовал **точную** версию вида
`vMAJOR.MINOR.PATCH`. После такого согласования разрешено запустить штатный GitHub
Actions workflow и отредактировать публичное описание созданного Release.
Автоматическое обнаружение скилла само по себе не разрешает публикацию.

Аргументом может быть точная стабильная версия (`v1.2.3`) или тип повышения
(`major`, `minor`, `patch`). Точная версия, явно указанная пользователем в запросе,
уже считается согласованной. Тип повышения и вызов без аргумента согласованием не
считаются: выбери минимальное корректное повышение по изменениям после прошлого
Release, объясни выбор и запроси подтверждение точного тега. До ответа не создавай
тег, draft или Release и ничего не публикуй.

Скилл выпускает уже готовый `main`. Он не реализует исправления, не сливает PR и
не публикует произвольную рабочую ветку. Если проверки требуют изменения кода,
остановись: исправление должно пройти обычные этапы `solve` → `review` → `commit`
→ `merge`, а релиз запускается заново после обновления `main`.

Не удаляй, не передвигай и не пересоздавай теги. Не удаляй Release или его assets,
не используй force-push и не обходи защиту репозитория.

## Зафиксировать прошлую и будущую версии

1. Прочитай `AGENTS.md`. Проверь корень репозитория, `origin`,
   `git status --short --branch` и `git worktree list`. Рабочая папка и индекс
   должны быть чистыми, включая untracked-файлы. Не делай автоматический stash.
2. Сопоставь `origin` с `stray-live-pixel/Lawa`. Во всех командах `gh` передавай
   `--repo stray-live-pixel/Lawa`, чтобы совпавшее имя или номер не выбрали другой
   репозиторий.
3. Выполни `git fetch origin --tags`, переключись на `main` и обнови её только через
   `git pull --ff-only origin main`. Локальная `main` и `origin/main` должны указывать
   на один коммит; занятый другим worktree или разошедшийся `main` не исправляй
   автоматически.
4. Получи последний публичный стабильный Release через GitHub и отдельно просмотри
   стабильные теги и черновики. Прошлой версией считается именно последний публичный
   стабильный Release. Более новый тег, draft или несоответствие Release и Git-истории
   сначала расследуй: не выпускай следующую версию поверх неоднозначного состояния.
5. Проверь, что прошлый тег входит в историю проверяемого `main` и после него есть
   изменения. Если `main` уже совпадает с прошлой версией, публиковать нечего.
6. Определи следующий SemVer:
   - точный аргумент пользователя имеет приоритет;
   - для `v0.x` новая возможность или несовместимое публичное изменение повышает
     `MINOR`, а совместимое исправление, документация или release tooling — `PATCH`;
   - начиная с `v1.0.0`, несовместимый контракт повышает `MAJOR`, совместимая
     возможность — `MINOR`, исправление — `PATCH`.
7. Принимаются только теги вида `vMAJOR.MINOR.PATCH` без суффиксов и ведущих нулей.
   Новая версия должна быть строго выше прошлой. Убедись, что её нет среди локальных
   и удалённых тегов, GitHub Releases и draft Releases.
8. Покажи пользователю прошлую версию, предлагаемый точный тег, причину выбранного
   повышения и краткий состав изменений. Если точный тег не был указан пользователем
   изначально, остановись и дождись явного подтверждения. Ответ вроде «да», «ОК» или
   повтор точного тега считается подтверждением только в контексте этого предложения.

Зафиксируй SHA актуального `main`. Все проверки, тег, workflow и Release должны
относиться именно к нему. Если SHA изменился после согласования, оно больше не
действует: начни оценку заново и повторно согласуй точную версию для нового состава.

## Подготовить содержательные release notes

Описание готовь **до отправки тега**, чтобы после сборки осталось только опубликовать
уже проверенный текст. Используй временный файл вне рабочей папки.

Обязательно исследуй полный диапазон `<прошлый-тег>...<проверенный-SHA>`:

- first-parent историю и все вошедшие коммиты;
- полный diff и его статистику;
- названия и описания вошедших PR;
- пользовательскую документацию для новых команд, параметров и ограничений.

Release notes должны начинаться с `Что изменилось с <прошлая-версия>` и объяснять
пользовательский результат, а не пересказывать имена файлов или сырые commit messages.
Добавляй только применимые разделы, но проверь каждый из них:

- новые возможности и способы их использовать;
- исправления и изменения надёжности;
- совместимость, миграция и существенные известные ограничения;
- заметные изменения документации, примеров или сайта;
- команды обновления и новой установки;
- поддерживаемые платформы, состав Release и актуальные ограничения установки из
  `README.md` и `.github/workflows/release.yml`;
- ссылка сравнения `<прошлый-тег>...<новый-тег>` и ссылки на основные PR.

Не оставляй вместо changelog общий текст вроде «готовый релиз для macOS и Linux».
Не приписывай версии неподтверждённые возможности. Не скрывай migration steps или
известное ограничение, если они влияют на безопасное использование новой функции.

## Проверить и собрать точную версию

Запусти проверки для зафиксированного SHA:

```sh
go test -race -count=1 ./...
go vet ./...
go mod tidy -diff
sh -n install.sh
shellcheck --shell=sh install.sh
git diff --check <прошлый-тег>...HEAD
```

Отсутствующий локально `shellcheck` не считается успешной проверкой. Это допустимый
пробел только потому, что Linux job штатного Release workflow запускает ShellCheck
до публикации; явно зафиксируй пробел и всё равно дождись успешного CI. Любая
фактическая ошибка проверки блокирует тег.

Во временной папке собери четыре автономных бинарника с точным будущим тегом в
linker metadata:

- `darwin/amd64`;
- `darwin/arm64`;
- `linux/amd64`;
- `linux/arm64`.

Используй `CGO_ENABLED=0`, `-trimpath` и тот же `-ldflags -X` для
`internal/buildinfo.Version`, что задан в `.github/workflows/release.yml`. На
нативной платформе проверь:

- `lawa version` печатает будущий тег;
- `lawa help` завершается успешно;
- `lawa skill` побайтно совпадает с `cmd/lawa/SKILL.md`.

Перед тегом повторно проверь чистоту папки, совпадение `HEAD` с `origin/main` и
сохранность зафиксированного SHA.

## Запустить штатную публикацию

1. Создай на зафиксированном SHA аннотированный тег с сообщением `Lawa <тег>`.
2. Отправь только точный ref: `git push origin refs/tags/<тег>`. Не создавай Release
   вручную: push тега `v*` запускает `.github/workflows/release.yml`, который сначала
   проверяет Ubuntu и macOS, а затем собирает draft, проверяет assets и делает его
   публичным.
3. Найди workflow по точному тегу, SHA и времени запуска. Дождись терминального
   результата через `gh run watch --exit-status`. Обычно достаточно десяти минут;
   если workflow остаётся в очереди дольше, не объявляй релиз опубликованным и сообщи
   его ссылку и текущее состояние.
4. При transient-сбое сначала установи причину, затем можно один раз перезапустить
   тот же run. При ошибке кода или конфигурации не передвигай тег: эта версия уже
   занята, исправление требует нового PR и следующего SemVer.
5. После успешного workflow найди Release по точному тегу и замени только его notes
   подготовленным changelog через `gh release edit --notes-file`. Сохрани название,
   tag, assets и статус Release. После неопределённого ответа сначала перечитай
   Release, а не повторяй изменение вслепую.

## Проверить публичный результат

Успех подтверждён только когда одновременно выполнено следующее:

- workflow завершился с `success`;
- Release не draft и не prerelease, а `/releases/latest` указывает на новый тег;
- тег и Release относятся к зафиксированному SHA;
- публичны ровно обязательные assets: `install.sh`, `SHA256SUMS` и четыре архива
  `darwin/linux × amd64/arm64` с новым тегом в имени;
- описание явно сравнивает новую версию с прошлой, содержит пользовательские
  изменения и правильную compare-ссылку;
- все публичные assets скачаны во временную папку, архивы и `install.sh` проходят
  проверку опубликованным `SHA256SUMS`;
- нативный бинарник из **скачанного публичного архива** печатает новый тег и успешно
  выполняет `help`; его встроенный скилл совпадает с опубликованным ожидаемым скиллом;
- локальная ветка остаётся чистой `main`, совпадающей с `origin/main`.

Если точный Release уже полностью опубликован, повторный вызов ничего не создаёт:
перепроверь его и при необходимости дополни только отсутствующие release notes.
Если есть тег без готового Release, найди связанный workflow и продолжи диагностику;
не создавай новый тег с тем же именем.

## Завершение

Коротко сообщи версию, ссылку на Release, SHA `main`, результат workflow и проверенные
платформы/assets. Отдельно назови оставшийся пробел или ограничение. Не называй
публикацией один только push тега, draft или ещё выполняющийся workflow.
