# Merge: готовый PR → слияние → актуальный main

## Договор с пользователем

Явный вызов `/merge` или `$merge` разрешает слить указанный PR, переключиться
на `main` и обновить его. Номер или URL можно взять из аргумента; без аргумента
используй однозначно связанный PR текущей задачи. Автоматическое обнаружение скилла
не является разрешением на слияние. Не удаляй ветки и worktree без отдельного запроса.

Примеры: `$merge 12`, `$merge` после публикации PR в этом чате.

## Определить точную цель

1. Прочитай `AGENTS.md`. Проверь корень репозитория, remotes, `git status --short --branch`
   и `git worktree list`. При локальных изменениях остановись до слияния:
   не делай stash и не рискуй потерять работу при последующем переключении.
2. Сопоставь репозиторий PR с `origin`. Передавай `--repo` явно; не сливай PR из другого
   репозитория по совпавшему номеру. Если не удаётся однозначно определить PR,
   спроси его номер или URL, не выбирай последний открытый PR наугад.
3. Получи свежие данные через `git fetch origin` и `gh pr view`:
   `state`, `isDraft`, `baseRefName`, `headRefName`, `headRefOid`, `mergeable`,
   `mergeStateStatus`, `reviewDecision`, `statusCheckRollup`, `files`, `mergeCommit`.
   Ожидаемая база — `main`; другую базу не меняй и не сливай молча.
4. Если PR уже `MERGED`, повторное слияние не нужно: перейди к обновлению `main`.
   Если PR закрыт без слияния, остановись, не открывай его заново.
5. Если локальная ветка этой задачи содержит незапушенные коммиты или её HEAD
   отличается от проверенного head PR, выясни расхождение до слияния.
   Не сливай устаревшую версию задачи и не публикуй новые коммиты в этом сценарии.

## Условия слияния

- Проверь состав полного PR, его самостоятельность и размер по правилам `AGENTS.md`.
  Ориентир — 500 строк. Размер от 501 до 1200 строк не блокирует слияние, но явно
  обрати внимание пользователя на крупный PR. Если PR больше 1200 строк, не сливай
  его без отдельного решения о разбиении. Не урезай проверки ради размера.
- Не сливай draft, конфликтующий PR, PR с запросом изменений от ревьюера, проваленными
  проверками или невыполненными требованиями ветки. Не применяй `--admin` и не отключай
  защиту ветки. Исправление кода и конфликтов требует отдельного запроса.
- Для `UNKNOWN` один раз перечитай состояние. Если оно не определилось, остановись.
  Для выполняющихся проверок используй `gh pr checks --watch --fail-fast` в управляемой
  сессии, чтобы можно было сообщать прогресс. Не запускай бесконечные повторные попытки:
  по умолчанию жди не более пяти минут, затем сообщи, что слияние ещё не выполнено.
- Если CI не настроен, это не означает «проверки прошли». Оцени доступные результаты
  проверок именно текущего head PR. Для документации достаточно просмотра diff
  и проверки форматирования; для кода нужны подходящие проекту тесты и сборка.
  При отсутствии нужных подтверждений готовности остановись и объясни пробел.
- Зафиксируй проверенный `headRefOid`. При изменении head повтори оценку готовности
  для новой версии; не сливай непроверенные коммиты.

## Слияние и обновление

1. Используй обычный merge commit и защиту от смены head:
   `gh pr merge <номер> --repo <репозиторий> --merge --match-head-commit <проверенный-SHA>`.
   Если правила репозитория запрещают этот способ, сообщи ограничение; не обходи его.
2. Не включай `--auto` без запроса. Если правила GitHub отправили PR в очередь,
   не объявляй его слитым: проверь фактический статус. При необходимости ожидания
   используй механизм ожидания или мониторинга среды, не обещай незапущенное наблюдение.
3. После ответа перечитай PR: успех — `state: MERGED` и известный `mergeCommit`.
   При потере ответа сначала проверь состояние, а не повторяй слияние вслепую.
4. Переключись через `git switch main`, затем выполни `git pull --ff-only origin main`.
   Если локального `main` нет, создай его от `origin/main` с tracking.
   При расхождении истории не делай reset, rebase или force-push: сохрани состояние
   и сообщи проблему. Если `main` занят другим worktree, не меняй его автоматически.
5. Проверь, что текущая ветка — `main`, HEAD совпадает с `origin/main`, коммит слияния
   входит в его историю, а рабочая папка чистая.

## Завершение

Коротко сообщи ссылку на слитый PR и актуальный коммит `main`.
Разделяй результаты: «PR слит, но локальный main не обновлён» — частичное выполнение,
а очередь или включённое ожидание GitHub ещё не означают слияние.
