# Merge: PR → слияние → актуальный main

## Полномочия и цель

`/merge`, `$merge` или явная просьба разрешает слить указанный PR и обновить локальный
`main`. Возьми номер или URL из запроса либо однозначно связанный PR текущей задачи.
Автоматическое срабатывание скилла разрешения не даёт. Если цель неоднозначна, запроси
номер или URL. Не исправляй код, не обходи защиту и не удаляй ветки или worktree.

Используй только операции `git` и `gh`. Не запускай тесты, сборку, линтеры, форматтеры
и другие проверочные скрипты. Готовность определяй по состоянию PR в GitHub.

## Проверка

1. Прочитай `AGENTS.md`. Определи корень репозитория и `origin`. Убедись, что PR
   относится к `origin`, и во всех командах `gh` передавай `--repo`.
2. До слияния проверь `git status --short --branch`, `git worktree list` и локальную
   ветку задачи. При незакоммиченных изменениях или незапушенных коммитах, относящихся
   к PR, остановись: не сливай устаревший результат и не меняй локальное состояние.
3. Через `gh pr view` проверь состояние, draft, базу, SHA head, mergeability, решение
   ревью и проверки GitHub. Ожидаемая база — `main`; другую не сливай без нового явного
   решения пользователя.
4. Если PR уже слит, переходи к обновлению `main`; если закрыт без слияния — остановись.
   Не сливай draft, конфликтующий PR, PR с запросом изменений, проваленными или ещё
   выполняющимися обязательными проверками. Не используй `--admin` и `--auto`.
5. Если состояние неизвестно, один раз обнови данные, затем остановись. Если head
   изменился после проверки, проверь новую версию заново.

## Слияние и обновление

1. Выполни обычный merge commit с защитой от смены проверенного head:
   `gh pr merge <номер> --repo <репозиторий> --merge --match-head-commit <SHA>`.
   Если политика репозитория запрещает этот способ, остановись.
2. Перечитай PR. Слияние подтверждено только при `state: MERGED` и известном
   `mergeCommit`; очередь GitHub и потерянный ответ успехом не считай и команду вслепую
   не повторяй.
3. Проверь `git status --short --branch` и `git worktree list`. Если изменения мешают
   переключению или `main` занят другим worktree, не меняй локальное состояние.
   Иначе переключись на `main` и выполни `git pull --ff-only origin main`. Если
   локального `main` нет, создай tracking-ветку от `origin/main`. При расхождении
   истории не делай reset, rebase, stash или force-push.
4. Проверь текущую ветку, чистоту рабочей папки, совпадение HEAD с `origin/main` и
   наличие merge commit в истории.

## Результат

Сообщи ссылку на PR и актуальный коммит `main`. Явно отдели полное выполнение от
частичного: например, «PR слит, локальный main не обновлён».
